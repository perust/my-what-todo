# daily-todo — Claude Code 단계별 프롬프트

PRD(`todo-app-prd.md` v1.2)를 Claude Code에 넘길 5개 프롬프트로 변환한 문서다.

> **이 문서는 처음 만들 때 쓴 기록이다. 지금의 지시가 아니다.**
> 5단계는 이미 다 지났고, 그 뒤로 앱이 훨씬 멀리 왔다. 여기 적힌 "완료 검증"과
> "하지 말 것"은 **그 시점의** 기준이라 지금 것과 어긋나는 대목이 있다.
> 지금 지켜야 할 제약은 언제나 저장소 뿌리의 [`CLAUDE.md`](../CLAUDE.md)에 있다.
> 둘이 다르면 `CLAUDE.md`가 맞다.

## 사용 전 준비

```
daily-todo/
├── CLAUDE.md              ← 아래 내용으로 먼저 생성
└── docs/
    └── todo-app-prd.md    ← PRD 파일을 여기에 둔다
```

**진행 규칙**

1. 단계 프롬프트를 **그대로 복사해서** 붙여넣는다. 요약하거나 줄이지 않는다 — "하지 말 것" 목록이 이 문서의 핵심이다.
2. 한 단계가 끝나면 **커밋하고 `/clear`로 컨텍스트를 비운다.** 각 프롬프트는 독립적으로 동작하도록 썼다.
3. Claude Code가 "다음 단계도 이어서 할까요?"라고 물으면 **거절한다.** 단계 경계가 무너지면 어디서 깨졌는지 못 찾는다.
4. 각 단계의 `완료 검증`을 직접 통과시킨 뒤 다음으로 넘어간다.

프로젝트 내내 변하지 않는 제약이다. 매 프롬프트에서 반복하지 않기 위해 따로 둔다.

**→ [`CLAUDE.md`](../CLAUDE.md)**

여기 사본을 두지 않는다. 처음에는 초안을 이 자리에 붙여뒀는데, `CLAUDE.md`가 자라는
동안 이쪽은 그대로 굳어 **두 벌이 조용히 어긋났다.** 그냥 낡기만 한 것이 아니라
*이유*가 뒤집힌 대목이 있었다 — 옛 사본은 "ES 모듈을 쓰지 않는 것은 `file://`에서
막히기 때문"이라고 적어뒀지만, 실제 이유는 모듈 스크립트가 언제나 지연 실행이라
`store.js`가 첫 페인트를 놓친다는 것이다(F-14). `file://`은 이제 지원 대상도 아니다.
그 낡은 이유를 읽으면 "이제 Pages로 서비스하니 모듈을 써도 되겠네"가 되고,
그러면 테마 깜빡임이 그대로 되살아난다.

블로그에 앱 사본을 두지 않기로 한 것과 같은 판단이다. 사본은 갱신을 잊는 것이
기본값이고, 잊었다는 사실은 사고가 난 뒤에야 드러난다.

## 1단계 — 데이터 계층

UI 없이 로직만 완성한다. 이 단계가 끝나면 앱의 두뇌는 전부 만들어져 있고, 이후 단계는 화면 붙이는 일만 남는다.

```
docs/todo-app-prd.md 를 읽어줘. 특히 §4(기능 요구사항), §5(데이터 모델),
§8(엣지 케이스)을 정확히 따라야 해.

이번 단계 목표: UI 없이 데이터 계층만 완성한다. 화면은 그리지 않는다.

## 만들 것

1. `index.html` — 빈 껍데기. `<div id="app"></div>` 하나와
   parse.js → store.js 순서의 script 태그만 둔다.

2. `parse.js` — 순수 함수 하나를 export(전역 `Parse` 객체로 노출)한다.
   `Parse.parseInput(raw)` → `{ title, priority, tags }`
   - 우선순위: 제목 맨 앞의 `!` 하나만 소비해서 "high". 나머지는 "normal".
   - 태그: 제목 **끝에서 역방향으로** 연속된 `#단어`만 파싱. 앞에 공백 필수.
   - PRD §4 F-05, F-07의 입력 규칙 예시가 전부 그대로 통과해야 한다.
   - 태그 정규화: trim, 영문 소문자화, 중복 제거, 최대 5개.

3. `store.js` — 전역 `Store` 객체. PRD §5의 헬퍼를 전부 구현한다.
   - CRUD: `load, save, add, addChild, update, remove, toggle`
   - 조회: `getRoots(filter), getChildren(parentId), isLeaf(id),
            getStats(filter), getAllTags(filter), getDescendants(id),
            isContextRow(id, filter)`
   - **완료 전파** (F-11): 하향/상향/상향해제 전부.
   - **정렬** (F-06): 형제 그룹 안에서만. `priority` 1차, `order` 2차.
     완료 여부는 정렬에 영향 없음.
   - **집계** (F-10): 리프만 센다. 하위가 있는 상위는 분모에서 제외.
   - **필터** (F-09): `{type:"all"} | {type:"category",value} | {type:"tag",value}`
   - **로드 시 검증**: PRD §8의 "로드 시 검증 순서"를 그 순서대로 구현.
     스키마 검증 → priority/tags 교정 → 순환 참조 제거 → 고아 승격 →
     깊이 평탄화 → order 재정렬
   - `localStorage` 접근 불가 시 메모리 배열로 폴백. `Store.isPersistent`로 노출.

## 하지 말 것

- CSS 파일을 만들지 마라.
- `app.js`를 만들지 마라.
- 렌더링 코드, 이벤트 핸들러를 한 줄도 쓰지 마라.
- 테스트 프레임워크를 설치하지 마라.

`index.html`을 브라우저에서 열고 콘솔에 아래를 붙여넣었을 때
주석에 적힌 결과가 나와야 한다. 안 나오면 고쳐라.

```js
Store.load();
const a = Store.add(Parse.parseInput("!세금 신고"), "work");
Store.addChild(a.id, Parse.parseInput("서류 모으기 #세금"));
const b = Store.addChild(a.id, Parse.parseInput("홈택스 입력"));

Parse.parseInput("C# 공부 #cs #복습");
// { title: "C# 공부", priority: "normal", tags: ["cs","복습"] }

Store.getStats({type:"all"});
// { done: 0, total: 3, percent: 0 }  ← "세금 신고"는 하위가 있어 제외

Store.toggle(b.id);
Store.getChildren(a.id).filter(x => x.completed).length;  // 1

Store.toggle(a.id);

Store.getRoots({type:"all"})[0].title;                    // "세금 신고" (높음이 위)
Store.getAllTags({type:"all"});                           // [{tag:"세금", openCount:0}]

로 데이터가 살아있는지 확인하고 끝낸다.

## 2단계 — 평면 목록으로 동작하는 앱

계층 없이 먼저 쓸 수 있는 앱을 만든다. store에는 이미 모든 필드가 있지만 화면은 평평하게 그린다.

```

## 만들 것

1. `styles.css` — PRD §7의 스타일 방향을 따른다.

  **편집창에 태그를 다시 합쳐 넣지 마라.** 제목만 보여준다.
- **삭제 + 실행 취소** (F-04): 확인 다이얼로그 없이 즉시 삭제.
  하단에 5초짜리 실행 취소 토스트. 복원 시 원래 순서 위치로.

## 3단계 — 계층

렌더링을 2중 루프로 교체하고 하위 할 일을 붙인다. 데이터 계층은 이미 계층을 알고 있으므로 이 단계는 순수하게 화면 작업이다.

## 고칠 것

`app.js`의 렌더링을 2중 루프로 교체한다.
- 바깥 루프: `Store.getRoots(filter)`
- 안쪽 루프: `Store.getChildren(root.id)`
- **재귀를 쓰지 마라.** 깊이가 2로 고정이므로 필요 없다.
- 마크업은 `<ul>` 안에 `<ul>`을 중첩한다. 들여쓰기를 CSS로만 흉내 내지 마라.

## 추가할 기능

- **하위 추가** (F-02): 상위 항목 hover/focus 시 `+` 버튼 노출.
  클릭하면 그 상위 바로 아래에 인라인 입력창이 열린다.
  Enter → 하위 추가되고 **입력창이 그 자리에 유지**되어 연속 입력 가능.
  Esc 또는 빈 상태 Enter → 입력창 닫힘.
  하위 입력에서도 `Parse.parseInput`을 동일하게 적용한다.
- **3단계 차단**: 하위 항목에는 `+` 버튼이 없다.
- **완료 전파 표시** (F-11): `Store.toggle`이 이미 전파를 처리하므로
  재렌더만 하면 된다. 다만 부분 완료 상위는 네이티브 속성으로 표시한다.
  `checkbox.indeterminate = !item.completed && children.some(c => c.completed)`
  CSS로 흉내 내지 마라.
- **캐스케이드 삭제 UI** (F-04): 상위 삭제 시 토스트 문구에 총 개수 표시.
  "4개 항목이 삭제됨". 실행 취소 시 트리 구조와 순서가 전부 복원된다.
- **하위는 카테고리 UI 없음**: 배지도, 변경 수단도 표시하지 않는다.
  상위 카테고리를 바꾸면 하위도 따라 바뀐다(이미 store가 처리).

## 스타일

- 하위 항목 왼쪽 24px 들여쓰기 + 상위-하위를 잇는 1px 세로 연결선

- 하위 추가 버튼에 `aria-label="하위 할 일 추가: {상위 제목}"`

## 4단계 — 우선순위 · 태그 · 필터 · 진행률

파생 뷰를 한꺼번에 붙인다. 넷 다 "store가 계산한 결과를 어떻게 보여줄까"라는 같은 문제라서 함께 간다.

```
docs/todo-app-prd.md 의 §2(분류 축 역할 구분), §4 F-05~F-10,
§7(우선순위 표현, 태그 표현)을 따른다.
store.js는 이미 정렬·필터·집계를 전부 구현하고 있다. 수정하지 마라.

이번 단계 목표: 우선순위, 태그, 필터, 진행률의 화면 표현.

## 추가할 기능

### 우선순위 (F-05, F-06)
- 항목 왼쪽에 우선순위 마커. **클릭하면 높음→보통→낮음→높음 순환.**
- **`보통`에는 아무 표시도 하지 않는다.** 단, 마커 영역의 **자리는 차지한다**
  (히트 영역이 필요하고, 자리가 들쭉날쭉하면 왼쪽 정렬이 흔들린다).
- 높음: 3px 세로 accent 바 + 제목 굵게
- 낮음: 제목 명도 하강. **취소선은 쓰지 마라** — 완료와 헷갈린다.
- 정렬은 store가 이미 한다. 재렌더만 하면 제자리에 이동한다.
- `aria-label="우선순위 변경: {제목}, 현재 높음"` (색만으로 구분되지 않게)

### 태그 (F-07)
- 제목 오른쪽에 배지. **카테고리 배지보다 약한 대비.**
- **태그에는 색을 쓰지 마라.** 색은 카테고리 전용이다.
- hover 시 `×` 노출 → 개별 삭제
- 3개 초과 시 `+2`로 접고, 항목에 포커스하면 전부 펼친다
- 배지는 `<button>`으로 만들고 클릭하면 그 태그로 필터링
- `aria-label="태그 필터: 세금"`

### 필터 (F-09)
- 상단 탭: `전체 / 업무 / 개인 / 공부`
- 그 아래 태그 바: `Store.getAllTags(filter)` 결과를 미완료 개수와 함께 노출
- **필터 상태는 하나뿐이다.** 카테고리 필터 중 태그를 누르면
  카테고리 필터가 **해제되고** 태그 필터로 전환된다. 반대도 동일.
  두 축을 동시에 켜지 마라.
- 활성 필터 재클릭 또는 `전체` 탭 → 해제
- 태그 필터에서는 매칭된 하위의 상위를 **문맥 행**으로 함께 표시한다.
  문맥 행: 체크박스 비활성, 흐리게, 삭제·편집 버튼 미노출,
  `aria-disabled="true"`. 이벤트 위임 핸들러에서도 조작을 한 번 더 막는다.
- 필터 중인 태그를 가진 항목이 0개가 되면 자동으로 `전체`로 복귀
- 태그가 하나도 없으면 태그 바 자체를 숨긴다 (빈 줄 남기지 마라)

### 진행률 (F-10)
- 상단에 `완료 수 / 전체 수` + 백분율 + 가로 프로그레스 바
- `Store.getStats(filter)`를 그대로 쓴다. **app.js에서 다시 계산하지 마라.**
- `role="progressbar"` + `aria-valuenow`

### 입력창 도움말
`placeholder` 아래에 한 줄 상시 노출: `!로 시작하면 높음, 끝에 #태그`
접두어 규칙은 발견되지 않으면 없는 기능이다.

## 하지 말 것

- 다중 태그 필터(AND/OR)를 만들지 마라.
- 태그 자동완성을 만들지 마라.
- 태그 이름 일괄 변경/삭제를 만들지 마라.
- 우선순위를 4단계 이상으로 늘리지 마라.
- 우선순위나 태그를 하위에 상속시키지 마라. 각자 독립이다.
- 진행률에 우선순위 가중치를 주지 마라. 모든 리프가 1개다.

## 완료 검증

1. `!세금 신고 #급함` 입력 → 제목 "세금 신고", 높음 마커, `#급함` 배지,
   목록 위쪽에 배치됨
2. 상위 하나에 하위 3개를 붙인 뒤 진행률을 확인 → **분모에 상위가 안 들어간다.**
   상위 2개(각 하위 3개) + 하위 없는 상위 1개면 분모는 7이다.
3. `업무` 탭 클릭 → 업무 트리만, 진행률도 업무 기준으로 재계산
4. 그 상태에서 태그 배지 클릭 → 카테고리 탭이 해제되고 태그 필터로 전환
5. 하위에만 붙은 태그로 필터 → 그 상위가 문맥 행으로 흐리게 나오고,
   체크박스가 눌리지 않으며, 진행률 분모에 안 들어간다
6. 필터 중인 태그의 마지막 항목 삭제 → 자동으로 `전체`로 복귀
7. 우선순위 마커를 세 번 클릭 → 높음→보통→낮음→높음 순환, 매번 재정렬
8. 완료 체크를 해도 항목이 **이동하지 않는다** (정렬은 우선순위에만 반응)
```

## 엣지 케이스

PRD §8의 세 표(파싱 / 계층·상태 / 저장·환경)를 **한 행씩 확인하고**

- 손상된 JSON → `daily-todo:v1:corrupted`로 이관 후 빈 목록 시작 + 배너

- 빈 화면은 안내가 아니라 행동 유도다. 사과하지 마라.

## 접근성 (PRD §9)

- 우선순위와 카테고리가 **색만으로 구분되지 않는지** 확인
