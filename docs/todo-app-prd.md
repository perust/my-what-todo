## 1. 배경과 목표

### 문제
머릿속에 뭉쳐 있는 "지금 해야 할 일"을 실행 가능한 단위로 **쪼개서** 눈앞에 늘어놓고 관리하고 싶다. 쪼개고 나면 하루에 10~20개가 나오는데, 이 규모를 부담 없이 담아둘 도구가 없다. 기존 도구는 계정 로그인, 동기화, 협업 기능까지 딸려 와서 이 용도에는 과하다. 필요한 건 **쪼갠 항목을 빠르게 넣는 속도**, **그중 뭐부터 할지 가려내는 수단**, 그리고 **지금 얼마나 했는지**다.

### 성공 기준
- 상위 할 일 하나를 3개로 쪼개는 데 마우스를 잡지 않아도 된다
- 20개를 입력하면서 우선순위와 태그까지 **키보드만으로** 붙일 수 있다
- 앱을 열자마자 3초 안에 "지금 뭐부터 해야 하는지" 파악된다
- 새로고침, 브라우저 재시작, 기기 재부팅 후에도 데이터가 그대로다

### 비목표 (v1에서 하지 않는 것)
스코프가 넘치면 완성되지 않는다. 아래는 **명시적으로 제외**한다.

- **3단계 이상 중첩** (§4 F-02 참조)
- **다중 태그 동시 필터** (AND/OR 조합)
- **태그 자동완성, 태그 이름 일괄 변경/삭제**
- 드래그로 **부모 바꾸기** (같은 형제 안에서의 순서 바꾸기는 F-19로 지원한다)
- 로그인, 계정, 서버, 데이터베이스
- 기기 간 동기화, 클라우드 백업
- 마감일, 알림, 반복 일정
- 빌드 도구, 번들러, npm 의존성

## 2. 용어

| 용어 | 정의 |
|---|---|
| **상위 할 일** | `parentId`가 `null`인 항목. 카테고리를 가진다. |
| **하위 할 일** | `parentId`가 상위 항목을 가리키는 항목. 카테고리는 상위에서 상속하되, 우선순위와 태그는 독립적으로 가진다. |
| **리프(leaf)** | 하위 할 일이 하나도 없는 항목. 하위 할 일은 항상 리프이고, 하위가 없는 상위 할 일도 리프다. |
| **문맥 행** | 태그 필터에서, 자신은 태그가 없지만 매칭된 하위를 가져서 문맥용으로만 표시되는 상위 항목. |

> **리프가 진행률의 단위다.** 상위 할 일에 하위가 붙는 순간 그 상위는 "묶음 라벨"이 되고, 실제로 세는 대상은 하위들이다. 이 규칙 하나가 §4 F-10 전체를 결정한다.

### 세 가지 분류 축의 역할 구분

셋을 한 문서에 넣으면 금방 겹치므로 역할을 못 박는다.

| 축 | 값 | 개수 | 상속 | 정렬에 영향 | 용도 |
|---|---|---|---|---|---|
| **카테고리** | 사용자가 관리 (기본 3종) | 항목당 1개 (필수) | 하위가 상위를 상속 | 없음 | 삶의 영역 구분 |
| **우선순위** | 0~3 (0이 가장 높음) | 항목당 1개 (기본 `1`) | 상속 없음 | **있음** | 순서 결정 |
| **태그** | 자유 입력 | 항목당 0~5개 | 상속 없음 | 없음 | 임의 묶기 |

## 4. 기능 요구사항

### F-01. 상위 할 일 추가

상단 입력창에 제목을 쓰고 카테고리를 골라 목록에 추가한다.

**수용 기준**
- [ ] 입력창에서 `Enter` 또는 `추가` 버튼으로 등록된다
- [ ] 등록 직후 입력창이 비워지고 **포커스가 유지**된다 (S1을 위해 필수)
- [ ] 카테고리는 직전에 선택한 값이 기본값으로 유지된다
- [ ] 제목 문자열에서 우선순위와 태그를 파싱한다 (F-05, F-07)
- [ ] 공백만 입력하면 등록되지 않고, 입력창 포커스도 그대로다 (에러 문구 없음)
- [ ] 파싱 후 제목이 100자를 넘으면 차단한다
- [ ] 새 항목은 형제 그룹 안에서 우선순위 규칙에 따라 배치된다 (F-06)

### F-02. 하위 할 일 추가

상위 할 일을 실행 단위로 쪼갠다. **깊이는 2단계까지만 허용한다.**

**수용 기준**
- [ ] 상위 항목에 마우스를 올리거나 포커스하면 `+` 버튼이 노출된다
- [ ] `+` 클릭 시 해당 상위 항목 바로 아래에 인라인 입력창이 열린다.
      **같은 `+`를 다시 누르면 닫힌다** — 연 것을 같은 자리에서 닫는다.
      그 버튼은 `aria-expanded`로 지금 어느 쪽인지 알리고 이름도 함께 바뀐다
- [ ] 입력창 옆에 **`추가` 버튼과 `×` 버튼을 함께 둔다.** 둘 다 **항상 보인다** —
      hover로 숨기면 터치 화면에서 빠져나갈 길이 사라진다
- [ ] 입력 후 `Enter` 또는 `추가` → 하위 항목이 추가되고
      **입력창이 그 자리에 유지된다** (연속 입력). 둘은 같은 코드를 탄다
- [ ] `Esc`, `×`, 빈 상태로 `Enter` → 입력창이 닫힌다.
      **빈 칸에서 `추가`를 누르는 것은 닫지 않는다** — 넣겠다고 누른 것이지 그만두겠다는 뜻이 아니다
- [ ] 하위 입력에서도 `!`·`#` 파싱이 동일하게 동작한다
- [ ] 하위 항목에는 `+` 버튼이 없다 (3단계 차단)
- [ ] 하위 항목은 카테고리 선택 UI가 없다 (상위에서 상속)

> **왜 2단계인가**: 저장 스키마(`parentId`)는 임의 깊이를 표현할 수 있다. 깊이를 제한하는 것은 **UI뿐**이다. 나중에 3단계가 필요해지면 렌더링과 `+` 버튼 노출 조건만 고치면 되고, 데이터 마이그레이션은 없다. 반대로 처음부터 무한 깊이를 지원하면 재귀 렌더링, 캐스케이드 삭제 범위, 진행률 집계가 전부 재귀가 되면서 "복잡하지 않게"라는 조건이 깨진다.

### F-03. 할 일 수정

**수용 기준**
- [ ] 제목을 클릭하면 인라인 편집 모드로 전환되고 텍스트가 전체 선택된다
- [ ] 편집 시 원본 제목만 보여준다 — **태그는 제목 문자열에 다시 합치지 않는다** (F-07 참조)
- [ ] `Enter`로 저장, `Esc`로 취소, 포커스가 벗어나면 저장
- [ ] 편집 중 입력한 `!`·`#`도 새로 파싱된다
- [ ] 빈 제목으로 저장하면 취소로 처리한다 (삭제하지 않는다)
- [ ] 상위/하위 항목 모두 동일하게 동작한다
- [ ] 상위 카테고리를 바꾸면 **하위 항목의 카테고리도 함께 갱신된다**
- [ ] 완료된 항목도 수정할 수 있다

**카테고리 바꾸기**

한 번 정한 카테고리를 나중에 옮긴다. 제목 편집과 같은 방식이다 — 그 자리에서 바뀌고, 고르면 들어가고, `Esc`로 물린다.

**수용 기준**
- [ ] 상위 항목의 **카테고리 배지를 누르면** 그 자리에서 카테고리 목록으로 바뀐다
- [ ] 고르는 즉시 반영된다. `Esc`를 누르거나 고르지 않고 빠져나가면 바뀌기 전으로 돌아간다
- [ ] 같은 카테고리를 다시 골랐으면 저장하지 않는다. 판 번호만 올라가고 바뀌는 것이 없다
- [ ] 하위 항목에는 배지가 없다. 하위의 카테고리는 **상위를 통해서만** 바뀐다 —
      `Store.update`가 하위의 `category` patch를 거부한다 (§8 참조)
- [ ] 문맥 행의 배지는 누를 수 없다. 보여주기만 한다
- [ ] 고르는 동안에는 목록을 다시 그리지 않는다. 통째로 헐면 고르던 목록이 함께 사라진다

> **왜 순환 버튼이 아닌가**: 카테고리는 64개까지 늘어나므로(F-13) 열 개만 돼도 원하는 것에 닿기까지 아홉 번을 눌러야 한다. 우선순위도 같은 이유로 목록에서 고른다 — 네 단계뿐이지만 **누를 때마다 정렬이 다시 걸려 그 항목이 자리를 옮긴다** (F-05).

### F-04. 할 일 삭제

**수용 기준**
- [ ] 각 항목의 삭제 버튼으로 즉시 삭제된다 (확인 다이얼로그 없음)
- [ ] **상위 항목 삭제 시 하위 항목도 함께 삭제된다** (캐스케이드)
- [ ] 삭제 직후 하단에 `실행 취소` 토스트가 5초간 뜬다
- [ ] 하위가 함께 삭제된 경우 토스트에 총 개수를 표시한다 — "4개 항목이 삭제됨"
- [ ] 실행 취소 시 **상위·하위의 구조, 순서, 우선순위, 태그가 전부** 복원된다
- [ ] 마지막 하위 항목을 지우면 상위 항목은 다시 리프가 된다 (진행률 분모에 다시 포함)
- [ ] **그 5초 동안에는 다른 알림이 토스트 자리를 뺏지 않는다.** 밀린 알림은
      실행 취소 창이 닫힌 뒤에 뜬다 (F-22의 뽀모도로 알림이 대표적이다)
- [ ] **되돌릴 것을 세운 뒤에 목록을 그린다.** 위 규칙은 이미 걸린 것이 있을 때만
      걸리는데, 자동 복귀 알림(F-09)은 그리는 도중에 나온다. 순서를 뒤집으면
      그 알림이 실행 취소 토스트에 곧바로 덮여 사라진다

### F-05. 우선순위

**0 / 1 / 2 / 3** 네 단계. **0이 가장 높다.** 기본값은 `1`.

**수용 기준**
- [ ] 모든 항목이 우선순위를 가지며, 지정하지 않으면 `1`이다
- [ ] 상위와 하위는 **각자 독립적으로** 우선순위를 가진다 (상속 없음)
- [ ] 입력창 **카테고리 옆 선택 상자**로 0~3을 고른다. 직전 선택값이 유지된다
- [ ] 선택지는 **숫자만** 적는다. `가장 높음` 같은 설명은 붙이지 않는다 —
      몇 번 써 보면 알게 되는 규칙이고, 매번 읽히면 목록보다 선택 상자가 넓어진다.
      대신 `aria-label`과 도움말(F-21)이 그 사실을 알린다
- [ ] 제목 **맨 앞**의 `!` 하나는 `0`으로 해석되고 제목에서 제거된다.
      선택 상자보다 `!`가 **이긴다** — 방금 친 글자가 미리 골라둔 값보다 최근이다
- [ ] 항목의 우선순위 마커를 누르면 **그 자리에서 `0`~`3`을 고르는 목록이 열린다.**
      고르면 바로 바뀌고, `Esc`를 누르거나 고르지 않고 빠져나가면 물러난다.
      제목 편집·카테고리 변경과 같은 방식이다
- [ ] 우선순위 변경 즉시 형제 그룹 안에서 재정렬된다 (F-06)
- [ ] 저장값은 **숫자**다. 숫자 자체가 순위라 정렬 가중치 표를 따로 두지 않는다

**입력 규칙**

`priority`는 **지정했을 때만** 값을 가진다. `null`은 "안 적었다"는 뜻이고, 그때 무엇을 쓸지는 호출부(입력창 선택값 또는 기본값)가 정한다.

```
"!세금 신고"   → priority: 0,    title: "세금 신고"
"세금 신고"    → priority: null, title: "세금 신고"    (선택 상자 값을 쓴다)
"중요! 확인"   → priority: null, title: "중요! 확인"   (맨 앞이 아니면 무시)
"!!긴급"      → priority: 0,    title: "!긴급"        (하나만 소비)
```

낮추는 접두어는 두지 않는다. 급한 걸 빠르게 올리는 게 접두어의 목적이고, 나머지는 선택 상자와 마커 클릭으로 충분하다. 접두어가 늘수록 제목에 기호를 쓸 때 부딪힐 여지만 커진다.

> **왜 0이 가장 높은가**: 사용자가 정한 규칙이다. "1순위"라는 일상 어법과는 어긋나지만, 배열 첨자와 정렬 가중치가 그대로 일치해 코드에 변환 계층이 생기지 않는다.

> **왜 하위에 상속하지 않나**: 쪼개는 이유가 "이 중에 뭐가 급한지 가리려고"인데, 상위 우선순위를 하위가 물려받으면 그 구분이 사라진다. 카테고리는 삶의 영역이라 트리 전체가 공유하는 게 자연스럽지만, 우선순위는 실행 단위마다 다르다.

### F-06. 우선순위 기반 정렬

**형제 그룹 안에서만** 정렬한다. 트리 구조는 절대 깨지지 않는다.

```js
const compare = (a, b) => a.priority - b.priority || a.order - b.order;
```

**수용 기준**
- [ ] 상위 항목끼리는 상위 항목끼리, 하위 항목은 같은 부모의 형제끼리만 정렬된다
- [ ] 1차 기준은 우선순위, 2차 기준은 추가 순서(`order`)다
- [ ] **완료 여부는 정렬에 영향을 주지 않는다** (완료해도 제자리 유지)
- [ ] 우선순위를 바꾸면 그 자리에서 즉시 이동한다

> 완료 토글은 하루에 20번 일어나므로 항목이 움직이면 위치 기억이 깨진다. 반면 우선순위 변경은 드물게, 그리고 의도적으로 하는 동작이라 이동이 오히려 피드백이 된다. 그래서 정렬은 우선순위에만 반응한다.

### F-07. 태그

자유 입력. 카테고리는 만들고 지우는 데 한 번 손이 가지만, 태그는 제목을 치면서 그 자리에서 붙는다.

**수용 기준**
- [ ] 제목 **끝쪽에 연속으로 나열된** `#태그`만 태그로 파싱되고 제목에서 제거된다
- [ ] 태그 앞에는 반드시 공백이 있어야 한다
- [ ] 항목당 최대 5개까지 저장하고, 초과분은 버린다
- [ ] 앞뒤 공백 제거, 영문은 소문자로 정규화, 중복 제거
- [ ] 상위와 하위는 각자 독립적으로 태그를 가진다 (상속 없음)
- [ ] 태그 배지는 항목 제목 오른쪽에 표시하고, 클릭하면 해당 태그로 필터링된다

**파싱 규칙**

제목 **끝에서부터 역방향으로** `#단어`가 연속되는 구간만 태그로 본다. 이렇게 하면 제목 중간의 `#`를 태그로 오인하지 않는다.

```js
// "C# 공부 #cs #복습" → title: "C# 공부",  tags: ["cs", "복습"]
// "홈택스 입력 #세금"  → title: "홈택스 입력", tags: ["세금"]
// "C# 공부"           → title: "C# 공부",    tags: []
// "#세금"             → title: "#세금",      tags: []   (앞에 공백이 없음)

function parseTags(raw) {
  let title = raw.trim();
  const tags = [];
  const TAIL_TAG = /\s#([^\s#]+)$/;
  let m;
  while ((m = title.match(TAIL_TAG))) {
    tags.unshift(m[1]);
    title = title.slice(0, m.index).trimEnd();
  }
  return { title, tags: normalizeTags(tags) };
}
```

`#세금` 하나만 입력하면 제목이 "#세금"인 항목이 만들어진다. 제목이 비는 상황을 만들지 않기 위한 의도된 동작이다.

**편집 시 태그 처리**

인라인 편집을 열 때 태그를 제목 문자열에 다시 합치지 **않는다**. 제목만 보여주고, 편집 중 새로 `#`를 입력하면 기존 태그에 **추가**된다. 태그를 지우려면 배지의 `×`를 누른다.

> 합쳐서 보여주면 "제목만 고치려다 태그가 통째로 날아가는" 사고가 난다. 파싱은 입력 시점의 편의 기능이지, 태그의 저장 형태가 아니다.

### F-08. 카테고리 분류

처음 열면 **업무 / 개인 / 공부** 셋이 주어지고, 이후로는 사용자가 만들고 지운다.

**수용 기준**
- [ ] 모든 상위 할 일은 반드시 하나의 카테고리를 가진다 (미분류 없음)
- [ ] 하위 할 일은 상위의 카테고리를 그대로 따르며, 독립적으로 바꿀 수 없다
- [ ] 카테고리 배지는 **상위 항목에만** 표시한다
- [ ] 색상 외에 **텍스트 라벨도 함께** 표시한다
- [ ] 내부 저장값은 id, 화면 표시는 이름. 기본 3종의 id는 `work` / `personal` / `study`
- [ ] 카테고리를 만들고 지우는 방법은 F-13에 있다

### F-09. 필터

**필터는 한 번에 하나만 활성화된다.** 상태는 다음 셋 중 하나다.

```js
filter = { type: "all" }
       | { type: "category", value: "work" }
       | { type: "tag",      value: "세금" }
```

**수용 기준**
- [ ] 상단 탭: `전체` / `업무` / `개인` / `공부`
- [ ] 그 아래 태그 바에 **현재 사용 중인 태그 목록**을 미완료 개수와 함께 노출한다
- [ ] 태그 필터가 켜져 있어도 **태그 바는 좁아지지 않는다.** 고른 태그만 남으면
      다른 태그로 건너뛸 수단이 사라지기 때문이다. 카테고리와 검색어는 그대로 태그 바를 좁힌다
- [ ] 카테고리 필터 중 태그를 클릭하면 카테고리 필터가 해제되고 태그 필터로 **전환**된다 (그 반대도 동일)
- [ ] 활성 필터를 다시 클릭하거나 `전체` 탭을 누르면 해제된다
- [ ] 카테고리 필터는 **상위 기준**으로 적용되고, 매칭된 상위는 하위와 함께 통째로 표시된다
- [ ] 태그 필터는 **항목 단위**로 매칭하되, 매칭된 하위의 상위를 **문맥 행**으로 함께 표시한다
- [ ] 문맥 행은 체크박스가 비활성이고 흐리게 표시되며, 삭제·편집 버튼이 노출되지 않는다
- [ ] 필터 상태는 새로고침 시 초기화된다 (`전체`로 복귀)
- [ ] 필터 중인 태그를 가진 항목이 0개가 되면 자동으로 `전체`로 복귀한다
- [ ] **저절로 풀린 것은 이유를 알린다** — `#세금 태그가 없어져 전체 목록으로 돌아왔습니다.`
      아무 말 없이 목록이 늘어나면 무엇이 잘못됐는지 알 길이 없다.
      되돌릴 것이 걸려 있으면 그 5초가 지난 뒤에 뜬다 (F-04)
- [ ] 필터 결과가 0건이면 빈 상태 문구를 보여준다

> **왜 필터를 하나만 허용하나**: 카테고리 축과 태그 축을 동시에 켜면 조합 상태가 곱으로 늘고, 빈 상태 문구·진행률 분모·자동 복귀 조건을 조합마다 정의해야 한다. 단일 필터로 두면 상태가 3종으로 끝나고, 이 규모의 앱에서 잃는 게 거의 없다. 다중 필터는 v2 후보다.

### F-10. 진행률 보기

**리프만 센다.** 상위 할 일은 하위가 있으면 분모에서 제외한다.

```
분모 = 현재 필터에 보이는 항목 중 하위가 없는 항목의 수
분자 = 그중 완료된 항목의 수
```

**수용 기준**
- [ ] 상단에 `완료 수 / 전체 수` 와 백분율을 표시한다
- [ ] 가로 프로그레스 바로 시각화한다
- [ ] **현재 필터 기준으로 계산한다** (`전체` / 카테고리 / 태그 모두 동일 규칙)
- [ ] 하위를 가진 상위 항목은 분모·분자 어디에도 포함되지 않는다 — 문맥 행도 정의상 리프가 아니므로 자동으로 제외된다
- [ ] 하위가 없는 상위 항목은 리프로 취급해 포함한다
- [ ] 우선순위와 태그는 진행률 계산에 **가중치를 주지 않는다** (모든 리프가 1개)
- [ ] 분모가 0이면 0%로 표시하고 바는 빈 상태로 둔다 (NaN 금지)
- [ ] 백분율은 소수점 없이 반올림한다
- [ ] 헤더 우측에 **남은 할 일 개수 배지**를 둔다. `전체 − 완료`이며 0이면 감춘다.
      진행률과 같은 기준(리프·현재 필터)으로 세야 나란히 놓았을 때 어긋나지 않는다

### F-11. 완료 체크와 전파

**수용 기준**
- [ ] **하향 전파**: 상위를 완료로 체크하면 하위가 전부 완료된다. 되돌리면 하위도 전부 미완료가 된다.
- [ ] **상향 전파**: 하위가 전부 완료되면 상위가 자동으로 완료된다.
- [ ] **상향 해제**: 완료 상태에서 하위 하나를 해제하면 상위도 자동으로 미완료가 된다.
- [ ] **부분 완료**: 하위 일부만 완료된 상위는 체크박스를 `indeterminate` 상태로 표시한다
- [ ] 하위가 없는 상위 항목은 일반 항목처럼 독립적으로 동작한다
- [ ] 완료 시 제목에 취소선이 그어지고 명도가 낮아진다
- [ ] 완료해도 목록에서 사라지지 않고 **제자리에 남는다**
- [ ] 전파로 상태가 바뀐 항목도 `completedAt`이 갱신된다

```js
checkbox.indeterminate = !item.completed && children.some(c => c.completed);
```

### F-12. 데이터 영속성

**수용 기준**
- [ ] 모든 변경 직후 `localStorage`에 저장한다
- [ ] 앱 로드 시 저장된 데이터를 복원한다
- [ ] 새로고침, 탭 종료 후 재접속, 브라우저 재시작 후에도 데이터가 유지된다
- [ ] 저장 실패 시 사용자에게 알린다 (§8)

### F-13. 카테고리 관리

카테고리 탭 오른쪽 톱니바퀴로 관리 패널을 연다.

**수용 기준**
- [ ] 톱니바퀴에 `aria-label="카테고리 관리"`, `aria-expanded`, `aria-controls`를 둔다
- [ ] 패널은 탭 바로 아래에 열리고, `Esc`로 닫히면 포커스가 톱니바퀴로 돌아온다
- [ ] 패널은 카테고리마다 색 점 · 이름 · 항목 수 · 삭제 버튼을 보여준다
- [ ] 이름을 입력해 추가한다. 추가 후 입력창은 비워지고 **포커스가 유지된다**
- [ ] 이름은 1~12자. 같은 이름은 거부하고 이유를 알린다 (색만으로는 구분되지 않기 때문)
- [ ] **카테고리는 64개까지 만든다** (`Store.MAX_CATEGORIES`). 상한에 닿으면 저장 실패가 아니라
      `카테고리는 64개까지 만들 수 있습니다.`라고 이유를 밝힌다
- [ ] 상한과 이름 중복은 **로드·가져오기 경로에서도 똑같이 막는다.** 상한 너머는 읽지 않고 버리고,
      앞에서 이미 쓴 이름과 겹치는 것은 건너뛴다. 비교는 12자로 자른 뒤의 이름으로 한다 —
      그래야 12자 너머에서만 다른 두 이름이 화면에서 같아 보이는 것까지 걸린다
- [ ] **이름을 눌러 그 자리에서 고친다.** 할 일 제목을 고칠 때와 같은 방식이다 —
      `Enter`로 넣고, `Esc`로 물리고, 다른 데를 누르면 넣는다
- [ ] `Esc`는 이름 편집만 물린다. 관리 패널까지 닫지 않는다
- [ ] 이름을 바꿔도 항목의 소속과 색조는 그대로다. 항목은 id로 카테고리를 가리키기 때문이다
- [ ] 바꾼 이름이 비었거나 다른 카테고리와 겹치면 **이유를 알리고 옛 이름을 지킨다**
- [ ] 새 카테고리의 색조는 **이미 쓰는 색들과 가장 멀리 떨어진 자리**를 자동으로 고른다
- [ ] 항목이 없는 카테고리는 확인만 받고 지운다
- [ ] 항목이 남아 있으면 **옮겨갈 카테고리를 반드시 고르게 한다**. 미분류가 없기 때문이다
- [ ] 상위를 옮기면 그 하위도 함께 따라간다
- [ ] **마지막 하나는 지울 수 없다.** 버튼을 비활성화하고 store에서도 거부한다
- [ ] 필터 중인 카테고리를 지우면 자동으로 `전체`로 복귀한다

> **왜 이름 변경을 그 자리에서 하나**: 이름을 고치는 일은 지우고 다시 만드는 것과 다르다.
> 지웠다 만들면 항목이 전부 다른 카테고리로 옮겨 갔다가 하나씩 돌아와야 하고, 색조도 새로 뽑힌다.
> 이름만 갈아 끼우면 소속도 색도 그대로 남는다.

> **왜 이름 중복을 막나**: 카테고리는 색과 이름 두 가지로 읽힌다. 색은 자동 배정이라 사용자가 고를 수 없으므로, 이름까지 같으면 배지만 보고는 어느 쪽인지 알 방법이 없다.

> **왜 개수에 상한을 두나**: 화면이 감당할 수를 한참 넘겨 잡은 값이지만, 상한이 아예 없으면 카테고리가 수십만 개인 파일 하나로 앱이 그 자리에서 멈춘다. 새 색조를 고르는 `pickHue`가 이미 쓰는 색들과의 거리를 `Math.min(...used)`로 재는데, 스프레드로 펼친 인자가 엔진의 개수 제한을 넘기면 `RangeError`가 난다. 상한은 `addCategory`뿐 아니라 로드·가져오기에도 함께 건다 — 만들 때만 막으면 다음에 앱을 열 때 카테고리가 예고 없이 사라지고 항목만 남는다.

> **왜 삭제할 때 옮길 곳을 강제하나**: F-08의 "미분류 없음"을 지키려면 항목은 언제나 어딘가에 속해야 한다. 삭제를 막아버리면 쓸 수 없는 카테고리가 목록에 남고, 항목까지 함께 지우면 되돌릴 수 없는 손실이 된다. 옮기는 쪽이 둘 다 피한다.

### F-14. 테마 전환

우측 상단 토글 스위치로 라이트/다크를 고른다.

**수용 기준**
- [ ] 고르기 전에는 **OS 설정을 따른다**. 고른 뒤에는 OS와 무관하게 그 선택을 지킨다
- [ ] 선택은 저장되고 새로고침·재접속 후에도 유지된다
- [ ] 고른 테마가 OS 설정과 다르더라도 **첫 페인트부터 고른 색으로 나온다.**
      반대 색으로 한 번 칠해졌다가 뒤집히지 않는다
- [ ] 아직 고르지 않았다면 OS 설정이 바뀔 때 화면도 따라 바뀐다
- [ ] 토글은 `role="switch"` + `aria-checked`를 쓴다
- [ ] 토글 안에 **해와 달을 함께** 둔다. 지금 켜진 쪽이 손잡이 위에 올라와 진하게 보이고,
      반대쪽은 트랙에 흐리게 남는다 — 무엇으로 바뀌는지 누르기 전에 알 수 있어야 한다
- [ ] 해·달은 장식이라 `aria-hidden`이다. 상태는 `aria-checked`가 전한다
- [ ] 팔레트는 값마다 `light-dark()`로 한 번만 적는다. 두 벌을 따로 적지 않는다

> **왜 두 벌을 적지 않나**: 라이트·다크 팔레트를 각각 나열하면 한쪽만 고치는 실수가 반복된다. `color-scheme` 하나를 바꿔 모든 `light-dark()`가 함께 뒤집히게 하면 어긋날 자리가 없다. 카테고리 배지처럼 색조가 동적인 값도 같은 방식으로 처리한다.

### F-15. 검색

입력창 아래 검색란에서 실시간으로 걸러낸다.

**수용 기준**
- [ ] 입력하는 즉시 목록이 좁혀진다 (별도 확인 동작 없음)
- [ ] **제목과 태그를 함께 본다.** 대소문자는 구분하지 않는다
- [ ] 검색어는 분류 축(전체/카테고리/태그)과 **함께** 걸린다. 서로를 해제하지 않는다
- [ ] 카테고리·태그 탭을 바꿔도 검색어는 유지된다
- [ ] 매칭된 하위의 상위는 **문맥 행**으로 함께 표시한다 (태그 필터와 같은 규칙)
- [ ] `Esc` 또는 `×` 버튼으로 검색어를 비운다
- [ ] 0건이면 `"{검색어}"에 해당하는 할 일이 없습니다.`

> **왜 검색만 다른 축과 겹치나**: F-09가 하나만 허용한 것은 카테고리와 태그, 즉 **같은 성격의 분류 축 둘**이다. 검색은 분류가 아니라 좁히기라서 어느 분류 위에도 얹힌다. "업무 중에서 세금 관련만"은 자연스러운 요구고, 이걸 막으면 검색이 반쪽이 된다.

> **주의**: 태그 필터의 자동 복귀(F-09)를 판정할 때는 **검색어를 뺀 채로** 물어야 한다. 검색 결과가 0건인 것과 그 태그를 가진 항목이 사라진 것은 다르다.

### F-16. 완료한 항목 일괄 삭제

**수용 기준**
- [ ] 완료한 항목이 하나라도 있을 때만 `완료한 항목 N개 삭제` 버튼이 보인다
- [ ] 누르면 **확인 다이얼로그**를 띄운다. 개수를 밝히고, 되돌릴 수 있다고 알린다
- [ ] 다이얼로그는 `<dialog>` + `showModal()`을 쓴다. `confirm()`을 쓰지 않는다
- [ ] `Esc`와 `취소`로 닫히고, 닫으면 아무것도 지우지 않는다
- [ ] 삭제 후 `실행 취소` 토스트가 뜨고, 되돌리면 완료 상태까지 그대로 복원된다
- [ ] 삭제 대상은 **현재 필터와 무관하다**. "모두"이므로 전체를 센다
- [ ] **되돌릴 것을 세운 뒤에 목록을 그린다.** F-04와 같은 순서다 — 뒤집으면 그리는
      도중에 나온 알림이 실행 취소 토스트에 곧바로 덮여 사라진다 (§13)

> **왜 `confirm()`이 아닌가**: 네이티브 대화상자는 스타일을 맞출 수 없고, 자동화 도구에서 페이지 전체를 멈춰 세운다. `<dialog>`는 포커스 가둠과 `Esc`를 기본으로 주면서 앱과 같은 모양을 유지한다.

**바깥 클릭으로 닫기 — 대화상자 공통 규칙**

- [ ] 세 대화상자(도움말 · 완료 삭제 · 가져오기) 모두 바깥을 누르면 닫힌다
- [ ] 닫기는 언제나 **취소**다. 바깥을 눌러 무언가가 실행되는 일은 없다
- [ ] **상자 안쪽 여백을 눌러도 닫히지 않는다.** 뒤 배경을 누르면 이벤트 대상이
      대화상자 자신이 되는데, 안쪽 여백도 대상이 같다. 좌표가 실제로 상자 밖인지 다시 본다
- [ ] **키보드로 안쪽 버튼을 누른 것을 바깥 클릭으로 오해하지 않는다.**
      그때 좌표는 (0, 0)으로 들어와 상자 밖으로 계산된다. 자식을 눌렀는지 먼저 거른다

> **왜 F-04와 달리 확인을 받나**: 한 건 삭제는 실행 취소로 충분하다. 일괄 삭제는 한 번에 수십 건이 사라지고 무엇이 지워졌는지 눈으로 세기 어려워, 실행 취소만으로는 되돌릴 판단조차 하기 힘들다.

### F-17. 키보드 단축키

**수용 기준**
- [ ] `Alt+N` — 새 할 일 입력창으로 포커스를 옮기고 내용을 전체 선택한다
- [ ] `Alt+1`~`Alt+9` — 카테고리 탭을 **자리 순서대로** 전환한다 (1번은 `전체`)
- [ ] 입력 중에도 동작하되, 글자가 끼어들지 않도록 기본 동작을 막는다
- [ ] 한글 조합 중(`isComposing`)에는 반응하지 않는다
- [ ] 각 대상에 `aria-keyshortcuts`와 `title`을 달고, 도움말(F-21)의 `단축키` 묶음에 적는다.
      입력창 힌트 줄에는 타이핑 규칙 둘만 남긴다 (§7 "입력창 도움말")

> **왜 `key`가 아니라 `code`인가**: macOS에서 `Alt+1`은 `key`가 `¡` 같은 특수문자로 바뀐다. `code`(`Digit1`)는 자판 배열과 무관하게 그대로다.

### F-21. 도움말

화면 오른쪽 위 `?` 버튼으로 연다.

**수용 기준**
- [ ] `<dialog>` + `showModal()`을 쓴다. `Esc` · `닫기` · **바깥 클릭**으로 닫힌다
- [ ] 닫으면 포커스가 `?` 버튼으로 돌아온다
- [ ] 열면 `닫기` 버튼에 포커스가 간다. 스크롤 영역이 먼저 잡히면 테두리가 본문 전체를 두른다
- [ ] 내용은 정적 마크업이다. 스크립트로 만들지 않는다
- [ ] 여덟 묶음: 빠른 입력 · 우선순위 · 카테고리 · 필터와 검색 · 정렬 · 뽀모도로 · 단축키 · 데이터
- [ ] 본문이 길면 대화상자 안에서만 스크롤한다 (`max-height` + `overflow-y`).
      스크롤 영역에 `tabindex="0"`을 둔다. 없으면 브라우저에 따라 포커스를 못 받아
      키보드로는 아래쪽 묶음까지 굴려 볼 방법이 사라진다
- [ ] 좁은 화면에서는 용어와 설명을 한 줄씩 쌓는다

### F-22. 뽀모도로 타이머

오른쪽 위 토마토 아이콘으로 열고 닫는다. 패널은 제목 줄과 진행률 게이지 사이에 나타난다.

**버튼 표기**
- [ ] 토마토는 **빨간색**이다. 팔레트 밖의 색을 하나 쓰는 유일한 자리다
- [ ] 아이콘 옆에 `뽀모도로 타이머`라고 적는다. 모양만으로는 무엇인지 단정할 수 없고,
      `뽀모도로`만으로는 기법 이름이라 무엇을 여는 버튼인지가 빠진다
- [ ] **돌아가는 중임은 글자 쪽이 알린다.** 아이콘은 늘 빨갛게 둔다 —
      토마토가 파래지거나 초록이 되면 그건 더 이상 토마토가 아니다
- [ ] 휴식 중에는 패널과 같은 초록으로 맞춘다
- [ ] 좁은 화면에서도 글자를 지우지 않는다. 대신 헤더 간격을 좁혀 자리를 만든다

> **왜 색 규칙의 예외인가**: §7은 색을 카테고리·우선순위·중립 배경까지로 묶었다. 토마토는 그 규칙보다 "무엇인지 바로 알아보는 것"이 앞선다고 판단해 예외로 뒀다. 예외는 여기 하나뿐이고, 그래서 `--tomato` 변수 하나로만 쓴다.

**단일 타이머 수용 기준**
- [ ] 시계 아이콘 옆에 남은 시간을 `MM:SS`로 보여준다
- [ ] 미리 정해둔 길이 세 가지(25 · 5 · 15분)를 한 번에 고른다. 고른 것은 표시가 남는다
- [ ] **지금 무엇으로 돌아갈지는 켜진 버튼 하나로 읽는다.** 사이클 · 프리셋 셋 · `설정`
      가운데 언제나 하나만 켜져 있다. 직접 입력한 길이일 때는 `설정`이 켜진다 —
      아무것도 켜져 있지 않으면 시작을 눌렀을 때 몇 분짜리가 도는지 알 방법이 없다
- [ ] 사이클로 넘어가면 직접 입력 칸을 비운다. 남겨두면 그 값으로 도는 줄 안다
- [ ] 직접 입력으로 1~180분을 정한다. `min`/`max`/`step`을 두어 브라우저가 먼저 걸러낸다
- [ ] 시작 · 일시정지 · 계속 · 초기화. 끝난 뒤에는 `다시 시작`으로 바로 한 판 더 돌린다
- [ ] 끝나면 `00:00`을 남긴다. 끝났다는 사실이 화면에 보여야 한다
- [ ] 돌아가는 동안 문서 제목에 남은 시간을 얹는다. 배경 탭에서도 보인다
- [ ] 패널을 닫아도 돌아간다. 그때는 버튼의 **글자와 바탕**이 돌아가는 중임을 알린다.
      토마토 아이콘은 늘 빨갛게 둔다 (위 "버튼 표기" 참조)
- [ ] `Esc`로 패널을 닫고 포커스는 아이콘으로 돌아온다
- [ ] 끝날 때 소리를 낸다. **소리 파일을 두지 않고** 그 자리에서 만든다 (외부 요청 0건)
- [ ] 남은 시간 표시는 `role="timer"` + `aria-live="off"`.
      1초마다 읽어주면 방해만 된다. 끝났다는 안내는 토스트가 맡는다
- [ ] **새로고침해도 돌아가던 자리에서 이어진다.** 돌고 있었으면 계속 돌고,
      멈춰 있었으면 멈춘 채로, 회차와 구간까지 그대로 돌아온다
- [ ] 돌아가던 타이머로 돌아왔으면 패널을 펴서 보여준다. 멈춰 있었으면 펴지 않는다
- [ ] 자리를 비운 사이에 구간이 끝났으면 **`00:00`에 세워둔다.** 지금 와서 소리를 내지 않는다 —
      흘려보낸 시간을 이제 와 되돌릴 수는 없다. 사이클이었다면 **다음 구간을 누를 자리는 세워둔다**
      (F-22a). 아무것도 세워두지 않으면 사이클을 이으려고 처음부터 다시 걸어야 한다
- [ ] 타이머를 한 번도 건드리지 않은 사람에게는 아무것도 남기지 않는다

> **왜 저장 형식에 넣지 않나**: 1초마다 저장하면 판 번호(`rev`)가 계속 올라가고, 그때마다 다른 탭이 전부 다시 읽는다 (F-20). 그 탭이 고치던 제목과 되돌릴 수 있던 5초가 타이머를 시작했다는 이유로 날아간다. 게다가 타이머는 탭마다 따로 도는 것이라 탭 사이에서 공유할 것이 아니고, 내보낸 파일에 끝나는 시각이 들어가면 남의 기기에서 이미 지난 시각이 된다.

> **그래서 어디에 두나**: **세션 저장소**의 `daily-todo:v1:run`에 따로 둔다. 새로고침을 넘기고, 탭마다 따로 놀고, 탭을 닫으면 사라진다 — 필요한 만큼과 정확히 같다. 판 번호를 건드리지 않으므로 다른 탭은 아무것도 눈치채지 못한다.

> **1초마다 쓰지는 않는다**: 남은 초는 끝나는 시각에서 다시 나오는 값이라 남길 이유가 없다. 그래서 "지금 상태"를 한 줄로 요약할 때 **돌아가는 동안에는 남은 초를 빼고** 만든다. 요약이 달라질 때만 쓰므로, 실제로 쓰는 때는 시작·멈춤·구간 전환·길이 변경뿐이다. 한 판에 열 번 남짓이다.

> **왜 1초씩 빼지 않나**: 끝나는 시각을 정해두고 남은 시간을 매번 다시 잰다. 배경 탭에서는 타이머가 1분에 한 번까지 느려지므로, 1초씩 빼면 돌아왔을 때 그만큼 어긋나 있다. 화면이 다시 보이는 순간에도 한 번 더 맞춘다.

**사이클 수용 기준 (F-22a)**
- [ ] `사이클` 버튼 한 번으로 1회차 집중부터 끝까지 이어서 돈다
- [ ] 네 회차를 돌고 **1회차로 되돌아온다**
- [ ] 1~3회차 뒤에는 짧은 휴식, **4회차 뒤에는 긴 휴식**이 온다
- [ ] 한 구간이 끝나면 **`00:00`에 멈춰 서서 기다린다.** 저절로 다음 구간으로 넘어가지 않는다
- [ ] 그 자리에 다음 구간을 잇는 버튼이 생긴다 — `휴식 시작` · `긴 휴식 시작` · `집중 시작`.
      **집중이 끝날 때와 휴식이 끝날 때 모두** 그렇다
- [ ] 기다리는 동안에는 `다시 시작`을 치운다. 나란히 두면 방금 끝난 구간을 한 번 더 도는 버튼과
      사이클을 잇는 버튼이 같은 줄에 서서, 어느 쪽이 이어가는 것인지 읽히지 않는다
- [ ] 문서 제목에는 남은 시간 대신 **누를 것**을 적는다. `00:00`만 적으면 탭 목록에서
      멈춘 것인지 끝난 것인지 갈라지지 않는다
- [ ] 기다리는 상태는 **새로고침을 넘긴다.** 세션 기록에 다음 구간까지 함께 남긴다 (F-22)
- [ ] 기다리는 동안 회차 길이를 고쳐도 **대기가 지워지지 않는다.** 새 길이는 버튼을 누를 때 읽는다
- [ ] 지금 어느 구간인지 이름으로 보여준다 — `집중 2/4` · `휴식 2/4` · `긴 휴식`
- [ ] 휴식 구간은 색을 달리해 한눈에 갈라 보이게 한다
- [ ] 프리셋이나 직접 입력을 고르면 사이클에서 빠져 단일 타이머가 된다
- [ ] `초기화`는 사이클 중이면 1회차 집중으로 되돌린다
- [ ] 구간이 끝날 때 나는 소리는 **다음이 집중이면 올라가고 휴식이면 내려간다**.
      화면을 보지 않아도 무엇이 시작됐는지 알 수 있어야 한다

**회차 설정 수용 기준 (F-22b)**
- [ ] 톱니바퀴로 설정을 열고 닫는다. 회차마다 집중·휴식 시간을 분 단위로 정한다
- [ ] 그 톱니바퀴는 **카테고리 관리와 같은 그림**을 쓴다. 색을 늘리지 않기로 한 만큼
      모양으로 알아보게 만드는데, 같은 앱 안에서 설정이 두 가지 그림으로 나오면
      그 길이 막힌다 (v3.2에서 해 모양을 톱니바퀴로 고침)
- [ ] 회차 수는 넷으로 고정한다. 값은 1~180분
- [ ] 설정은 **저장된다**. 돌아가는 상태와 달리 자주 바뀌지 않기 때문이다
- [ ] 값 하나를 고칠 때 **다른 칸을 다시 그리지 않는다.**
      전부 새로 그리면 방금 옮겨간 칸이 교체되며 포커스와 입력하던 내용이 사라진다
- [ ] 범위 밖 값은 **직전 값으로 되돌린다.** 공장 기본값이 아니다 —
      한 칸이 잘못됐다고 손대지도 않은 값이 바뀌면 안 된다
- [ ] `기본값` 버튼으로 공장 설정(25/5 · 25/5 · 25/5 · 25/25)으로 되돌린다

**펼친 시계 수용 기준 (F-22c)**
- [ ] 화살표로 원형 시계를 열고 닫는다. 간단한 줄만 보는 상태가 기본이다
- [ ] 그 화살표 옆에 **무엇을 하는 버튼인지 글자로 적는다** — `펼치기` ↔ `접기`.
      열리면 화살표도 뒤집는다. 설정(톱니)은 아이콘만 쓴다
- [ ] **시간이 흐른 만큼 원이 채워진다.** 남은 시간이 아니라 지나간 시간을 그린다
- [ ] 가운데에 남은 시간과 구간 이름을 함께 둔다
- [ ] 사이클 회차 넷을 점으로 보여주고, 지난 회차와 지금 회차를 갈라 표시한다
- [ ] `Esc`는 안쪽 화면(설정 → 시계 → 패널) 순서로 하나씩 닫는다

**위젯 수용 기준 (F-22d)**

패널을 닫아도 남은 시간이 보여야 한다. 자리를 두 군데 둔다 — 페이지 안과 페이지 밖이다.

*미니 타이머 (페이지 안, 모든 브라우저)*
- [ ] 한 판이 걸려 있는데 패널이 닫혀 있으면 **화면 오른쪽 아래**에 작은 타이머가 남는다.
      "걸려 있다"는 돌아가는 중 · 일시정지 중 · 다음 구간을 기다리는 중 셋을 말한다.
      건드린 적 없거나 초기화한 직후에는 뜨지 않는다
- [ ] **반투명하다.** 다만 바탕만 반투명으로 깔고 글자는 불투명한 색을 그대로 쓴다 —
      `opacity`로 통째로 흐리면 대비가 그만큼 떨어지고, 얼마나 떨어졌는지는 계산해보기 전에는 보이지 않는다
- [ ] 그 **진하기를 사용자가 정한다.** 회차 설정(톱니) 안에 손잡이를 두고 0~100에서 고른다.
      기본은 82다 — 뒤에 오는 것이 `--bg`든 `--surface`든 섞인 결과가 원래 `--surface`에서
      거의 벗어나지 않는 값이다
- [ ] 고른 값은 **저장한다.** 테마와 같은 성격의 화면 설정이라 저장 형식 안에 함께 담는다 (`miniOpacity`)
- [ ] 아래로는 55%까지만 내려간다. 그보다 옅으면 미니 타이머가 할 일 카드 위에 겹쳤을 때
      바탕이 사라져 아래 글자가 비치고, 흐린 글자가 3.07:1까지 내려간다. 손잡이의 `min`은
      `Store.MINI_OPACITY_MIN`에서 가져온다 — 따로 적으면 저장은 막는데 손잡이만 더 내려간다
- [ ] 범위 밖 값은 **가장 가까운 자리로 옮긴다.** 기본값으로 되돌리면 옅게 보려던 뜻이
      통째로 지워진다 — 하한을 새로 둔 날 23으로 맞춰둔 값이 82로 튀어 올랐다
- [ ] **끄는 동안에는 화면만 따라오고, 손을 뗄 때 한 번 저장한다.** 매 순간 저장하면 판 번호가
      한 번 끌 때마다 수십 번 올라가고, 그때마다 다른 탭이 고치던 것과 되돌릴 수 있던 5초가 날아간다 (F-20)
- [ ] 손잡이의 `step`은 1이다. 5로 두면 저장된 82가 80으로 스냅되어 숫자와 손잡이가 어긋나고,
      끌어서 82로 돌아갈 길이 사라진다
- [ ] 어느 값에서도 **글자는 그대로 읽힌다.** 진하기는 바탕·테두리·그림자에만 걸린다.
      0에서도 글자가 얹히는 것은 `--bg`나 `--surface`라 대비가 흔들리지 않는다
- [ ] 누르면 패널이 다시 열린다. 다음 구간을 기다리는 중이라면 **거기서 바로 이을 수 있다** —
      패널을 열어야만 누를 수 있으면 미니 타이머를 둔 이유가 없어진다
- [ ] `×`로 거둔다. 패널을 다시 열면 거둔 뜻도 함께 거둔다 —
      한 번 눌렀다고 이 탭이 사는 내내 되살릴 길이 없으면 안 된다
- [ ] **토스트가 이 자리로 올라오지 않는다.** 겹치면 방금 생긴 `휴식 시작`이 그 사실을 알리는
      알림에 가려, 알리려던 그 동작을 누를 수 없게 된다
- [ ] 패널이 열려 있거나 별도 창으로 빼놓았으면 뜨지 않는다. 같은 시계를 두 군데 그리지 않는다

*별도 창 (Document Picture-in-Picture, Chrome · Edge)*
- [ ] `창으로 빼기`로 항상 위에 뜨는 작은 창을 연다. **브라우저를 최소화해도 남는다**
- [ ] 그 창에 **원형 시계**를 둔다. 숫자만으로는 얼마나 왔는지가 읽히지 않는다.
      가운데에 남은 시간과 구간 이름, 그리고 **누를 것까지 함께** 넣는다
- [ ] 누를 것은 **글자가 아니라 모양**이다 — 돌리기(▶) · 멈추기(‖) · 다음 구간으로(▶|).
      멈춘 것을 다시 미는 것과 사이클을 잇는 것은 다른 일이라 같은 모양을 쓰지 않는다.
      읽히는 이름은 `aria-label`·`title`로 남긴다. 모양만 남기면 화면을 못 보는 사람에게는
      아무것도 남지 않고, 음성으로 조작하는 사람은 부를 말을 잃는다
- [ ] 그 버튼을 **원 안에** 둔다. 밖에 한 줄을 두면 그 줄만큼 창이 커져야 하고,
      항상 위에 뜨는 창에서는 그 높이가 그대로 가리는 넓이가 된다
- [ ] **그림이 칸을 꽉 채우게 그린다.** 작게 그리면 버튼 지름의 3분의 1도 차지하지 못해,
      테두리 동그라미만 보이고 가운데는 비어 보인다. 선으로 긋는 모양(‖)은 채우는
      모양들과 나란히 서므로 그만큼 굵게 긋는다
- [ ] 버튼 바탕을 **옅게 깔아 존재를 만든다.** 테두리만 두면 그 안의 그림이 창 바탕과
      같은 어둠 위에 얇게 얹혀 멀리서는 빈 동그라미로 보인다
- [ ] 다만 **테두리는 옅히지 않는다.** 경계에 요구되는 3:1은 글자 기준(4.5:1)과 별개로
      따로 재야 한다 — 55%로 두었더니 2.46까지 내려가 있었다
- [ ] 기다리는 중에는 구간 이름 자리에 **누를 것**을 적는다. 모양만으로는 `계속`과
      `휴식 시작`이 갈라지지 않는데, 그 자리는 이미 있으므로 높이가 늘지 않는다.
      원이 가득 찬 것이 방금 것이 끝났다는 말을 대신한다
- [ ] 그 시계는 펼친 시계(F-22c)와 **같은 클래스를 쓴다.** 색도 굵기도 1초 전환도 한 곳에서 온다.
      마크업을 베끼면 두 벌이 되어 한쪽만 고치게 된다
- [ ] **요청한 창 크기가 그대로 나오지 않는다.** 적는 높이는 바깥 크기라 브라우저가 자기
      머리띠(되돌아가기 단추가 있는 줄)를 그 안에서 빼가고, 최소 폭을 따로 두며, 마지막 크기를
      기억하고, 사용자가 직접 끌어 바꾼다. 132를 달라고 했더니 안쪽이 76px로 온 적이 있다.
      그래서 시계 크기를 숫자로 못박지 않고 남는 자리에서 얻는다 — 못박으면 그때 창 밖으로 잘린다
- [ ] **원형 시계로 볼지 숫자만 볼지는 사용자가 고른다.** 창 크기로 정하지 않는다 —
      작은 창에서도 원을 보고 싶을 수 있고, 큰 창에서도 숫자만 보고 싶을 수 있다.
      고른 것은 저장한다 (`pipDial`)
- [ ] 그 버튼은 **모서리에 세워 흐름에서 빼낸다.** 줄로 두면 그 줄만큼 창이 커진다.
      흐리게 두되 hover로만 드러내지는 않는다 — 이런 버튼이 있다는 것을 알 방법이
      창 안에 달리 없다
- [ ] **가로는 늘 남고 세로가 비싸다.** 브라우저가 정하는 최소 폭을 내릴 방법이 없어서,
      세로를 줄이면 가로에 빈 자리가 생긴다. 좁아질수록 세로로 쌓던 것을 가로로 눕혀 그 자리를 쓴다
- [ ] 창이 낮아지면 구간 이름을 접고 **버튼을 원 밖 오른쪽으로 뺀다.** 세로가 모자란
      것이지 가로가 모자란 것이 아니므로, 원은 그만큼 더 클 수 있다
- [ ] 숫자만 보기는 **한 줄로 눕힌다** — 남은 시간 · 구간 이름 · 버튼이 가로로 선다.
      세로로 쌓으면 그만큼 창이 높아야 하는데, 가로는 어차피 남는다
- [ ] 글자 크기는 남는 높이에서 얻되 **아래로도 막는다.** 계산만 따르면 안쪽 76px에서 2px가 된다
- [ ] 여백과 버튼도 함께 줄인다. 고정된 자리가 창보다 커지면 숫자가 들어갈 높이가 남지 않는다
- [ ] 스크롤 막대를 내지 않는다. 손바닥만 한 창에서는 그것이 남은 자리를 가져간다

*가리는 넓이 (F-22e)*

항상 위에 뜨는 창이라 **가리는 넓이가 곧 비용이다.** 줄일 수 있는 자리를 전부 줄인다.

- [ ] 처음 열 때만 크기를 달라고 하고 **그 뒤로는 손대지 않는다.** 브라우저가 마지막
      크기를 기억하므로, 우리가 다시 정해주면 사용자가 맞춰둔 크기를 되돌려버린다.
      크기는 창 가장자리를 끄는 사람의 몫이다
- [ ] 누를 것을 원 안에 넣어 **버튼 줄 하나를 통째로 없앤다** (위 참조)
- [ ] 글자를 모양으로 바꿔 그 버튼이 차지하던 폭도 줄인다
- [ ] 좁아지면 세로로 쌓던 것을 가로로 눕혀, 내리지 못하는 가로 최소치를 자리로 쓴다

> **가로 최소치는 내리지 못한다**: 240보다 작게 달라고 해도 240이 온다. 브라우저가 정하는 값이고 `requestWindow()`에 이를 넘길 방법이 없다. 그래서 세로만이라도 낮게 잡고, 가로로 남는 자리는 비워둔다.
- [ ] 버튼은 패널과 같은 글자를 쓴다
- [ ] 같은 `styles.css`를 물려주고 테마도 함께 뒤집는다. 저 창만 반대 색으로 남지 않게 한다
- [ ] 시계는 **그 창 자신의 타이머로** 돈다. 본 창이 배경에 있으면 `setInterval`이 1분에
      한 번까지 느려져, 본 창 것만 믿으면 저 창의 시계가 멈춰 있다가 껑충 뛴다
- [ ] 지원하지 않는 브라우저에서는 **버튼 자체를 내지 않는다.** 자리만 남겨두면 눌러도
      아무 일이 없는 버튼이 되고, 왜 안 되는지 알 길이 없다

> **왜 두 가지인가**: 브라우저 창을 최소화해도 남으려면 별도 OS 창밖에 길이 없는데, 그 창은 Chrome·Edge에만 있고 **반투명하게 만들 수 없다**(창 바탕은 브라우저가 불투명하게 깐다). 반대로 페이지 안 위젯은 어디서나 되고 반투명도 되지만 브라우저를 최소화하면 함께 사라진다. 서로가 못 하는 것을 메우므로 둘 다 둔다.

> **창 위치는 정하지 않는다**: Document PiP에는 위치를 지정하는 API가 없다. 브라우저가 정하고, 대개 화면 오른쪽 아래에 연다.

> **별도 창은 반투명하게 만들 수 없다**: `requestWindow()`가 받는 것은 크기뿐이고, 웹에는 OS 창의 투명도를 건드리는 API가 없다. 창 바탕은 브라우저가 불투명하게 깐다. 그래서 진하기 조절은 **페이지 안 미니 타이머에만** 붙인다 — 거기서는 그냥 요소라 얼마든지 옅게 만들 수 있다.

> **왜 4단계가 아니라 세 가지인가**: 25 · 5 · 15는 뽀모도로의 집중·짧은 휴식·긴 휴식이다. 나머지는 직접 입력이 받는다.

> **왜 눌러야 이어지나** (v3.2에서 뒤집음): 처음에는 자동으로 이어붙였다. 근거는 "사이클은 한 번 걸어두고 일에 집중하는 것이고, 구간마다 누르게 하면 그게 집중을 끊는다"였다. 쓰다 보니 그 자동 진행이 **경계 자체를 지워버렸다** — 화면을 보고 있지 않은 사이에 집중이 끝나고 휴식이 시작되면, 돌아왔을 때 눈에 보이는 것은 그냥 흐르는 숫자뿐이다. 지금이 집중인지 휴식인지, 애초에 한 구간이 지나가기는 한 것인지 화면에 남는 단서가 없다. 소리는 그 순간 자리에 없었으면 들리지 않고, 배경 탭에서는 자동재생 정책에 막히기도 한다.
>
> **멈춰 있는 시계는 놓칠 수가 없다.** `00:00`에 서서 `휴식 시작`을 내밀고 있으면, 몇 분 뒤에 돌아오든 몇 시간 뒤에 돌아오든 무엇이 끝났고 무엇을 눌러야 하는지가 한눈에 읽힌다. 잃는 것은 구간 사이의 클릭 한 번이고, 얻는 것은 "지금 무슨 구간이 도는 중인지 모르겠다"가 일어나지 않는다는 보장이다.
>
> **같은 이유가 휴식 → 집중에도 그대로 걸린다.** 경계를 놓치는 것은 어느 쪽 구간이 끝나든 똑같이 일어나므로, 한쪽만 수동으로 두면 규칙이 둘이 되고 어느 쪽이 어느 쪽인지 또 외워야 한다.

> **왜 채우는 방향인가**: 뽀모도로는 "얼마나 남았나"보다 "얼마나 했나"를 보는 기법이다. 비어가는 원은 조급함을 주고, 채워지는 원은 쌓인 것을 보여준다.

> **왜 설정만 저장하나**: 회차 길이는 한 번 정하면 오래 쓰는 값이라 저장할 값어치가 있다. 반대로 돌아가는 상태는 1초마다 바뀌어서, 저장하면 판 번호가 계속 올라가고 다른 탭이 그때마다 다시 읽는다 (F-20).

> **무엇을 넣나**: "써 보면 아는 것"은 넣지 않는다. 넣는 건 **써 봐도 모르는 것**이다 — 타이핑 접두어, 단축키, `0이 가장 높다`, 진행률이 하위만 세는 이유, 끌기가 직접 순서에서만 되는 이유, 데이터가 이 브라우저에만 있다는 사실. 화면에 단서가 없는 규칙만 모은다.

**문체 — 사용자에게 말하듯 쓴다**

도움말은 §7 마이크로카피 규칙("버튼은 실행 결과를 그대로 말한다")의 연장이지만, 짧게 자르는 것보다 **한 문장을 끝까지 맺는 것**이 먼저다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| 넣습니다 · 답니다 · 붙입니다 | **추가합니다** |
| 이깁니다 · 잡힙니다 · 걸립니다 | **관계 없이 적용됩니다** · **선택할 수 있습니다** |
| 한 항목에 5개까지. | **항목당 5개까지 추가할 수 있습니다.** |
| 옆에서 고른 값 | **우측에 선택된 우선순위** |
| 추려 보기 · 빠르게 적기 | **필터와 검색** · **빠른 입력** |

- **명사로 끊지 않는다.** "5개까지."처럼 서술어 없이 멈추면 메모처럼 읽힌다
- **은유와 압축을 쓰지 않는다.** "이깁니다", "손잡이가 잡힙니다"는 짧지만 한 번 더 해석해야 한다
- **위치는 화면에 보이는 대로 부른다.** "옆에서"가 아니라 "우측에"
- **설명이 길어지면 지운다.** `+` 버튼 설명은 "하위 할 일을 추가합니다." 한 줄이면 된다.
  깊이 제한 같은 건 부딪혀 봐야 알게 되는 것이지, 미리 읽을 내용이 아니다

### F-18. 내보내기 / 가져오기

**수용 기준**
- [ ] `내보내기` — 저장 형식 그대로를 JSON 파일로 내려받는다. 파일명은 `my-what-todo-YYYY-MM-DD.json`
- [ ] 날짜는 **로컬 기준**이다. `toISOString()`은 UTC라 한국 오전에는 하루 전으로 찍힌다
- [ ] `가져오기` — 파일을 고르면 **덮어쓰기 전에** 확인 다이얼로그를 띄운다
- [ ] 다이얼로그는 `취소` / `그냥 가져오기` / **`백업 후 가져오기`** 셋을 준다
- [ ] `백업 후 가져오기`는 현재 데이터를 먼저 내려받은 뒤 교체한다
- [ ] 가져온 데이터는 **로드와 같은 검증 파이프라인**을 탄다 (§8)
- [ ] JSON이 아니거나 `todos` 배열이 없으면 거부하고 이유를 알린다. 기존 데이터는 그대로 둔다
- [ ] 가져온 뒤 필터·검색어를 초기화한다. 예전 필터가 가리키던 것이 없을 수 있다
- [ ] 외부로 아무것도 보내지 않는다. `Blob` + `URL.createObjectURL`로 브라우저가 저장한다

> **왜 백업을 권하나**: 가져오기는 이 앱에서 유일하게 **실행 취소가 없는** 동작이다. 전부를 한 번에 갈아치우므로 토스트 한 줄로 되돌릴 수 있는 규모가 아니다. 되돌릴 수 없으면 되돌릴 재료를 먼저 쥐여주는 게 맞다.

**JSON 파일 연결 (1~2단계)**

- [ ] `파일 연결`은 `showSaveFilePicker`로 `my-what-todo.json`을 제안하고 JSON 필터를 준다
- [ ] 파일을 고르면 현재 `Store.exportData()`를 들여쓰기 JSON으로 즉시 쓴다
- [ ] 연결 성공 뒤 성공한 Store 변경의 시점별 스냅샷을 한 쓰기 큐에서 순서대로 저장한다
- [ ] picker 취소는 조용히 끝내며 기존 LocalStorage 상태와 기존 파일 연결을 건드리지 않는다
- [ ] 쓰기 실패는 LocalStorage 정본을 되돌리지 않고 간결하게 알린다
- [ ] 파일 핸들은 현재 페이지 세션에서만 유지하며 IndexedDB 등에 남기지 않는다
- [ ] API 미지원 환경에서는 연결을 시도하지 않고 내보내기/가져오기 사용을 안내한다
- [ ] footer에 `파일 연결 안 됨` / `파일 연결 중…` / `{파일명} 연결됨 · 마지막 저장 HH:MM:SS` 상태를 항상 표시한다
- [ ] 파일명은 실제 handle 이름을 쓰되 비거나 문자열이 아니면 `my-what-todo.json`을 쓴다
- [ ] 마지막 저장 시각은 initial write와 자동 저장의 `write` + `close`가 모두 성공한 뒤에만 갱신한다
- [ ] 취소하거나 후보 쓰기에 실패한 재연결은 기존 파일명과 마지막 성공 저장 시각으로 복귀한다
- [ ] 연결 중에는 연결 버튼을 비활성화하고, 성공 뒤 문구를 `파일 다시 연결`로 바꾼다

**JSON 외부 변경 감지·충돌 해결 (5A)**

- [ ] `getFile().text()`가 있는 handle은 성공한 own write의 exact JSON text를 handle별 baseline으로 메모리에만 둔다
- [ ] 자동 save와 retry는 같은 serial job 안에서 `createWritable()` 바로 전에 현재 exact bytes를 baseline과 비교하고, 다르면 write 없이 `conflict:true`로 전환한다
- [ ] 초기 connect의 첫 쓰기는 사용자가 고른 파일을 앱 상태로 덮는 명시 동작이므로 비교하지 않으며, 같은 drain의 후속 쓰기부터 비교한다
- [ ] conflict 동안 LocalStorage·UI·Markdown은 유지하고 JSON 자동 저장과 retry만 막는다. 최신 직렬화 성공본은 force 후보로 갱신하며 직렬화 실패는 과거 후보를 무효화한다
- [ ] `checkExternal()`은 focus와 hidden→visible에서 read-only 비교만 하며 read 오류를 false conflict로 만들지 않는다
- [ ] footer는 `{파일명} 연결됨 · 외부 변경 감지 · 자동 저장 중지`와 `충돌 해결`을 표시하고 일반 retry는 숨긴다
- [ ] 해결 선택은 `앱 내용으로 덮어쓰기` / `외부 파일 유지` / `취소`다. force는 실행 시 `Store.exportData()`를 다시 직렬화하고 진행 중 save를 최신 version까지 drain한다
- [ ] `외부 파일 유지`는 외부 bytes를 전혀 쓰지 않고 JSON 연결만 해제한다. LocalStorage·Markdown·앱 상태는 바꾸지 않는다
- [ ] `getFile`이 없는 구형/test handle은 기존 저장을 유지하되 감지 불가를 conflict로 오인하지 않는다
- [ ] 외부 원문·handle·오류 객체는 public state, toast, DOM에 공개하지 않는다

파일 API에는 원자적 compare-and-swap이 없다. 따라서 `getFile().text()` 확인과 실제 write 사이의
read→write TOCTOU 경쟁은 남는다. 비교를 `createWritable()` 직전 같은 serial job에서 수행해
창을 최소화하지만, 이 보호는 **best-effort(최선 노력)**이며 외부 프로세스가 그 짧은 사이에
다시 쓰는 경우까지 원자적으로 막지는 못한다.

**Obsidian Markdown 자동 생성 (4단계)**

- [ ] `Markdown 연결`은 `showSaveFilePicker`로 `my-what-todo.md`와 `.md` 필터를 제안한다
- [ ] 사용자가 Obsidian vault 안에서 고른 파일에 현재 `Store.exportData()`를 즉시 쓰고,
      연결 뒤의 성공한 Store 변경을 한 쓰기 큐에서 순서대로 덮어쓴다
- [ ] 파일 핸들은 현재 페이지 세션에서만 유지한다. 새로고침하거나 페이지를 닫으면 다시 골라야 한다
- [ ] 출력 bytes는 다음 형식을 고정한다: `title`·`generated_by`·`format_version` YAML
      frontmatter, `# My What Todo`, 제한 편집 가져오기 안내, 카테고리 순서의 `##` 절,
      `- [ ] (P0) 제목 #태그 <!-- my-what-todo:id=... -->` 항목과 2칸 들여쓴 하위 항목,
      그리고 파일 끝 newline 하나
- [ ] 형제는 `order` → `createdAt` → `id` 순으로 정렬하고, 같은 snapshot은 언제나 같은
      bytes를 만든다. 제목·태그·카테고리는 HTML/Markdown으로 실행되지 않게 escape한다
- [ ] 4단계 당시 연결 runtime은 **앱이 정본인 단방향 보기**였고, 6A의 별도 순수 parser를
      연결이나 Store에 호출하는 app/Sync 통합은 제외했다. 현재 6B2의 제한적 충돌 가져오기는
      아래 6A/6B2 계약에 따라 별도로 통합한다
- [ ] render/write 실패는 LocalStorage 정본과 JSON mirror를 막지 않으며, 실패한 새 연결은
      오래된 후보를 활성화하지 않는다. 기존 연결이 있으면 그 핸들과 마지막 성공 상태를 보존한다

**Markdown 외부 변경 감지·충돌 해결 (5B)**

- [ ] `getFile().text()`가 있는 Markdown handle은 성공한 own write의 exact bytes를 handle별
      baseline으로 메모리에만 둔다. handle과 baseline은 현재 페이지 세션을 벗어나 저장하지 않는다
- [ ] 자동 save는 같은 serial job 안에서 `createWritable()` 직전에 현재 bytes를 baseline과
      비교하고 다르면 write 없이 conflict로 전환한다. 초기 connect 첫 쓰기는 명시적 덮어쓰기라
      비교하지 않으며, 같은 connect drain의 후속 쓰기부터 비교한다
- [ ] conflict 동안 LocalStorage·UI·JSON mirror는 유지하고 Markdown 자동 저장만 멈춘다.
      해결 선택은 `앱 내용으로 덮어쓰기` / `외부 파일 유지` / `취소`다
- [ ] force는 실행 시 최신 `Store.exportData()`를 다시 render하고 진행 중 새 save까지 drain한다.
      `외부 파일 유지`는 Markdown bytes를 쓰지 않고 Markdown 연결만 해제한다
- [ ] `checkExternal()`은 focus와 hidden→visible에서 read-only 비교한다. read 오류는 false
      conflict로 만들지 않고 자동 저장 보류 상태로 알리며, 정상 재검사/저장으로 복구한다
- [ ] 취소하거나 initial write에 실패한 재연결은 기존 active conflict를 보존한다. 성공한
      재연결만 conflict를 해제하고 성공 bytes로 새 baseline을 만든다
- [ ] `getFile`이 없는 구형/test handle은 저장을 유지하되 감지 불가를 conflict로 오인하지 않는다
- [ ] 외부 원문·handle·오류 객체는 public state, toast, DOM에 공개하지 않는다

파일 API에는 원자적 compare-and-swap이 없으므로 Markdown도 확인 read→write 사이의 TOCTOU
경쟁이 남는다. 비교를 같은 serial job의 쓰기 직전에 두어 창을 줄이지만 **best-effort(최선 노력)**
보호이며, 외부 프로세스가 그 짧은 사이에 다시 쓰는 경우까지 원자적으로 막지는 못한다.

**Canonical Markdown 기존 항목 편집 parser (6A)**

`MarkdownImport.parse(text, currentSnapshot)`는 임의 Markdown reader가 아니다. 현재 snapshot을
`MarkdownExport.render`한 정본 문서에서 모든 기존 todo ID가 정확히 한 번 남은 제한 편집만
받고, complete 새 plain snapshot과 항목별 변경 요약을 결정론적으로 만든다.

| 변경 | 6A | 규칙 |
|---|---:|---|
| checkbox / P0~P3 / 제목 / 태그 | 지원 | canonical escape 역변환과 제한을 통과해야 함 |
| 형제 순서 / root 카테고리 이동 | 지원 | 기존 카테고리 절의 순서와 이름은 고정 |
| 기존 ID의 root↔child 재배치 | 지원 | root 0칸, child 2칸, 최대 2단계 |
| todo 추가·삭제 | 거부 | unknown·duplicate·missing ID 모두 typed error |
| 카테고리 추가·삭제·이름/순서 변경 | 거부 | 현재 heading exact-once/order |
| theme/sort/pomodoro/version/category metadata | 거부 | 결과에는 현재 값을 exact clone으로 보존 |
| 기타 절·임의 section/문장/Markdown | 거부 | canonical grammar 밖의 입력은 fail-closed |

파서는 current plain graph와 스키마를 accessor 실행 없이 strict 검증하고, 입력 크기를 현재
canonical bytes와 todo 수에 비례해 제한한다. ID와 escape는 canonical roundtrip을 요구하며,
마지막에는 반드시 `MarkdownExport.render(data) === text`를 확인한다. 오류는 raw 행·값·외부 ID를
담지 않는 고정 한국어 `MarkdownImportError`다. 6A script는 export와 sync 사이에 로드된다.
6B2에서는 충돌 해결의 `Markdown 편집 가져오기`가 원문을 DOM에 노출하지 않고 변경 종류별
개수만 미리 보여준다. 체크박스·P0~P3·제목·태그·형제 순서·기존 카테고리 이동·최대 2단계
재배치만 허용하며, 항목 추가/삭제·카테고리 CRUD·기타 절·설정·임의 Markdown은 거부한다.
미리보기에는 token/current/baseline/summary만 보관하고 raw text와 parsed data는 버린다.

확인 시 현재 `Store.exportData()`가 baseline과 exact JSON으로 같은지 검사하고 core가 재검증한
bytes를 저장된 current에 다시 parse한 뒤 동기 `Store.importData`를 호출한다. Store/LocalStorage를
먼저 적용하며 JSON mirror와 Markdown 정본 저장은 독립적이다. Markdown write/render 실패 뒤에도
적용된 LocalStorage는 롤백하지 않고 충돌을 유지한다. 연결과 conflict token은 현재 페이지
세션에만 유지된다. 파일 API에는 원자적 compare-and-swap이 없으므로 read→verify→write 사이
TOCTOU는 남는 **best-effort(최선 노력)** 보호다.

### F-23. 문의하기

목록 아래 `내보내기` · `가져오기` 옆에 둔다. 가끔 쓰는 동작이라 같은 줄이 맞다.

**수용 기준**
- [ ] 누르면 대화상자가 열리고 제목과 내용을 적는다. `<dialog>` + `showModal()`을 쓴다
- [ ] `메일 앱 열기`를 누르면 그 내용이 채워진 채로 **메일 앱이 열린다**
- [ ] 내용이 비어 있으면 열지 않고 그 사실을 알린다. 제목이 비어 있으면 `My What Todo 문의`를 쓴다
- [ ] 그 알림은 **상자 안에 적는다.** 토스트로 알리면 모달의 뒤 배경 아래에 깔리고,
      지운 항목의 5초가 걸려 있으면 알림이 통째로 미뤄져 눌러도 아무 일이 없는 것처럼 보인다.
      `role="alert"` 규칙(자리를 먼저 열고 글은 다음 태스크에)은 카테고리 오류와 같다
- [ ] **이 상자는 바깥을 눌러도 닫히지 않는다.** 다른 상자는 고르지 않고 닫으면 취소라
      잃는 것이 없지만, 여기에는 적던 글이 들어 있다
- [ ] 같은 이유로 닫을 때 칸을 비우지 않는다. `Esc`로 닫았다가 다시 여는 길이 있고,
      그때마다 비우면 쓰던 글이 소리 없이 사라진다. 메일 앱에 넘긴 뒤에만 비운다
- [ ] 받는 주소를 화면에도 적는다. 메일 앱이 없는 환경에서 옮겨 적을 자리가 필요하다
- [ ] 주소를 **소스에 통째로 적지 않는다.** 조각으로 두고 누를 때 잇는다
- [ ] 할 일 내용은 함께 담지 않는다. 문의하려고 누른 것이지 데이터를 보내려고 누른 것이 아니다

> **왜 메일 앱에 넘기나**: 이 앱은 `connect-src 'none'`이라 **밖으로 보낼 길이 자체가 없다** (§6). 서버로 부치려면 그 규칙을 열어야 하는데, 그 규칙 하나가 "데이터가 나가지 않는다"를 의도가 아니라 보장으로 만들고 있다. 문의 한 줄 때문에 그것을 무를 값어치는 없다. `mailto:`는 브라우저가 바깥 프로그램에 넘기는 것이라 페이지가 무언가를 부치는 것이 아니고, CSP도 건드리지 않는다.

> **왜 주소를 조각으로 두나**: 저장소가 공개라 소스에 `mailto:...@...`가 그대로 있으면 수집기가 훑어간다. 소스를 읽는 사람은 여전히 알 수 있으므로 가리는 것이 목적은 아니다 — HTML만 긁고 지나가는 쪽에 이어 붙은 주소를 남기지 않는 것이 목적이다.

> **왜 대화상자인가**: 버튼 하나로 빈 메일 창을 여는 길도 있다. 만들 것은 적지만 메일 앱이 설정되지 않은 기기에서는 **아무 일도 일어나지 않고, 그 사실을 알릴 자리도 없다.** 앱 안에서 적게 하면 적어도 그 화면에 받는 주소가 남아 있다.

> **글자 수는 주소 길이에서 나온다**: 메일 앱과 운영체제에 따라 `mailto:` 주소가 **2000자쯤에서 뒤가 잘린다.** 잘린 것은 작성 창에 그대로 보이지만, 이미 앱을 떠난 뒤라 되돌릴 방법이 없다. 그래서 애초에 넘지 못하게 막는다.
>
> 한글 한 글자는 UTF-8 3바이트라 인코딩하면 **9자**가 된다 (ASCII는 1~3자, 줄바꿈은 3자라 여기에 못 미친다). 고정부는 `mailto:`(7) + 주소(22) + `?subject=`(9) + `&body=`(6) = 44자다. 따라서 `44 + 9 × (제목 + 내용) < 2000`이면 어떤 글을 적어도 안전하고, 제목과 내용을 합쳐 **217자**까지가 그 조건이다. **제목 40자 · 내용 160자**로 나눠 최악이 1844자에 머물게 했다.
>
> - [ ] 숫자는 `maxlength` **한 곳에만** 적는다. 화면 문구는 그 값을 읽어 만든다 — 문장에 숫자를 따로 박아두면 한쪽만 고쳤을 때 화면이 거짓말을 한다
> - [ ] 몇 자까지인지 **미리 말한다.** 말하지 않으면 `maxlength`가 조용히 입력을 멈춰 키보드가 고장 난 것처럼 보인다
> - [ ] 그 문구는 "더 긴 이야기는 열린 메일 앱에서 이어 쓰면 된다"까지 말한다. 이 칸은 천장이 아니라 넘겨주는 자리다
> - [ ] 이 관계는 회귀 테스트가 지킨다 — `index.html`의 두 `maxlength`를 읽어 최악의 주소 길이를 계산한다. 나중에 칸을 늘리면 거기서 걸린다
>
> 이모지처럼 4바이트인 글자는 12자로 부푼다. 전부 이모지로 채우면 2444자가 되지만, 문의 한 통을 이모지로만 적는 경우를 위해 칸을 더 줄이지는 않는다.

### F-19. 정렬 옵션

필터 줄 오른쪽 선택 상자로 고른다. **어느 모드에서도 형제 그룹 안에서만 정렬한다.**

| 모드 | 기준 |
|---|---|
| **우선순위순** (기본) | F-06 그대로. 우선순위 1차, `order` 2차 |
| 직접 순서 | `order`만. 끌어서 옮길 수 있는 유일한 모드 |
| 생성일순 | `createdAt` |
| 카테고리순 | 카테고리 목록의 순서 |
| 완료상태순 | 미완료 먼저 |

**수용 기준**
- [ ] 고른 모드는 저장되고 새로고침 후에도 유지된다
- [ ] 트리 구조는 어느 모드에서도 깨지지 않는다
- [ ] **직접 순서 모드에서만** 끌기 손잡이가 잡힌다
- [ ] 손잡이 자리는 모든 모드에서 유지한다. 모드를 바꿀 때 목록 왼쪽이 흔들리면 안 된다
- [ ] 끌어 놓기는 **같은 부모의 형제 사이에서만** 된다. 부모가 바뀌는 이동은 거부한다
- [ ] 놓일 자리를 선으로 미리 알린다
- [ ] 마우스 없이 `Alt+↑` / `Alt+↓`로도 옮긴다. 옮긴 뒤 포커스는 그 항목에 남는다

> **왜 드래그를 직접 순서 모드로 제한하나**: 다른 모드에서는 정렬 기준이 자리를 다시 정한다. 우선순위순에서 낮음 항목을 맨 위로 끌어 놓으면 놓는 순간 제자리로 튕긴다. 사용자가 한 일이 취소되는 것처럼 보이므로, 손으로 정한 순서가 그대로 남는 모드에서만 잡히게 했다.

> **왜 부모를 바꾸지 못하게 하나**: 부모가 바뀌면 캐스케이드 삭제 범위, 진행률 분모(리프 판정), 완료 전파 대상이 한꺼번에 달라진다. 순서 바꾸기는 `order` 하나만 건드리므로 이 셋 중 어느 것도 흔들리지 않는다.

### F-20. 여러 탭에서 열었을 때

같은 앱을 두 탭에서 열어두면, 한쪽이 통째로 저장하면서 다른 쪽의 작업을 덮어쓸 수 있다. **두 겹으로 막는다.**

**1겹 — 따라가기.** 다른 탭이 저장하면 `storage` 이벤트가 온다. 받는 즉시 다시 읽어 화면을 맞춘다.

**2겹 — 쓰기 직전 확인.** 저장본에 판 번호(`rev`)를 둔다. 쓰기 직전에 저장소를 다시 읽어, 우리가 마지막으로 본 `rev`와 다르면 **쓰지 않고 물러난다.**

**수용 기준**
- [ ] 다른 탭의 저장을 받으면 곧바로 다시 읽어 화면을 맞춘다
- [ ] 그때 편집·하위 입력·되돌리기 토스트는 접는다. 없어진 항목을 가리킬 수 있다
- [ ] 낡은 상태에서 쓰기를 시도하면 **거부하고 되돌린 뒤** 최신을 읽어온다
- [ ] 거부됐을 때 사용자가 입력한 내용은 그대로 둔다. 다시 누르면 되게 한다
- [ ] `rev`는 내보내기에 넣지 않는다. 가져온 파일에는 없는 값이다
- [ ] **판 번호를 읽을 수 없는 저장본은 원문을 비교한다.** 판 번호를 넣기 전에 쓰인
      v1·v2 저장본을 가진 사용자가 영영 저장하지 못하면 안 되기 때문이다 (§13)
- [ ] 연달아 들어오는 외부 변경은 **한 프레임에 한 번**으로 합친다
- [ ] 보이지 않는 탭에서는 **읽어만 두고 그리기를 미룬다.** 읽기까지 거르면 판 번호가
      낡아 다음 저장의 경합 검사가 죽는다. 미뤄둔 것은 탭이 다시 보일 때 화면에 옮긴다
- [ ] 메모리 폴백(저장 불가 환경)에서는 다른 탭이 없으므로 늘 통과한다

> **왜 이벤트만으로는 부족한가**: `storage` 이벤트는 비동기다. A가 쓰고 B에게 이벤트가 닿기 전에 B가 먼저 쓰면 A의 저장이 사라진다. 이벤트는 "평소에 맞춰두는" 장치고, 실제로 손실을 막는 건 쓰기 직전의 `rev` 확인이다.

> **왜 병합하지 않나**: 두 탭의 변경을 합치려면 항목 단위 타임스탬프와 충돌 해소 규칙이 필요하다. 1인용 단일 기기 앱에서 그 복잡도를 지불할 이유가 없다. 거부하고 최신을 보여준 뒤 다시 하게 하는 편이 예측 가능하다.
>
> **현재 구현 한계**: `rev` 확인은 대부분의 낡은 쓰기를 거부하지만, LocalStorage에는 원자적 compare-and-swap이 없다. 두 탭이 같은 `rev`를 읽고 실제 저장까지 정확히 겹치면 둘 다 성공으로 판단하고 마지막 쓰기가 앞선 변경을 덮을 수 있다. 이 창을 완전히 닫으려면 변경 API를 비동기로 바꾸고 Web Locks 또는 IndexedDB 트랜잭션으로 저장 구간 전체를 묶어야 한다.

## 5. 데이터 모델

### 항목 스키마

트리를 중첩 객체로 저장하지 않고 **평평한 배열 + `parentId`**로 저장한다.

```js
{
  id:          "018f2a...",   // string, 고유 ID
  parentId:    null,          // null이면 상위 할 일, 아니면 상위 항목의 id
  title:       "홈택스 입력",   // string, 1~100자 (태그·우선순위 접두어 제거 후)
  category:    "work",         // string, 카테고리 id (하위는 상위 값 복사)
  priority:    1,              // 0~3. 0이 가장 높다. 기본 1
  tags:        ["세금"],        // string[], 0~5개
  completed:   false,          // boolean
  createdAt:   1754179200000,  // number, Date.now()
  completedAt: null,           // number | null
  order:       0               // number, 같은 parentId 안에서의 추가 순서
}
```

`priority`는 숫자이고 그 값이 곧 순위다. 정렬 가중치 표가 따로 없어 단계를 늘려도 비교자를 고칠 필요가 없다. v2까지 쓰던 `"high"`/`"normal"`/`"low"`는 로드 시 `0`/`1`/`2`로 옮긴다.

`order`는 정렬의 **2차 기준**으로만 쓰인다. 화면 순서는 `priority` → `order` 조합으로 매번 계산한다.

### 카테고리 스키마

```js
{
  id:   "work",   // string, 고유 ID. 기본 3종만 읽기 쉬운 고정값을 쓴다
  name: "업무",    // string, 1~12자. 목록 안에서 유일해야 한다
  hue:  221       // number, 0~359. 채도·명도는 CSS가 정하고 색조만 여기서 온다
}
```

색을 `#2563eb` 같은 완성된 값이 아니라 색조 하나로 저장하는 이유: 라이트·다크 두 벌을 각각 저장하면 어긋나기 시작한다. 색조만 데이터로 두고 채도·명도는 테마마다 한 곳에서 정하면 카테고리가 몇 개로 늘어나도 톤이 흐트러지지 않는다.

**store가 함께 내주는 상수**

UI가 같은 숫자를 따로 적어두면 한쪽만 고쳤을 때 화면과 저장이 어긋난다. 한도와 목록은 store에서 가져다 쓴다.

```js
Store.PRIORITIES          // [0, 1, 2, 3]
Store.MAX_TITLE           // 100
Store.MAX_CATEGORY_NAME   // 12
Store.MAX_CATEGORIES      // 64 — UI가 "더 만들 수 없다"를 저장 실패와 다르게 알리려면 필요하다
Store.SORTS               // F-19의 다섯 모드
Store.POMO_ROUNDS         // 4
Store.POMO_MIN_MINUTES    // 1
Store.POMO_MAX_MINUTES    // 180
Store.MINI_OPACITY_MIN    // 55 — 손잡이의 min을 여기서 가져온다. 따로 적으면
                          //   저장은 막는데 손잡이만 더 내려가는 칸이 생긴다
```

**색인**: `find` / `childrenOf` / `hasChildren`는 매번 배열을 훑지 않고 `Map` 두 개(`byId`, `parentId → 자식들`)를 쓴다. 없으면 질의가 O(n²)이 되어 1000개에서 눈에 띈다. 구조가 바뀌는 자리마다 색인을 버리고 다음 질의에서 다시 만든다.


변경 API는 저장에 실패하면 **변경 전체를 되돌리고 `null`을 준다.** 호출부는 `null`을 "저장하지 못했다"로 읽는다 (§8 참조).

`update`는 값이 잘못된 경우에도 `null`을 준다. 그중 하나가 **하위 항목의 `category` patch**다 — 하위는 상위를 상속하므로(F-08) 상위를 통해서만 바뀐다. UI는 하위에 배지를 그리지 않지만, 거절은 store가 다시 한 번 한다.

  할 일이 통째로 고아가 된다. 화면에 보이는 이름과 저장소 키는 별개다
- **값**: 아래 객체를 `JSON.stringify()` 한 문자열
- 돌아가는 뽀모도로만 예외로 **세션 저장소**의 `daily-todo:v1:run`에 따로 둔다.
  이유는 F-22에 적었다. 내보낸 파일에는 들어가지 않는다

```js
{
  version: 6,
  rev:        7,                   // 판 번호. 쓸 때마다 1씩 오른다 (F-20)
  theme:      "dark",              // "light" | "dark" | null (null이면 OS를 따름)
  sort:       "priority",          // 정렬 모드 (F-19)
  pomodoro:   [ /* 회차별 { focus, rest } 넷 (F-22) */ ],
  miniOpacity: 82,                 // 미니 타이머 바탕의 진하기 55~100 (F-22d)
  pipDial:     true,               // 빼놓은 창을 원형 시계로 보는가 (F-22d)
  categories: [ /* 카테고리 배열 */ ],
  todos:      [ /* 항목 배열 (평평한 구조) */ ]
}
```

테마도 이 안에 넣는다. 키를 하나만 쓴다는 규칙을 지키면서 저장 실패 롤백과 메모리 폴백을 그대로 물려받는다.

**v1 → v2 이관**: `categories`가 없는 저장본은 기본 3종을 채워 넣고 시작한다. 기본 3종의 id가 v1의 카테고리 값과 같으므로 항목은 그대로 이어진다.

**v3 → v4 이관**: `pomodoro`가 없으면 기본 사이클(25/5 · 25/5 · 25/5 · 25/25)을 채운다. 덧붙이는 값이라 옮길 것이 없다.

**v4 → v5 이관**: `miniOpacity`가 없으면 82를 채운다. 이것도 덧붙이는 값이라 옮길 것이 없다.

**v5 → v6 이관**: `pipDial`이 없으면 `true`를 채운다. 마찬가지로 옮길 것이 없다.

> **루트에 키를 더할 때는 세 곳을 함께 본다**: `store.js`의 `adopt`·`persist`·`exportData`·`commit`·`importData`·`reset`이 하나라도 빠지면 그 값만 저장되지 않거나 되돌려지지 않는다. 그리고 **`markdown-import.js`의 `ROOT_KEYS`가 루트 키를 정확히 일치로 검사한다** — 거기에 더하지 않으면 Markdown 충돌 가져오기가 통째로 `INVALID_CURRENT`로 거부된다. 새 값의 범위 검사도 같은 자리에 둔다. 통과한 snapshot이 그대로 복제되어 Store로 돌아가므로, 여기가 또 하나의 문이다.

**v2 → v3 이관**: `priority` 문자열을 숫자로 옮긴다 — `high`→`0`, `normal`→`1`, `low`→`2`. 알 수 없는 값은 `1`이다. 세 단계가 네 단계의 앞자리로 그대로 들어가므로 순서가 뒤집히지 않는다.

이관 결과를 로드 시점에 되쓰지는 않는다 — 다음 변경이 일어날 때 함께 저장된다.

## 6. 기술 요구사항

### 스택
- HTML + CSS + 순수 JavaScript (ES2020+)
- 프레임워크, 빌드 도구, npm 패키지 **없음**
- 저장소: `localStorage`

### 파일 구조

```
daily-todo/
├── index.html
├── styles.css
├── theme.js    # 첫 페인트 전에 고른 테마를 칠한다. Store.peekTheme() 하나만 부른다.
├── parse.js    # 제목 문자열 → { title, priority, tags }. 순수 함수만.
├── store.js    # 데이터 계층: 로드/저장/CRUD/전파/정렬/집계. DOM을 모른다.
└── app.js      # UI 계층: 렌더링 + 이벤트. store와 parse만 호출한다.
```

일반 `<script>` 태그로 로드하되 순서는 `store.js` → `theme.js`(여기까지 `<head>`) → `parse.js` → `file-sync.js` → `markdown-export.js` → `markdown-import.js` → `markdown-sync.js` → `app.js`(여기부터 본문 끝)다. 이 순서는 그냥 목록이 아니라 계약이다 — `markdown-sync.js`는 `MarkdownExport`와 `MarkdownImport`가 이미 서 있어야 돌고, 회귀 테스트가 그것을 검사한다. **앞의 둘만 `<head>`에 두고 나머지는 본문 끝에 둔다** — 고른 테마를 첫 페인트 전에 알아야 하기 때문이다 (F-14, §13). `theme.js`는 `Store.peekTheme()` 하나만 부른다.

**인라인 `<script>`를 두지 않는다.** CSP의 `script-src 'self'`를 `'unsafe-inline'` 없이 걸려면 인라인 스크립트가 없어야 한다. 해시로 허용할 수도 있지만, 그 스크립트를 고칠 때마다 해시를 다시 계산해야 하고 잊으면 조용히 막혀 깜빡임이 되살아난다 (§13).

### 콘텐츠 보안 정책 (CSP)

`index.html`의 `<meta http-equiv="Content-Security-Policy">`로 건다. GitHub Pages 같은 정적 호스팅은 응답 헤더를 정할 수 없어 `<meta>`가 유일한 수단이다.

```
default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'none';
img-src data:; font-src 'none'; media-src 'none'; object-src 'none';
base-uri 'none'; form-action 'none'
```

- **`connect-src 'none'`이 핵심이다.** `fetch`·XHR·`sendBeacon`·WebSocket을 전부 막는다. 나중에 누가 주입 구멍을 내더라도 데이터가 밖으로 나갈 길이 없다.
- `img-src data:`는 빈 아이콘(`<link rel="icon" href="data:,">`) 하나 때문이다. 그것을 두지 않으면 브라우저가 `/favicon.ico`를 찾아가 위반이 새로고침마다 콘솔에 쌓인다. `data:`는 네트워크를 타지 않아 유출 경로가 되지 않는다.
- `frame-ancestors`는 `<meta>`에서 동작하지 않아 뺐다. 헤더로만 걸린다.
- 스타일은 CSSOM(`el.style.setProperty`)으로 건드린다. CSP는 CSSOM을 막지 않으므로 `style-src`에 `'unsafe-inline'`이 필요 없다.

> **CSP가 지금 막는 구멍이 있나**: 없다. `innerHTML`도 `eval`도 동적 스크립트도 없어서 주입할 자리가 없다. 이건 **나중을 위한 장치**다. 누군가 규칙을 잊고 주입 경로를 만들어도 데이터가 나가지 못하게 한다. 대신 규칙 하나가 늘었다 — 인라인 스크립트와 `style=` 속성을 쓸 수 없다.

> **`type="module"`을 쓰지 않는 이유**: 모듈 스크립트는 **언제나 지연 실행**이다. `<head>`에 둬도 문서를 다 읽은 뒤에 돌기 때문에, 첫 페인트 전에 테마를 정해야 하는 `store.js`가 그 시점을 놓친다 (F-14, §13). 일반 스크립트 태그는 만난 자리에서 바로 돈다.
>
> 예전에는 `file://`에서 CORS에 막히는 것이 이유였다. 지금은 `file://`을 지원 대상에서 뺐지만, 위의 이유가 남아 규칙은 그대로다.

**`parse.js`를 따로 두는 이유**: 입력 파싱은 순수 함수라 콘솔에서 바로 검증할 수 있다. 우선순위·태그 규칙은 엣지 케이스가 가장 많은 부분인데, store나 UI에 섞여 있으면 확인하기 번거롭다. 분리해두면 M6·M7을 파싱 → 저장 → 표시 순으로 하나씩 확인하며 붙일 수 있다.

**완료 전파와 정렬은 store 안에서 끝낸다.** UI는 `Store.getRoots(filter)`가 돌려준 순서대로 그리기만 한다.

### 렌더링 전략

상태가 바뀌면 목록 전체를 다시 그린다. 항목 20개 규모에서는 diff 알고리즘이 불필요하다.

- 깊이가 2단계로 고정이므로 **재귀 없이 2중 루프**로 렌더링한다
- 이벤트는 목록 컨테이너 하나에 **이벤트 위임**으로 붙인다
- 각 DOM 노드에 `data-id`를 심고, `closest('[data-id]')`로 대상을 찾는다
- 액션은 `data-action` 속성으로 구분한다. 지금 쓰는 값은 열넷이다

  | 붙는 곳 | 값 |
  |---|---|
  | 할 일 행 | `toggle` · `edit` · `delete` · `add-child` · `pick-priority` · `remove-tag` · `change-category` · `drag` |
  | 탭·태그 바 | `filter-category` · `filter-tag` |
  | 카테고리 패널 | `rename-category` · `remove-category` · `confirm-remove-category` · `cancel-remove-category` |

  대화상자의 버튼만 `data-action`이 아니라 `data-choice`를 쓴다 (`close` / `cancel` / `confirm` / `plain` / `backup`) — 목록 위임과 섞이지 않게 이름을 따로 둔다
- 인라인 편집 중이거나 카테고리를 고르는 중이면 재렌더를 통째로 건너뛴다 (포커스 유실 방지).
  하위 입력창은 다시 그리되 **치던 내용을 밖에 받아두었다가 되돌려 넣는다** — 입력창이
  매 렌더마다 새로 만들어지므로, 받아두지 않으면 다른 항목을 체크하는 순간 내용이 사라진다

### 브라우저 지원
앱의 LocalStorage와 기존 내보내기/가져오기는 최신 Chrome, Edge, Safari, Firefox를
지원한다. 파일 연결은 File System Access API의 `showSaveFilePicker`를 제공하는 브라우저로
제한한다. 미지원 브라우저는 LocalStorage를 정본으로 계속 사용한다.

타이머를 별도 창으로 빼는 것(F-22d)은 Document Picture-in-Picture를 제공하는 브라우저로
제한한다 — 지금은 Chrome과 Edge다. 미지원 브라우저에서는 그 버튼을 내지 않고, 페이지 안
미니 타이머만 쓴다.

### 우선순위 표현 — 숫자를 그대로 보여준다

네 단계를 색이나 굵기만으로 구분시키면 읽을 수 없다. 사용자가 0~3으로 고르는 값이므로 **그 숫자가 곧 표시다.**

| 단계 | 표현 |
|---|---|
| 0 | 3px 세로 바(accent) + 숫자를 accent 색으로 + 제목 굵게 |
| 1 | 숫자만 (흐린 색) |
| 2 | 숫자 + 제목 명도를 낮춤 |
| 3 | 숫자를 더 흐리게 + 제목 명도를 낮춤 |

취소선은 어느 단계에도 쓰지 않는다 — 완료와 헷갈린다.

한눈에 걸려야 하는 건 `0` 하나뿐이라 세로 accent 바는 0에만 세운다. 나머지는 숫자가 조용히 알려주면 된다.

마커 영역은 모든 단계에서 **같은 자리를 차지한다**. 눌러서 고르는 자리라 히트 영역이 필요하고, 자리가 들쭉날쭉하면 목록 왼쪽 정렬이 흔들린다. 숫자는 그 칸의 가운데에 둔다 — 한쪽에만 패딩을 주면 `text-align: center`가 패딩 안쪽의 가운데를 잡아 밀린다.

### 태그 표현
- 제목 오른쪽에 작은 배지, 카테고리 배지보다 **약한 대비**로 (카테고리가 1차 축)
- 태그에는 색을 쓰지 않는다 — 색은 카테고리 전용이다
- 배지에 마우스를 올리면 `×`가 나타나 개별 삭제
- 3개를 넘으면 `+2` 로 접고, 항목에 포커스하면 전부 펼친다

### 계층 표현
- 하위 항목은 왼쪽으로 들여쓰고, 상위-하위를 잇는 1px 세로 연결선을 둔다.
  **선은 상위 체크박스의 왼쪽 테두리에 세우고, 하위 내용은 그 선 오른쪽에서 시작한다.**
  들여쓰기 값을 따로 정하지 않고 선 위치에서 유도한다 — 두 숫자를 나눠 적으면
  한쪽만 고쳤을 때 선이 하위 위로 올라탄다
- 하위 항목의 폰트 크기는 상위와 동일, **굵기만 낮춘다**

### 헤더 — 두 줄로 나눈다

한 줄에 다 넣으면 제목 옆이 버튼으로 빽빽해져 무엇이 이름표이고 무엇이 조작부인지 흐려진다.

나누는 기준은 **무엇에 대한 것인가**다.

**첫 줄 — 앱 자체**: 제목(왼쪽), 테마 토글과 도움말(오른쪽 끝).
테마와 도움말은 할 일이 하나도 없어도 뜻이 통하는, 앱 전체에 걸린 것이다.

**둘째 줄 — 지금 하는 일**: 남은 할 일 배지와 뽀모도로를 **오른쪽 끝에 붙인다.**
둘 다 목록의 상태에 매여 있다.

- 각 줄의 오른쪽 묶음 자체를 정렬한다. 안에 있는 개별 요소에 `margin-left: auto`를 주면,
  그 요소가 사라질 때(남은 할 일이 0이면 배지가 숨는다) 나머지가 왼쪽으로 딸려 온다
- 이름이 붙은 것을 앞에, 아이콘만인 것을 뒤에 둔다 (배지 → 뽀모도로, 토글 → 도움말)
- 두 줄의 오른쪽 끝을 맞춘다
- 좁은 화면에서는 묶음 간격만 줄인다. 제목이 두 줄로 갈라지면 안 된다

### 상태별 화면

| 상태 | 표시 |
|---|---|
| 할 일이 하나도 없음 | "아직 할 일이 없습니다. 위에 입력해서 시작하세요." |
| 검색 결과 0건 | "\"세금\"에 해당하는 할 일이 없습니다." — **검색 중이면 이 문구가 우선한다.** 0건의 이유가 검색어이기 때문이다 |
| 카테고리 필터 결과 0건 | "업무 카테고리에 할 일이 없습니다." |
| 태그 필터 결과 0건 | "#세금 태그가 붙은 할 일이 없습니다." |
| 태그가 하나도 없음 | 태그 바 자체를 숨긴다 (빈 줄을 남기지 않는다) |
| 전부 완료 | "11개 모두 완료했습니다." |
| 완료한 항목 없음 | `완료한 항목 삭제` 버튼을 숨긴다 |
| 남은 할 일 0 | 남은 할 일 배지를 숨긴다 |
| 저장 불가 환경 | 상단 배너: "이 브라우저에서는 데이터가 저장되지 않습니다. 탭을 닫으면 목록이 사라집니다." |

### 입력창 도움말
접두어 규칙은 발견되지 않으면 없는 기능이다. 입력창 `placeholder` 아래에 한 줄로 상시 노출한다.

> `!`로 시작하면 우선순위 0, 끝에 `#태그`

**여기에는 타이핑 규칙 둘만 남긴다.** 화면을 보고는 알 수 없는 건 이 둘뿐이다. 단축키를 비롯한 나머지는 도움말(F-21)로 옮긴다 — 힌트 줄이 길어지면 아무도 읽지 않는다.

### 마이크로카피 규칙
- 버튼은 실행 결과를 그대로 말한다 — `추가`, `삭제`, `실행 취소`
- 에러는 사과하지 않고, 무엇이 잘못됐고 어떻게 고치는지 말한다
- 빈 화면은 안내가 아니라 행동 유도다

### 스타일 방향
- 카테고리 색 + 우선순위 accent 1종 + 중립 배경. 그 외에 색을 늘리지 않는다
- 카테고리 색은 개수가 정해져 있지 않다. **색조만 카테고리마다 받고 채도·명도는 테마별로 한 번만 정한다.** 그래야 개수가 늘어도 톤이 흐트러지지 않는다
- **배지의 밝기는 `oklch()`로 못박는다.** `hsl`은 명도를 똑같이 줘도 색조마다 휘도가 크게
  달라, 파랑은 대비 5.97이 나오는데 초록·노랑은 2.3까지 떨어졌다. `OKLCh`의 `L`은 색조와
  무관하게 균일해 한 값으로 전 색조가 함께 통과한다. 색조는 `oklch(from hsl(...) L c h)`로
  **`hsl`에서 그대로 물려받는다** — 두 좌표계의 각도는 같은 숫자라도 다른 색이라,
  저장된 `hue`를 `oklch()`에 바로 넣으면 업무(221)가 청록이 되고 공부(262)가 파랑이 되어
  두 카테고리가 서로 붙는다. 데이터에는 여전히 `hue` 하나만 남는다
- `prefers-color-scheme` 으로 다크 모드 자동 대응
- 모바일 폭(360px)까지 대응. 좁은 화면에서는 간격이 줄고 들여쓰기도 함께 줄어든다
  (유도되므로 따로 정하지 않는다). 태그는 1개만 표시하고 나머지는 접는다

## 8. 엣지 케이스와 예외 처리

### 파싱

| 상황 | 처리 |
|---|---|
| `#` 뒤가 비어 있음 (`"할 일 #"`) | 태그로 보지 않는다. 제목에 그대로 남긴다 |
| 태그 6개 이상 | 앞에서부터 5개만 저장, 나머지는 버린다 (경고 없음) |
| 제목 중간의 `#` (`"C# 공부"`) | 태그 아님. 끝에서 역방향 연속 구간만 파싱 |
| 파싱 후 제목이 빔 | 등록 거부, 입력창 내용과 포커스 유지 |
| 제목 맨 앞 `!` 여러 개 | 하나만 소비, 나머지는 제목에 남는다 |
| 태그 대소문자·공백 차이 | 정규화 후 중복 제거 (`#Tax`, `#tax ` → `tax` 하나) |

### 계층·상태

| 상황 | 처리 |
|---|---|
| **고아 항목** (`parentId`가 가리키는 부모가 없음) | 로드 시 `parentId`를 `null`로 바꿔 상위로 승격 |
| **3단계 이상 데이터** | 로드 시 손자 이상은 상위로 승격해 2단계로 평탄화 |
| **순환 참조** (A→B→A) | 로드 검증 시 감지해 해당 항목들을 상위로 승격 |
| **문맥 행에 대한 조작 시도** | 체크박스·버튼이 비활성이므로 발생하지 않는다. 이벤트 위임 핸들러에서도 한 번 더 막는다 |
| **필터 중인 태그의 마지막 항목 삭제** | 자동으로 `전체` 필터로 복귀 |
| **필터 중인 카테고리 삭제** | 자동으로 `전체` 필터로 복귀 |
| **전파 도중 저장 실패** | 전파 전 상태 전체를 롤백 (부분 적용 금지) |
| **`priority`가 0~3 밖이거나 알 수 없는 값** | 로드 시 `1`로 교정. 옛 문자열은 숫자로 옮긴다 |
| **`tags`가 배열이 아님** | 로드 시 빈 배열로 교정 |

### 카테고리

| 상황 | 처리 |
|---|---|
| **항목의 `category`가 없는 카테고리를 가리킴** | 항목을 버리지 않고 첫 번째 카테고리로 옮긴다. 카테고리는 지워질 수 있으므로 이 값의 불일치는 손상이 아니다 |
| **`categories`가 없는 저장본 (v1)** | 기본 3종을 채우고 시작한다. id가 같아 항목은 그대로 이어진다 |
| **`categories`를 하나도 못 살림** | 기본 3종으로 되돌린다. 미분류 상태를 만들지 않는다 |
| **`hue`가 없거나 숫자가 아님** | 0으로 교정 |
| **이름이 12자 초과** | 로드 시 잘라내고, 입력 시에는 거부하고 이유를 알린다 |
| **같은 이름으로 추가 시도** | 거부한다. 색은 자동 배정이라 이름까지 같으면 구분할 방법이 없다 |
| **저장본·가져온 파일에 같은 이름이 둘** | 앞의 하나만 살리고 뒤는 건너뛴다. 자른 뒤의 이름으로 비교한다 |
| **카테고리가 64개를 넘는 저장본·파일** | 앞에서 64개까지만 읽고 나머지는 버린다. 그 카테고리를 가리키던 항목은 첫 번째로 옮겨간다 |
| **64개가 찬 상태에서 추가 시도** | 거부하되 저장 실패와 다르게 알린다 — `카테고리는 64개까지 만들 수 있습니다.` |
| **하위 항목의 `category`만 바꾸려는 시도** | 거부한다. 하위는 상위를 상속하므로 상위를 통해서만 바뀐다 (F-03) |
| **마지막 카테고리 삭제 시도** | 거부한다. 버튼도 비활성이고 store도 `null`을 준다 |
| **항목이 남은 카테고리 삭제** | 옮겨갈 카테고리 없이는 거부한다. UI가 먼저 물어본다 |
| **카테고리 변경 중 저장 실패** | 항목과 카테고리를 함께 롤백 (부분 적용 금지) |
| **테마 변경 중 저장 실패** | 테마도 함께 롤백. 화면은 되돌아간 값으로 다시 칠한다 |

### 검색·테마·단축키

| 상황 | 처리 |
|---|---|
| **검색 중에 태그 필터의 항목이 0건** | 자동 복귀를 판정할 때 검색어를 뺀다. 검색 결과 0건으로 태그 필터가 풀리면 안 된다 |
| **검색어가 공백뿐** | 앞뒤를 다듬은 뒤 비었으면 검색하지 않는 것으로 본다 |
| **검색 중 카테고리·태그 전환** | 검색어는 그대로 유지된다 |
| **저장된 `theme`이 알 수 없는 값** | `null`로 보고 OS 설정을 따른다 |
| **이미 열린 다이얼로그에 다시 `showModal()`** | 예외가 난다. 열려 있으면 아무것도 하지 않고 빠진다 |
| **한글 조합 중 단축키** | `isComposing`이면 반응하지 않는다 |
| **`Alt+숫자`가 가리키는 탭이 없음** | 아무것도 하지 않는다 (기본 동작도 막지 않는다) |
| **타이머가 도는 중 새로고침** | 돌아가던 자리에서 이어진다. 세션 저장소의 `daily-todo:v1:run`에 남겨두기 때문이다 (F-22). 자리를 비운 사이에 끝났으면 `00:00`에 세워두고 소리를 내지 않는다. 탭을 닫으면 사라진다 |
| **`daily-todo:v1:run`이 망가짐** | `null`로 보고 손대지 않는다. 회차 번호만 망가졌으면 사이클에서 빼고 단일 타이머로 되살린다 |
| **회차 설정에 범위 밖 값** | 직전 값으로 되돌린다. 공장 기본값으로 가지 않는다 |
| **`pomodoro`가 없거나 망가진 저장본** | 모자란 자리만 기본값으로 채운다 |
| **배경 탭에서 인터벌이 느려짐** | 끝나는 시각으로 다시 재고, 화면이 보일 때 한 번 더 맞춘다 |
| **소리를 낼 수 없는 환경** | 조용히 넘어간다. 토스트와 `00:00`으로 끝났다는 건 남는다 |
| **hover가 없는 기기(터치)** | 스치듯 드러나는 버튼(`+`, 삭제, 끌기 손잡이, 태그 `×`)을 숨기지 않는다. 숨기는 규칙은 `@media (hover: hover) and (pointer: fine)` 안에만 둔다 |

### 내보내기·가져오기·정렬

| 상황 | 처리 |
|---|---|
| **JSON이 아닌 파일** | 거부하고 "JSON 파일이 아닙니다"라고 알린다. 기존 데이터는 그대로 |
| **구조가 다른 JSON** | `todos` 배열이 없으면 거부한다 |
| **가져온 데이터가 깨져 있음** | 로드와 같은 검증을 탄다 — 고아 승격, 깊이 평탄화, `priority`·`tags`·`category` 교정 |
| **가져오기 도중 저장 실패** | 가져오기 전 상태로 통째로 되돌린다 — 항목·카테고리뿐 아니라 **테마·정렬·회차 설정까지** 스냅샷에 넣는다. 하나라도 빠지면 "되돌렸습니다"라고 알리면서 그 값만 파일 것으로 남는다 |
| **같은 파일을 다시 고름** | `input.value`를 비워 `change`가 다시 오게 한다 |
| **저장된 `sort`가 알 수 없는 값** | `priority`로 교정한다 |
| **형제가 아닌 곳에 끌어 놓음** | 거부한다. `dragover`에서 미리 막고 `reorder`도 다시 확인한다 |
| **자기 자신 위에 놓음** | 아무것도 하지 않는다 |

### 저장·환경

| 상황 | 처리 |
|---|---|
| `localStorage` 접근 불가 (시크릿 모드, 브라우저 차단) | 메모리 배열로 폴백해 앱은 정상 동작. 상단 경고 배너 |
| JSON 파싱 실패 (데이터 손상) | `daily-todo:v1:corrupted` 로 옮기고 빈 목록으로 시작. 배너 안내 |
| **파싱은 되지만 우리 형식이 아님** (객체가 아니거나 `todos`가 배열이 아님) | 손상과 **같은 경로**로 보낸다. `:corrupted`로 옮기고 빈 목록으로 시작하며 배너로 알린다 |
| **판 번호(`rev`)를 읽을 수 없는 저장본에 쓰기** | 그냥 덮지 않는다. 우리가 `load()`에서 읽어온 **그 원문 그대로일 때만** 지나가고, 아니면 물러난다 (F-20) |
| `QuotaExceededError` | 마지막 변경을 롤백하고 "저장하지 못했습니다" 알림 |
| 스키마 필드 누락/타입 불일치 | 항목 단위로 검증. 불량 항목만 버리고 나머지는 살린다 |
| 같은 앱을 여러 탭에서 열어둠 | **덮어쓰지 않는다.** F-20 참조 |
| `crypto.randomUUID` 미지원 | §5의 폴백 사용 |
| 제목·태그·카테고리 이름에 HTML/스크립트 삽입 | `textContent`로만 렌더링. `innerHTML` 금지 |
| 항목 100개 이상 | 전체 재렌더로도 문제없음. 500개 넘으면 그때 대응 |

**로드 시 검증 순서**: **카테고리 목록 확정** → 스키마 검증 → `priority`·`tags` 교정 → 순환 참조 제거 → 고아 승격 → 깊이 평탄화 → 카테고리 상속 재확인 + `order` 재정렬. 이 순서를 지켜야 뒤 단계가 앞 단계의 결과를 신뢰할 수 있다. 카테고리가 맨 앞인 이유는 항목의 `category` 검증이 그 목록을 기준으로 돌아가기 때문이다.

**소스 파일에 제어 문자를 남기지 않는다.** `Map` 키 구분자 같은 데 `'\u0000...'`를 쓰면 원시 NUL 바이트가 파일에 박히고, `grep`·`file`이 그 파일을 바이너리로 취급해 정적 검사가 조용히 아무것도 못 찾고 지나간다. `Map`은 `null`을 그대로 키로 받으므로 구분자가 필요 없다.

## 9. 비기능 요구사항

**성능**
- 초기 로드 200ms 이내, 토글/추가 반응 16ms 이내 (항목 100개 기준)
- 조회는 **색인(`Map`)으로 선형**을 유지한다. 배열을 항목마다 훑으면 O(n²)이 되어 1000개에서 무너진다
- 화면 갱신은 전체 재렌더로 둔다. 색인을 넣은 뒤로는 DOM 재구성이 지배적이고, 그마저 선형이다
- **1초마다 도는 자리는 틱당 DOM 변경 수로 잰다.** 시간이 아니라 이 숫자가 기준인 이유는,
  배경 탭에서 인터벌이 느려지면 초당 수는 줄어도 낭비는 그대로이기 때문이다.
  제목이 초마다 정확히 한 번 갈리므로 그것을 틱 수로 삼으면 스로틀링과 무관하게 잴 수 있다
- **접혀 있는 자리에는 쓰지 않는다.** 패널이 닫혀 있으면 그 안 전체를, 펼친 시계가 접혀
  있으면 그 안을 건너뛴다. 펴는 자리에서 다시 그리므로 펴는 순간 따라잡는다.
  실측으로 틱당 7건에서 2건으로 줄었다 — 남은 둘은 문서 제목과 지금 보이는 시계뿐이다
- **`hidden`은 한쪽으로만 샌다.** 이미 숨은 것에 `hidden = true`를 다시 넣으면 속성이
  그대로 다시 쓰이는데, 이미 보이는 것에 `false`를 넣는 것은 아무 일도 아니다.
  그래서 "늘 숨어 있는 자리"만 조용히 새고 있었다. `setText`·`setAttr`과 같은 요령으로 막는다
- 외부 폰트·이미지·CDN 요청 0건. 첫 화면이 뜨고 나면 그 뒤로는 네트워크를 쓰지 않는다 —
  할 일을 넣고 고치고 지우는 일이 전부 브라우저 안에서 끝난다.
  다만 **그 첫 화면은 받아와야 한다.** 서비스 워커를 두지 않으므로 네트워크가 없으면
  주소 자체가 열리지 않는다. `file://`도 지원 대상이 아니다(§6)

**접근성**
- 완료 체크는 실제 `<input type="checkbox">` 사용 (`indeterminate` 때문에 더욱 그렇다)
- 계층은 `<ul>` 안에 `<ul>`을 중첩해 마크업으로 표현한다
- 목록을 감싸는 바깥은 `<main>`이다. 어느 랜드마크에도 속하지 않으면 보조 기술의
  "본문으로 건너뛰기"가 걸릴 자리가 없다. `header`·`nav`·`footer`는 이미 그 안에 있다
- 모든 인터랙션이 키보드만으로 가능하고, 포커스 링이 보인다
- 우선순위는 마커에 **숫자를 직접 그린다**. 색·굵기만으로 네 단계를 구분시키지 않는다
- 우선순위 마커에 `aria-label="우선순위 변경: {제목}, 현재 0 (가장 높음)"`.
  열린 목록에도 같은 이름을 준다. 보이는 것은 숫자만 둔다 — 목록 안에서 자리를 넓히지 않는다
- 태그 배지는 `<button>`으로 만들고 `aria-label="태그 필터: 세금"`
- 하위 추가 버튼에 `aria-label="하위 할 일 추가: {상위 제목}"`
- 삭제 버튼에 `aria-label="삭제: {제목}"`
- 진행률 바에 `role="progressbar"` + `aria-valuenow`
- 문맥 행에 `aria-disabled="true"`
- 토스트는 `aria-live="polite"`
- 카테고리 관리 버튼에 `aria-label="카테고리 관리"` + `aria-expanded` + `aria-controls`
- 카테고리 삭제 버튼에 `aria-label="카테고리 삭제: {이름}"`, 옮길 곳 선택에 `aria-label="{이름}의 항목을 옮길 카테고리"`
- 카테고리 배지 버튼에 `aria-label="카테고리 변경: {제목}, 현재 {카테고리}"` (F-03)
- 카테고리 오류 문구는 `role="alert"`, 목록 상태 문구는 `role="status"`.
  **`role="alert"` 영역은 숨김이 풀리는 것과 글이 채워지는 것을 같은 태스크에 넣지 않는다** —
  자리를 빈 채로 먼저 열고 글은 다음 태스크에 넣는다 (§13)
- 잘못된 값을 받은 입력 칸에는 `aria-invalid="true"`를 함께 건다.
  문구를 띄우는 것만으로는 **어느 칸이** 잘못됐는지 전해지지 않는다
- 규칙을 적어둔 힌트 줄은 `aria-describedby`로 그 입력 칸에 묶는다
  (`#add-input` → 접두어 힌트, `#category-name` → 카테고리 오류)
- 도움말 본문처럼 세로로 넘치는 영역에는 `tabindex="0"`을 둔다. 없으면 브라우저에 따라
  포커스를 못 받아 키보드로 굴릴 방법이 사라진다
- **글자 대비는 라이트·다크 양쪽에서 WCAG AA(4.5:1)를 지킨다.** 평면 배경만 재지 않고
  그 색이 실제로 얹히는 틴트 위에서도 잰다. 카테고리 배지처럼 색조가 도는 값은
  밝기를 `oklch()`로 못박는다 — `hsl`의 명도는 같은 값이라도 색조마다 휘도가 달라
  절반이 기준에 못 미친다 (§7 "스타일 방향")
- 카테고리 색 점은 장식이다. 이름을 반드시 함께 쓴다 (색만으로 구분되지 않게)
- 테마 토글은 `role="switch"` + `aria-checked`. 남은 할 일 배지는 `aria-live="polite"`
- 도움말 버튼에 `aria-label="도움말"` + `aria-haspopup="dialog"`
- `prefers-reduced-motion: reduce`를 켠 사람에게는 전환을 끈다. 값마다 찾아 끄지 않고
  전부 한 번에 끈다 — 새로 붙인 전환을 빠뜨리면 그 설정을 켠 사람만 알게 되기 때문이다
- 뽀모도로 버튼에 `aria-label="뽀모도로 타이머"` + `aria-expanded` + `aria-controls`.
  **화면에 보이는 글자를 이름 안에 그대로 담는다** (WCAG 2.5.3) — 음성으로 "뽀모도로
  타이머"라고 부르는데 이름이 "뽀모도로"뿐이면 그 명령이 이 버튼에 닿지 않는다.
  보이는 글자와 접근 이름을 같게 둔다 — 음성으로 조작할 때 부르는 이름이 달라지면 안 된다
- 시계 펼치기·설정 버튼도 `aria-expanded` + `aria-controls`를 가진다.
  펼치기 버튼은 아이콘 옆에 **글자를 함께 보여주고**, 상태에 따라 `펼치기` ↔ `접기`로 바뀐다.
  `aria-label`(`시계 펼치기` ↔ `시계 접기`)은 보이는 글자를 그대로 품는다 —
  음성으로 조작하는 사람이 화면에 보이는 말로 부를 수 있어야 한다 (WCAG "Label in Name").
  글자와 `aria-label`은 **한 자리에서 함께** 고친다. 따로 두면 한쪽만 고치는 실수가 난다
- 회차 설정의 입력 칸마다 `aria-label`을 둔다 — `2회차 집중 시간(분)`
- 숫자만 적힌 선택지는 `aria-label`이 뜻을 채운다 — `우선순위 (0이 가장 높음)`
- 확인 다이얼로그는 `<dialog>` + `showModal()` — 포커스 가둠과 `Esc`를 브라우저가 맡는다
- 단축키 대상에 `aria-keyshortcuts`를 단다 (`Alt+N`, `Alt+1`~`Alt+9`)
- **끌어 놓기에는 반드시 키보드 대안을 둔다.** 손잡이에 `Alt+↑`/`Alt+↓`를 걸고
  `aria-label`로 그 사실을 알린다. 드래그만 있으면 마우스 없이는 순서를 못 바꾼다
- **삭제 직후 `실행 취소`에 키보드로 닿을 수 있어야 한다.** 지운 행이 사라지면서 포커스도 없어지는데 토스트는 DOM 맨 끝이라 Tab으로는 5초 안에 도착하기 어렵다. 키보드로 지운 경우(`e.detail === 0`)에는 실행 취소 버튼으로 포커스를 옮기고, 토스트가 닫힐 때 포커스가 그 안에 있었으면 입력창으로 되돌린다

## 10. 개발 마일스톤

각 단계는 **그 자체로 동작하는 앱**으로 끝난다. 중간에 멈춰도 쓸 수 있는 상태여야 한다.

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| **M1** | `store.js` — 로드/저장/CRUD + `parentId`·`priority`·`tags` 필드 + 조회 헬퍼 | 콘솔에서 트리를 만들고 새로고침해도 살아있다 |
| **M2** | 평평한 목록 렌더 + 상위 추가 + 완료 토글 (계층·우선순위·태그 표시 없음) | 화면에서 추가하고 체크할 수 있다 |
| **M3** | 계층 렌더링 + 하위 추가 + 완료 전파 | 쪼개기가 화면에서 된다. 상위/하위 체크가 맞물린다 |
| **M4** | 인라인 수정 + 캐스케이드 삭제 + 실행 취소 | CRUD가 전부 화면에서 된다 |
| **M5** | 카테고리 필터 + 리프 기준 진행률 | 필터 인프라와 집계가 완성된다 |
| **M6** | `parse.js` 우선순위 파싱 + 정렬 + 시각 표현 + 마커에서 고르기 | `!`로 입력한 항목이 위로 올라온다 |
| **M7** | `parse.js` 태그 파싱 + 태그 배지 + 태그 바 + 태그 필터 + 문맥 행 | `#`로 붙인 태그로 추려 볼 수 있다 |
| **M8** | 엣지 케이스, 빈 상태, 접근성, 반응형 | §8 표의 항목이 전부 처리됐다 |

> **순서에 관한 두 가지 원칙.**
> **M2를 계층 없이 끝낸다** — store에는 이미 모든 필드가 있지만 화면은 평평하게 그린다. M2 끝에서 이미 쓸 수 있는 앱이 나오고, M3은 렌더링 교체 하나로 좁혀진다.
> **M6·M7을 M5 뒤에 둔다** — 태그 필터는 M5에서 만든 필터 상태 기계를 재사용한다. 필터가 없는 상태에서 태그를 먼저 붙이면 "태그는 달았는데 쓸 데가 없는" 구간이 생기고, 나중에 필터를 넣으면서 태그 표시를 다시 고치게 된다.

## 12. 확인이 필요한 결정

착수 전에 답이 필요한 항목들이다. 기본 가정은 명시해뒀다.

1. **누적인가, 매일 리셋인가?**
   기본 가정 = **누적**. 완료 항목도 목록에 남고 직접 지운다.
   매일 초기화되는 개념이라면 `dueDate` 필드와 자정 롤오버 처리가 필요하고, 계층이 붙은 지금은 "부모는 어제 건데 자식은 오늘 것" 같은 경우까지 정의해야 해서 스코프가 크게 늘어난다.

2. ~~**우선순위 3단계로 충분한가?**~~ → **결정됨 (v1.6)**: 부족하다고 판단해 **0~3 네 단계**로 늘리고 입력창에 선택 상자를 두었다. 0이 가장 높다.

3. **태그를 상위에 붙였을 때 하위도 그 태그로 필터에 걸려야 하나?**
   기본 가정 = **아니오**. 상위만 걸리고, 하위는 하위대로 자기 태그로 걸린다.
   상속시키면 태그가 카테고리와 역할이 겹치기 시작한다.

4. **깊이 2단계로 충분한가?**
   기본 가정 = **2단계**. 스키마는 임의 깊이를 표현할 수 있어 나중에 UI만 고쳐 확장 가능하다.

5. ~~**카테고리 3개로 충분한가?**~~ → **결정됨 (v1.3)**: 부족하다고 판단해 사용자가 직접 만들고 지우게 했다 (F-13).
   **이름 바꾸기도 넣었다** (v2.6, F-13). 지우고 다시 만들면 항목이 전부 다른 카테고리로 옮겨 갔다가 하나씩 돌아와야 하고 색조도 새로 뽑히는데, 이름만 갈아 끼우면 소속도 색도 그대로 남는다.
   **항목의 카테고리를 나중에 바꾸는 길도 열었다** (v3.0, F-03). 배지를 눌러 그 자리에서 고른다. "상위 카테고리를 바꾸면 하위도 갱신된다"는 처음부터 명세에 있었지만 정작 닿을 UI가 없어, 잘못 넣은 항목은 지우고 다시 만드는 수밖에 없었다.

## 13. 구현하면서 명세와 달라진 것

만들어보고 나서 조정한 지점들이다. 명세를 그대로 두면 어긋나 보이므로 여기에 남긴다.

**편집 중 `!`는 올리기만 하고 내리지 않는다** (F-03·F-05).
F-03의 "편집 중 입력한 `!`·`#`도 새로 파싱된다"를 글자 그대로 적용하면, 오타 하나 고치려고 편집할 때마다 `!`를 안 썼다는 이유로 `높음`이 `보통`으로 떨어진다. `!`를 "올려라"라는 지시로 읽고, 없으면 기존 값을 유지한다. 태그는 F-07 명시대로 기존에 더한다.

**태그 필터 0건 문구는 도달할 수 없다** (F-09·§7).
"필터 중인 태그를 가진 항목이 0개가 되면 자동으로 `전체`로 복귀한다"가 먼저 걸려서 0건 화면이 나올 자리가 없다. 두 규칙이 겹치고 자동 복귀가 이긴다. 문구는 구현해뒀으니 자동 복귀를 빼면 바로 보인다.

**카테고리 탭에 개수를 넣지 않았다** (§7 화면 설계).
§7 그림에는 `전체 6 │ 업무 3`처럼 개수가 있지만, 그 숫자는 리프 기준 진행률과 계산 기준이 다르다. 두 숫자가 한 화면에서 다르게 세어지면 어느 쪽이 맞는지 알 수 없어 뺐다.

**태그 배지는 `<span>` 안에 버튼 두 개다** (§7 태그 표현).
"배지는 `<button>`으로"를 그대로 따르면서 `×`까지 버튼으로 만들면 버튼 중첩이라 유효하지 않은 HTML이 된다. 필터 동작이 버튼인 것은 지켰다.

**하위 입력창은 포커스가 벗어나도 닫히지 않는다** (F-02).
치던 내용이 클릭 한 번에 날아가지 않게 하는 보호다. 다른 상위의 `+`를 누르면 입력창이 그쪽으로 옮겨간다.

**하위 입력창에 `추가`·`×` 버튼을 붙였다** (F-02).
명세는 닫는 길로 `Esc`와 빈 상태 `Enter` 둘만 정했는데, **둘 다 화면에 보이지 않았다.** 열린 행에 들어 있는 것이 입력칸 하나뿐이라, `Esc`를 아는 사람만 빠져나올 수 있었고 마우스만 쓰는 사람은 넣을 수도 나갈 수도 없었다. `+`로 여는 짝이 있는데 닫는 짝이 없었던 셈이다.

"연속 입력"과 "실수로 안 닫힘"은 지키되, **그만두려는 사람을 위한 출구를 화면에 뒀다.** 같은 `+`를 다시 누르면 닫히는 것도 함께 넣었다 — 여는 버튼이 닫기도 한다는 것은 이미 사람들이 기대하는 동작이다.

**`load()`는 교정한 데이터를 되쓰지 않는다** (F-12).
여는 것만으로 저장소를 건드리지 않는 편이 안전하다. 다음 변경이 일어날 때 정리된 상태로 함께 저장된다.

**`is-primary`에 규칙을 붙였다** (§7 스타일 방향).
Markdown 충돌 상자와 미리보기 상자의 마크업에 `dialog-button is-primary`가 있는데
`styles.css`에는 그 선택자가 없었다. 눌러야 할 `Markdown 편집 가져오기`와 `가져오기`가
`취소`와 똑같이 보이고 있었던 셈이다. 문의하기(F-23)에서 같은 클래스를 쓰게 되면서
`is-danger`와 같은 모양(`--focus` 색 + 굵게)으로 규칙을 세웠다. 되돌릴 수 없다는 뜻과
이것을 누르라는 뜻이 갈라져야 할 자리가 아직 없어서 한 모양을 나눠 쓴다.

**`.pomo-dial-face svg`는 직계 자식만 잡아야 한다** (F-22d).
숫자만 보기에서 눈금을 접으려고 `body.pip.is-text .pomo-dial-face svg { display: none }`을
걸었더니, 그 안의 **버튼 아이콘까지 함께 사라졌다.** 누를 것을 원 안(`.pomo-dial-label`)에
넣은 뒤로 그 아이콘도 `.pomo-dial-face`의 자손이 되었기 때문이다. 화면에는 테두리만 남은
빈 동그라미가 떴고, 눌리기는 눌려서 한참 못 봤다. `>`를 넣어 눈금만 잡는다.

**검색은 분류 축과 함께 걸린다** (F-09 vs F-15).
F-09의 "필터는 하나만"은 카테고리와 태그, 같은 성격의 분류 축 둘에 대한 규칙이다. 검색은 분류가 아니라 좁히기라 그 위에 얹힌다. 자세한 이유는 F-15.

**직접 입력한 길이일 때는 `설정` 버튼이 켜진다** (F-22).
명세는 "고른 것은 표시가 남는다"를 프리셋에만 적었다. 그래서 시간을 직접 넣으면 **켜진 버튼이 하나도 없는 상태**가 됐고, 시작을 눌렀을 때 무엇으로 도는지 화면만 보고는 알 수 없었다. 남은 시간이 `07:00`으로 바뀌긴 하지만, 고르는 줄에서 아무 표시가 없으면 "설정이 먹었나" 자체가 불확실하다.

사이클 · 프리셋 셋 · `설정` 가운데 언제나 하나만 켜지도록 맞췄다. 프리셋과 같은 값(25분)을 직접 입력하면 프리셋 쪽이 켜진다 — 같은 상태를 두 곳에서 알릴 이유가 없다.

**로그인 버튼은 자리만 잡아둔 것이다** (§7).
이 앱에는 계정도 서버도 없고, "외부 요청 0건"과 CSP의 `connect-src 'none'`이 그것을 규칙으로 못박고 있다. 그래도 나중에 붙일 자리를 먼저 만들어 두는 편이 낫다고 보아 제목 아래 왼쪽에 버튼을 두었다 — 자리를 비워두면 그 사이에 다른 것이 들어와 나중에 옮기게 된다.

누르면 로그인 대화상자가 열린다. 아이디·비밀번호 칸과 `로그인` 버튼을 나중에 붙일 모양 그대로 두되, **셋 다 `disabled`로 잠가 두었다.**

**칸을 열어두지 않은 이유가 이 항목의 핵심이다.** 인증할 서버가 없는데 입력을 받으면 두 가지가 따라온다. 하나는 사용자가 다른 곳에서 쓰는 **진짜 비밀번호**를 치는 것이고, 다른 하나는 브라우저의 비밀번호 관리자가 그 값을 **저장하겠느냐고 묻는** 것이다. 아무 데도 보내지 않으니 안전하다고 말할 수도 있지만, 받을 곳이 없는 화면이 비밀번호를 받아내는 모양을 하고 있는 것 자체가 문제다. 잠가 두면 모양은 그대로 보이면서 그 위험만 빠진다.

같은 이유로 비밀번호 칸의 `type`은 `password`가 아니라 `text`다. `password`로 두면 잠겨 있어도 비밀번호 관리자가 로그인 폼으로 인식해 채우려 든다. 마찬가지로 `<form>`으로 감싸지 않았다 — 보낼 곳이 없는 폼은 CSP의 `form-action 'none'`에 막히기 전에 애초에 만들 이유가 없다.

문구로도 상태를 그대로 적는다. 위에는 **"아직 준비 중입니다. 화면만 미리 만들어 두었고, 지금은 할 일이 이 브라우저에만 저장됩니다."**, 아래에는 다른 기기로 옮기려면 내보내기·가져오기를 쓰라고 적었다. "준비 중"만 말하면 그동안 내 할 일이 어딘가 서버에 있는 줄 알 수 있고, 대안을 적지 않으면 기기를 옮기는 길이 아예 없는 줄 안다.

진짜 로그인을 만들려면 백엔드가 필요하고, §6의 절대 제약과 CSP를 함께 고쳐야 한다. 그때는 여러 탭·여러 기기의 충돌 처리(F-20)도 다시 설계해야 한다.

**우선순위를 순환에서 고르기로 바꿨다** (F-05).
명세는 마커를 누르면 `0 → 1 → 2 → 3 → 0`으로 돌게 했다. 네 단계뿐이라 돌리는 편이 빠를 것 같았는데, **기본 정렬이 우선순위라 한 번 누를 때마다 목록이 다시 서고 그 항목이 달아난다.** 3에서 0으로 가려면 세 번을 눌러야 하는데 두 번째 누를 자리에는 이미 다른 항목이 와 있다. 한 번에 고르면 정렬도 한 번만 일어난다. 카테고리 변경·제목 편집과 같은 방식이라 새로 배울 것도 없다.

**연결선을 체크박스 중심이 아니라 왼쪽 테두리에 세웠다** (§7).
처음에는 상위 체크박스의 **중심**에 그었다. 그런데 그 지점이 하위 행에서는 우선순위 숫자 칸 한복판(16px 중 11px)에 떨어져, **선이 숫자를 스치고 지나갔다.** 상위 기준으로 자리를 정하고 하위 행에서 무엇과 만나는지를 보지 않은 결과다.

테두리로 옮기면 네모를 반으로 가르지도 않고, 그만큼 왼쪽이라 하위 내용이 선 오른쪽에서 시작할 수 있다. 들여쓰기는 이제 `--indent`를 따로 적지 않고 선 위치에서 유도한다(`손잡이 + 간격 + 마커 + 간격 + 4px`). 넓은 화면과 좁은 화면 모두 여유 4px가 자동으로 나온다.

**우선순위 숫자를 칸 가운데로 옮겼다** (§7).
`width: 16px`에 `padding-left: 5px`를 주고 `text-align: center`를 걸면, 가운데는 **패딩 안쪽 11px의 가운데**가 된다. 숫자가 칸 중심보다 2.5px 오른쪽에 놓여 왼쪽 6.8px · 오른쪽 1.8px로 치우쳤다. 그 패딩은 우선순위 0의 accent 바 자리였는데, 바는 `position: absolute`라 애초에 자리를 비워둘 필요가 없었다. 패딩을 걷고 바를 칸 밖(`left: -5px`, 손잡이와의 간격)으로 뺐다.

**우선순위 4단계는 비목표였다.**
§1이 "우선순위 4단계 이상"을 제외했고 F-05는 3단계 고정이었다. 요청에 따라 0~3으로 늘렸다. 세 단계가 네 단계의 앞자리(0·1·2)로 그대로 들어가므로 기존 데이터의 상대 순서는 바뀌지 않는다.

함께 바뀐 것 둘: 저장값이 문자열에서 **숫자**가 됐고(§5), `보통`에 표시하지 않던 규칙이 **모든 단계에 숫자를 그리는** 것으로 바뀌었다(§7). 네 단계를 색과 굵기만으로 구분시킬 수 없기 때문이다.

**완료상태순 정렬은 F-06을 뒤집는다 — 다만 옵션으로만.**
F-06은 "완료 여부는 정렬에 영향을 주지 않는다"고 못 박았고 그 이유(하루 20번 일어나는 토글에 목록이 흔들리면 위치 기억이 깨진다)는 지금도 유효하다. 그래서 **기본값은 우선순위순 그대로** 두고, 완료상태순은 고를 때만 켜지게 했다. 기본을 쓰는 한 F-06의 수용 기준은 그대로 성립한다.

**수동 정렬은 비목표였다.**
§1이 "항목 순서 수동 정렬"을 제외했지만 요청에 따라 넣었다. 대신 **형제 그룹 안으로만** 한정해, 원래 함께 제외됐던 "드래그로 부모 바꾸기"는 그대로 막아뒀다. 이유는 F-19에 적었다.

**테마 부트스트랩을 인라인에서 `theme.js`로 뺐다** (§6 CSP).
CSP의 `script-src 'self'`를 `'unsafe-inline'` 없이 걸려면 인라인 스크립트가 없어야 한다. 해시(`'sha256-…'`)로 허용할 수도 있었지만, 그 다섯 줄을 고칠 때마다 해시를 다시 계산해야 하고 잊으면 스크립트가 **조용히 막혀** 첫 페인트 깜빡임이 되살아난다. 원인을 찾기 어려운 종류의 고장이라, 파일로 빼서 손댈 것을 없앴다. 대가는 `<head>`의 요청 하나다.

**`file://`은 더 이상 지원 대상이 아니다** (§6).
원래 `type="module"`을 쓰지 않는 이유가 `file://`의 CORS였다. 온라인에 올려 그 주소로 들어가기로 하면서 그 이유는 없어졌지만, **규칙은 남는다** — 모듈 스크립트는 언제나 지연 실행이라 `<head>`에 둬도 첫 페인트 뒤에 돌고, 그러면 테마를 제때 칠하지 못한다. 이유가 바뀌었다는 것을 적어두지 않으면 다음 사람이 "이제 `file://`을 안 쓰니 모듈로 바꿔도 되겠다"고 판단한다.

**블로그에 사본을 두지 않고 이 저장소를 직접 서비스한다** (§6).
처음에는 앱 파일을 블로그(`perust.github.io`)의 `public/contents/my-task/`로 복사해 두었다. 그러면 앱을 고칠 때마다 사본도 갱신해야 하는데, 실제로 그것을 잊어 **몇 주 묵은 버전이 올라가 있었다** — 그 사이 사이트에는 데이터가 말없이 사라지는 결함 셋이 살아 있었다. 소스가 고쳐졌다는 사실은 사용자에게 아무 의미가 없다.

지금은 저장소 자체를 GitHub Pages로 내보내고(`perust.github.io/my-what-todo/`) 블로그는 그 주소를 링크만 한다. 서브모듈도 검토했지만, 그쪽은 **가리키는 커밋을 손으로 올려야** 해서 잊을 자리가 그대로 남는다 — 복사가 한 줄로 줄 뿐이다.

**`store.js`는 `<head>`에서 먼저 읽는다** (F-14).
나머지 스크립트는 본문 끝에 있다. `store.js`만 앞으로 뺀 이유는 첫 페인트 전에 고른 테마를 알아야 하기 때문이다. 예전에는 OS가 라이트인데 다크를 골라둔 경우 라이트로 한 번 칠해졌다가 뒤집혔다.

`<head>`에서 도는 `theme.js`는 `Store.peekTheme()` 하나만 부른다. 저장소 키를 `index.html`에 다시 적지 않으려고 둔 API다. 여기서 `Store.load()`를 부르면 안 된다 — 손상 데이터를 치워버려서 나중에 `app.js`가 알림을 띄울 기회를 잃는다. `peekTheme()`은 상태를 하나도 건드리지 않는다.

**태그 바는 태그 필터에 좁아지지 않는다** (F-09).
"현재 사용 중인 태그 목록"을 문자 그대로 지키면, 태그 하나를 고른 순간 그 태그만 남아 다른 태그로 건너뛸 길이 사라진다. 태그 축만 빼고 센다. 카테고리와 검색어는 지금 보고 있는 범위 자체라 그대로 좁힌다.

**내보내기는 저장됐다고 말하지 않는다** (F-18).
`<a download>`를 눌러 브라우저에 넘기는 것까지가 앱이 할 수 있는 전부다. 내려받기가 막혔는지, 사용자가 취소했는지는 알 방법이 없다. 그래서 "내보냈습니다"가 아니라 내려받기를 시작했다고만 알리고, 파일이 없을 때 어디를 볼지 덧붙인다.

**블롭 주소는 한 박자 뒤에 거둔다** (F-18).
`link.click()` 직후에 `revokeObjectURL`을 부르면 브라우저가 아직 블롭을 읽기 전이라 내려받기가 취소될 수 있다.

**알림은 실행 취소를 밀어내지 않고 기다린다** (F-04 vs F-22).
토스트 하나를 알림과 실행 취소가 나눠 쓴다. 예전에는 알림이 오면 되돌릴 것을 지우고 자리를 차지했다. 뽀모도로는 아무 때나 구간이 끝나므로, 방금 지운 항목의 5초가 "25분이 끝났습니다"에 덮여 사라졌다. 알림은 뒤에 다시 뜨지만 지운 항목은 그 5초가 지나면 영영 되살릴 수 없다. 그래서 되돌릴 것이 걸려 있으면 알림이 기다린다.

미뤄둔 알림은 **하나만** 들고 있는다. 밀린 것을 줄줄이 띄우면 어느 것이 지금 일인지 알 수 없다.

**돌아가는 타이머만 세션 저장소에 둔다** (F-22 vs §5 "키는 하나만").
"`localStorage` 키는 하나"는 **할 일 데이터**를 흩뜨리지 말라는 규칙이다. 돌아가는 타이머는 내보낼 것도, 판을 매길 것도, 탭끼리 맞출 것도 아니다. 저장 형식에 섞으면 타이머를 시작했다는 이유로 다른 탭의 편집과 실행 취소가 날아간다. 세션 저장소는 다른 저장소이고, 새로고침을 넘기되 탭을 닫으면 사라진다 — 이 값의 수명과 정확히 같다.

**모션 줄이기에는 `!important`를 쓴다** (§9 접근성).
이 파일에서 유일한 `!important`다. 전환마다 선택자를 적어 끄면 나중에 하나를 빠뜨리게 되고, 빠뜨렸다는 사실은 그 설정을 켠 사람만 알게 된다. `*`로 한 번에 덮으려면 어느 규칙보다 뒤에 서야 한다.

**원형 시계의 전환 시간은 갱신 주기와 같아야 한다** (F-22).
`transition`을 갱신 주기보다 짧게 주면 그만큼만 움직이고 나머지 시간은 멈춰 있어, 이어서 흐르지 않고 초마다 끊겨 보인다. 갱신을 1초로 바꿀 때 전환도 함께 1초로 옮겼다.

**손상 판정은 파싱 실패보다 넓다** (§8).
§8은 손상을 "JSON 파싱 실패"로만 적었다. 그대로 두면 파싱은 되는데 우리 형식이 아닌 저장본 — 객체가 아니거나 `todos`가 배열이 아닌 것 — 이 그물을 빠져나간다. 그때 앱은 배너도 백업도 없이 빈 목록으로 시작하고 멀쩡한 새 앱처럼 보이는데, 원본은 저장소에 그대로 남아 있다가 사용자가 항목 하나를 추가하는 순간 예고 없이 덮여 영영 사라진다. `:corrupted` 백업과 손상 배너가 있는 이유가 정확히 이 상황이라, 두 경우를 같은 경로로 보낸다. 가져오기도 같은 검사를 통과해야 한다.

**판 번호가 없는 저장본은 원문을 비교해 가른다** (F-20).
F-20의 "낡은 상태면 거부한다"를 글자 그대로 적용하면 비교할 `rev`가 없는 저장본에서 답이 안 나온다. 없다고 그냥 덮으면 남이 써둔 것을 날리고, 전부 충돌로 보면 판 번호를 넣기 전에 쓰인 v1·v2 저장본을 가진 사용자가 영영 저장하지 못한다. 그래서 판 번호가 없을 때만 **우리가 `load()`에서 읽어온 그 원문 그대로인가**로 판정한다. 원문이 그대로면 그 사이에 아무도 쓰지 않았다는 증거이므로 지나가고, 한 글자라도 다르면 남이 쓴 것이므로 물러난다. 한 번 쓰고 나면 저장소에 든 것은 판 번호가 박힌 우리 블롭이라 이 길은 다시 쓰이지 않는다.

**판 번호와 테마는 블롭 앞머리에서 읽는다** (F-14·F-20).
`persist()`는 판 번호 하나 때문에, `peekTheme()`은 테마 하나 때문에 블롭을 통째로 파싱했다. 항목 1000개(218KB)에서 `JSON.parse` 한 번이 1.79ms고 그것이 변경 한 번(6.02ms)의 30%였다. `peekTheme()`은 첫 페인트 **앞**이라 그만큼 화면이 늦게 뜬다. `persist()`가 늘 같은 키 순서로 쓰므로 앞머리는 고정이고, 맨 앞에 앵커를 건 정규식으로 두 값만 꺼낸다(0.001ms). 앵커가 없으면 할 일 제목에 든 `"rev":`에 잘못 걸린다. 모양이 조금이라도 다르면 — 사람이 들여썼거나, 판 번호가 없는 v1·v2거나 — 예전처럼 통째 파싱으로 물러나므로 읽어내는 값은 달라지지 않는다.

**카테고리 개수에 상한을 뒀다** (F-13).
명세에는 개수 제한이 없었다. 상한이 없으면 카테고리가 수십만 개인 파일 하나로 앱이 그 자리에서 멈춘다 — 새 색조를 고르는 `pickHue`가 `Math.min(...used)`로 거리를 재는데, 스프레드로 펼친 인자가 엔진의 개수 제한을 넘기면 `RangeError`가 난다. 64는 엔진이 멈추지 않을 값으로 잡았다. `addCategory`만 막으면 안 되고 로드·가져오기에서도 같은 자리에서 잘라야 한다. 만들 때만 막으면 다음에 앱을 열 때 카테고리가 예고 없이 사라지고 항목만 남는다.

이 자리에는 원래 "64는 **화면이 감당할 수를 한참 넘겨 잡은 값**"이라고 적혀 있었다. 사실이 아니었다 — 아래 항목이 그 이야기다.

**탭 · 태그 바 · 카테고리 목록에 높이 상한을 뒀다** (§7 화면 설계).
개수 상한만 두고 **그 개수를 화면이 감당하는지는 재보지 않았다.** 세 곳이 모두 상한 없이 자라고 있었다.

- 카테고리 43개에서 탭바가 **열 줄 323px**가 되어, 할 일 목록이 화면 맨 아래에서야 시작했다. 사실상 목록이 보이지 않는다.
- 톱니와 정렬은 `align-items: center`로 붙어 있어, 탭이 여러 줄이 되면 **그 블록 한복판으로 내려앉았다.** 탭 사이에 끼어 있는 것처럼 보인다.
- 톱니를 눌러 여는 관리 패널은 **1920px로 통째로 펼쳐졌다.** 페이지가 3672px가 되고, 정작 `새 카테고리 이름` 입력칸이 그 끝에 밀려 하나 더 만들려면 화면 두 번 반을 굴려야 닿았다. 만드는 자리는 언제나 목록 바로 아래에 있어야 한다.

**64개 같은 극단에서만 나는 일이 아니었다.** 폰 폭(360px)에서는 카테고리 **8개** — 기본 3개에서 다섯 개만 더해도 — 톱니가 첫 줄에서 39px 내려간다. 도움말은 "카테고리는 64개까지 만들 수 있습니다"라고 안내하고 있었다. 만들 수는 있는데 만들면 화면이 감당하지 못했다.

탭과 태그 바는 **세 줄까지만** 자리를 내주고 그 안에서 굴린다. 관리 패널의 목록은 줄 높이가 이름 길이에 따라 달라져 줄 수로 잡을 수 없어 화면 절반까지만 쓴다. 톱니·정렬은 위에 붙인 뒤 탭 한 줄과의 높이 차이만큼만 내려 첫 줄 가운데에 세운다.

**치수는 한쪽에서 유도한다** — 탭은 세로 패딩 대신 `--tab-h`에서 높이를 얻고, 도구가 내려가는 거리와 세 줄 상한이 모두 그 값과 줄 간격에서 나온다. 따로 적어두면 탭 패딩을 고치는 순간 도구만 어긋나고, 줄 간격을 고치면 상한이 세 줄에서 어긋난다.

**대신 잃은 것도 적어둔다.** 상한을 넘긴 카테고리는 굴려야 보인다. 스크롤 막대가 겉으로 드러나지 않는 환경에서는 뒤에 더 있다는 것이 바로 보이지 않는다. 키보드로 넘기면 따라 굴러오고 관리 패널은 전부 보여주므로 닿을 길은 남아 있지만, 카테고리를 수십 개 쓰는 사용이 실제로 생기면 탭 말고 다른 고르는 방법이 필요하다.

**`role="alert"` 문구는 다음 태스크에 넣는다** (§9 접근성).
이런 영역은 **이미 접근성 트리에 있는 상태에서 내용이 바뀌어야** 읽힌다. 숨김이 풀리는 것과 글이 채워지는 것이 한 태스크 안에서 함께 일어나면 브라우저는 "글을 가진 영역이 통째로 새로 생겼다"고 보고, 일부 스크린리더는 그것을 읽지 않는다. 두 줄의 순서를 바꾸는 것으로는 달라지지 않는다 — 접근성 트리는 태스크가 끝난 뒤에 한 번 정리되므로 같은 태스크 안의 순서는 보이지 않는다. 그래서 자리를 빈 채로 먼저 열고 글은 다음 태스크에 넣어 실제로 태스크를 건넌다.

건너는 수단은 `setTimeout`이다. **`requestAnimationFrame`을 쓰면 안 된다** — 배경 탭에서 멈추기 때문에, 탭이 숨은 채로 이 자리가 불리면 상자만 열리고 글은 영영 들어가지 않는다. 사용자에게는 빈 상자가, 스크린리더에는 읽을 것이 없는 영역이 남는다. 같은 이유로 외부 변경 따라가기도 숨은 탭에서는 프레임을 기다리지 않는다 (바로 아래).

**외부 변경은 프레임당 한 번만 따라가고, 숨은 탭에서는 읽기만 한다** (F-20).
F-20은 "받는 즉시 다시 읽어 화면을 맞춘다"고 적었다. 이벤트마다 그대로 따라가면 옆 탭에서 `Alt+↓`를 길게 누를 때 초당 스물몇 번씩 들어오는데, 그때마다 통째로 다시 읽고 그리면 이 탭에서 고치던 제목과 되돌릴 수 있던 5초가 그 횟수만큼 날아간다. 그래서 플래그만 세우고 한 프레임에 한 번 돈다.

보이지 않는 탭에서는 **읽기만 하고 그리기를 미룬다.** 읽기까지 거르면 판 번호가 낡은 채로 남아 다음 저장의 경합 검사가 죽는다 — 물러나야 할 자리에서 물러나지 못하거나, 물러나지 않아도 될 자리에서 물러난다. 미뤄둔 것은 탭이 다시 보이는 순간 화면에 옮긴다.

**실행 취소가 실패해도 되돌릴 길을 남긴다** (F-04).
예전에는 복원을 시도하기 **전에** 토스트를 거뒀다. 다른 탭과 부딪히면 "다시 해주세요"라고 안내하면서 정작 다시 누를 곳이 없었고, 지운 항목은 영영 돌아오지 않았다. 이제 복원이 성공한 뒤에 거두고, 실패하면 실패 이유와 `실행 취소` 버튼을 **한 토스트에** 담는다. 이 실패는 `saved()`에 맡길 수 없다 — 되돌릴 것이 걸려 있으면 알림이 뒤로 미뤄져 아무 말도 못 하고, 충돌이면 최신을 읽어오면서 토스트째 접힌다.

**되살릴 때 버리는 알림은 "그 삭제 때문에 생긴 것"뿐이다** (F-04).
처음에는 되살리면 미뤄둔 알림을 무조건 버렸다. 필터가 저절로 풀렸다는 알림은 되살리는 순간 틀린 말이 되기 때문이다. 그런데 그 5초 사이에 사용자가 **다른 버튼을 눌러 생긴 알림**까지 함께 사라졌다 — 그 말은 여전히 맞는데도 영영 못 보게 된다. 알림마다 "이 삭제가 부른 것인가"를 표시해 그것만 버린다.

**필터가 저절로 풀리면 알린다** (F-09).
F-09는 "자동으로 `전체`로 복귀한다"까지만 정했다. 아무 말 없이 목록이 늘어나면 무엇이 잘못됐는지 알 길이 없어, `#세금 태그가 없어져 전체 목록으로 돌아왔습니다.`처럼 이유를 붙였다. 되돌릴 것이 걸려 있으면 그 5초가 지난 뒤에 뜨고, 되살리면 그 알림은 이미 틀린 말이라 버린다 — "태그가 없어졌다"고 알리는 사이에 그 태그는 돌아와 있다.

**필터 밖으로 나가는 항목을 만들면 어디로 갔는지 알린다** (F-01·F-02·F-09).
명세는 추가를 "목록에 나타난다"로만 적었다. 그런데 **필터가 걸려 있으면 나타나지 않는다.** `개인`을 보는 중에 카테고리를 `업무`로 두고 넣으면, 항목은 제대로 만들어지는데 화면은 그대로고 입력칸만 비워진다. 검색어와 태그 필터에서도 똑같다.

사용자에게 이건 **"추가가 안 먹었다"**로 읽힌다. 그러면 다시 누르게 되고, 보이지 않는 곳에 같은 항목이 하나씩 쌓인다. 하위 입력창은 넣은 뒤에 빈 칸으로 다시 열리기까지 해서 성공한 모습과 구별이 아예 안 된다.

그래서 만든 항목이 지금 필터에 걸리지 않으면 토스트로 알리고, **어느 축이 걸렀는지까지 짚는다** — `업무에 추가했습니다. 지금은 개인만 보고 있어서 이 목록에는 나오지 않습니다.` "안 보입니다"만으로는 어디를 눌러야 볼 수 있는지 알 수 없다. 걸리면 아무 말도 하지 않는다. 눈앞에 나타난 것을 굳이 말할 필요는 없다.

필터를 대신 풀어주지는 않는다. 보러 가는 것은 한 번 누르면 되지만, 보고 있던 자리를 앱이 마음대로 옮기면 되돌릴 방법이 없다.

**지운 뒤에는 되돌릴 것을 먼저 세우고 그린다** (F-04·F-16).
"알림이 실행 취소를 밀어내지 않고 기다린다"는 규칙은 **되돌릴 것이 이미 걸려 있을 때만** 걸린다. 그런데 자동 복귀 알림은 `render()` 안에서 나온다. 그리기를 먼저 하면 그 순간에는 아직 걸린 것이 없어 알림이 토스트를 차지하고, 뒤이어 오는 실행 취소 토스트가 그것을 곧바로 덮는다. 사용자는 필터가 왜 풀렸는지 영영 듣지 못한다. 순서를 뒤집어 `showUndo()`를 먼저 부르면 알림이 알아서 뒤로 미뤄지고, 5초 뒤에 제 차례로 뜬다. **삭제와 완료 항목 일괄 삭제 두 곳 모두** 이 순서를 지킨다 — 한쪽만 고치면 다른 쪽에서 같은 증상이 그대로 남는다.

**구간이 끝나도 저절로 넘어가지 않는다** (F-22a를 뒤집는다).
F-22a는 "집중이 끝나면 휴식으로 자동 전환"이었다. 실제로 쓰다 보니 **끝난 것을 알아채지 못한 채 다음 구간이 흐르는 일**이 생겼다. 자리를 비운 사이 휴식 5분이 지나가고 다음 집중까지 시작돼 있으면, 화면의 회차가 실제로 한 일과 어긋난다. 그래서 끝나는 자리에서 멈추고 `휴식 시작` 버튼을 세운다.

버튼을 `시작` **옆에** 두지 않고 그 자리를 대신 맡게 한 이유가 있다. 둘을 나란히 두면 `다시 시작`(방금 끝난 구간을 한 번 더)과 `휴식 시작`(다음 구간으로)이 같은 줄에 서서, 어느 쪽이 사이클을 잇는 것인지 읽히지 않는다. 잃은 것은 "손대지 않아도 사이클이 돈다"이고, 얻은 것은 "화면의 회차가 언제나 실제와 같다"이다.

**미니 타이머 불투명도에 하한을 뒀고, 범위 밖 값은 기본값이 아니라 가장 가까운 자리로 옮긴다** (F-22d).
0까지 내려가면 바탕과 테두리가 사라진다. 미니 타이머는 평면 배경이 아니라 **할 일 카드 위에도 얹히는데**(뷰포트가 좁으면 늘 겹친다) 그러면 아래 글자가 그대로 비쳐 흐린 글자가 3.07:1까지 내려가고 테두리는 1.00:1이 된다. 55%면 겹친 자리에서도 4.5:1을 지킨다.

하한을 새로 두면서 처음에는 범위 밖 값을 기본값(82)으로 되돌렸는데, **이미 23으로 맞춰 쓰던 값이 82로 튀어 올랐다.** 옅게 보고 싶어서 낮춰둔 뜻이 통째로 지워진 것이다. 읽어낼 수조차 없는 값(NaN, 객체)만 기본값으로 보내고, 숫자로 읽히면 하한·상한 중 가까운 쪽으로 옮긴다. 손잡이의 `min`은 `Store.MINI_OPACITY_MIN`에서 가져온다 — 따로 적으면 저장은 막는데 손잡이만 더 내려가는 칸이 생긴다.

**입력칸 테두리는 카드·구분선과 다른 값을 쓴다** (§9 접근성).
`--border`는 배경과 1.17~1.37:1이다. 카드 윤곽과 행 사이 구분선에는 그 정도가 알맞다 — 구조를 나누되 시선을 끌지 않는다. 그런데 같은 값이 입력칸에도 걸려 있었고, **아직 아무것도 적히지 않은 칸에서는 그 선이 "여기에 쓸 수 있다"고 말하는 유일한 표시**다. 그 대비로는 보이지 않는다 (WCAG 1.4.11은 3:1을 요구한다).

`--border`를 통째로 올리는 길은 택하지 않았다. 그러면 화면이 온통 선으로 덮인다. 대신 `--field-border`를 따로 두고 **입력칸에만** 건다. 라이트 3.38 / 3.13, 다크 3.17 / 3.46으로 카드와 바탕 어느 쪽에 놓여도 3:1을 넘긴다. 글자가 적힌 버튼과 카드·구분선은 테두리가 말하지 않아도 알아볼 수 있으므로 `--border` 그대로다.

**우리보다 새로운 형식의 저장본은 덮지 않는다** (F-20).
판 번호(`rev`)는 같은 형식 안에서의 경합만 가른다. Pages가 모든 파일에 `max-age=600`을 주므로 새 버전과 캐시에 남은 옛 버전이 한동안 함께 도는데, 그때 옛 탭이 한 번 저장하는 것만으로 새 형식에서 늘어난 필드가 사라진다. 저장 직전에 읽은 `version`이 우리가 아는 것보다 크면 물러나고 `lastError`를 `"newer"`로 둔다. 사용자에게는 새로고침을 권한다.

**손상 데이터를 옮기지 못해도 이후 저장을 막지 않는다** (§8).
백업 쓰기가 실패하면(손상 블롭이 클 때의 용량 초과) 원본이 저장소에 그대로 남는다. 그 원본은 **우리가 읽어온 그 원문**이므로 `revlessRaw`에 담아둬야 한다. 그러지 않으면 비교할 판 번호도 견줄 원문도 없어 이후 모든 저장이 `conflict`로 막혔다 — 화면에는 "다른 탭에서 먼저 바뀌었습니다"가 뜨는데 다른 탭은 없고, 그동안 편집이 조용히 버려졌다. 옮겼는지는 `Store.wasQuarantined`로 밖에서 물어본다. 배너가 "백업했습니다"라고 말하려면 실제로 옮겼어야 한다.

**세 검증 관문의 기준을 맞춘다** (§5·F-18).
`adopt`(저장본·가져오기), Markdown 정본 검증, 내보내기 세 곳이 같은 데이터를 서로 다르게 판정하면 앱이 자기 저장본 때문에 사용자의 파일을 탓하게 된다. 실제로 둘이 어긋나 있었다.

- **다듬고 자른다**(`trim` → `slice`)는 순서라, 잘린 자리가 공백이면 뒤 공백이 남는다. Markdown 검증은 그 값을 곧바로 거부해 충돌 가져오기가 통째로 죽었다. 자른 뒤에 한 번 더 다듬는다.
- 주소로 옮길 수 없는 id(짝 없는 서로게이트)가 `adopt`만 통과해, 가져오기 뒤로 Markdown 저장이 영영 실패하고 앱 안에서 되돌릴 길이 없었다. `adopt`에서도 거부한다.

**미뤄둔 알림 자리를 누가 지키는지도 정한다** (F-04 vs F-22).
"알림이 실행 취소를 밀어내지 않고 기다린다"까지는 정해뒀는데, **미뤄둘 자리가 하나뿐**이라는 것이 남은 문제였다. 나중 것이 앞의 것을 그대로 갈아치웠다.

앞의 것이 사용자가 **눌러서 나온 답**일 때가 나쁘다. 창으로 빼기가 실패했다는 답을 기다리던 사람이, 뒤이어 온 "집중 구간이 끝났습니다"만 듣고 자기가 누른 버튼이 어떻게 됐는지는 영영 듣지 못한다. 그래서 저절로 뜨는 알림(뽀모도로 구간 종료 둘뿐이다)은 눌러서 나온 답이 밀려 있으면 자리를 뺏지 않는다. 반대 순서는 그대로 둔다 — 뒤에 온 것이 방금 누른 것에 대한 답이라면 그쪽이 더 급하다. 저절로 뜬 것끼리는 나중 것이 이긴다. 낡은 구간 이야기를 들려줄 이유가 없다.

`showTimerNotice`라는 이름을 따로 둔 이유가 여기 있다. 어느 알림이 저절로 뜨는 것인지를 호출부에서 읽을 수 있어야, 새 알림을 더할 때 어느 쪽인지 고민하게 된다.

**시계를 펼치면 같은 숫자가 두 자리에 뜬다** (F-22).
머리줄의 작은 숫자만 accent로 물들고 원 안의 큰 숫자는 그대로였다. 같은 값인데 다른 상태처럼 읽히고, 눈이 가는 쪽은 큰 숫자다. 둘을 같은 자리에서 함께 물들인다. 빼놓은 창은 시계 모드와 숫자 모드가 `.pip-time` 하나를 함께 쓰므로 애초에 어긋나지 않는다.
