## 1. 배경과 목표

### 문제
머릿속에 뭉쳐 있는 "지금 해야 할 일"을 실행 가능한 단위로 **쪼개서** 눈앞에 늘어놓고 관리하고 싶다. 쪼개고 나면 하루에 10~20개가 나오는데, 이 규모를 부담 없이 담아둘 도구가 없다. 기존 도구는 계정 로그인, 동기화, 협업 기능까지 딸려 와서 이 용도에는 과하다. 필요한 건 **쪼갠 항목을 빠르게 넣는 속도**, **그중 뭐부터 할지 가려내는 수단**, 그리고 **지금 얼마나 했는지**다.

### 성공 기준
- 상위 할 일 하나를 3개로 쪼개는 데 마우스를 잡지 않아도 된다
- 20개를 입력하면서 우선순위와 태그까지 **키보드만으로** 붙일 수 있다
- 앱을 열자마자 3초 안에 "지금 뭐부터 해야 하는지" 파악된다
- 새로고침, 브라우저 재시작, 기기 재부팅 후에도 데이터가 그대로다

### 비목표 (v1에서 하지 않는 것)
스코프가 넘치면 완성되지 않는다. 아래는 **명시적으로 제외**한다.

- **3단계 이상 중첩** (§4 F-02 참조)
- **다중 태그 동시 필터** (AND/OR 조합)
- **태그 자동완성, 태그 이름 일괄 변경/삭제**
- 드래그로 **부모 바꾸기** (같은 형제 안에서의 순서 바꾸기는 F-19로 지원한다)
- 로그인, 계정, 서버, 데이터베이스
- 기기 간 동기화, 클라우드 백업
- 마감일, 알림, 반복 일정
- 빌드 도구, 번들러, npm 의존성

## 2. 용어

| 용어 | 정의 |
|---|---|
| **상위 할 일** | `parentId`가 `null`인 항목. 카테고리를 가진다. |
| **하위 할 일** | `parentId`가 상위 항목을 가리키는 항목. 카테고리는 상위에서 상속하되, 우선순위와 태그는 독립적으로 가진다. |
| **리프(leaf)** | 하위 할 일이 하나도 없는 항목. 하위 할 일은 항상 리프이고, 하위가 없는 상위 할 일도 리프다. |
| **문맥 행** | 태그 필터에서, 자신은 태그가 없지만 매칭된 하위를 가져서 문맥용으로만 표시되는 상위 항목. |

> **리프가 진행률의 단위다.** 상위 할 일에 하위가 붙는 순간 그 상위는 "묶음 라벨"이 되고, 실제로 세는 대상은 하위들이다. 이 규칙 하나가 §4 F-10 전체를 결정한다.

### 세 가지 분류 축의 역할 구분

셋을 한 문서에 넣으면 금방 겹치므로 역할을 못 박는다.

| 축 | 값 | 개수 | 상속 | 정렬에 영향 | 용도 |
|---|---|---|---|---|---|
| **카테고리** | 사용자가 관리 (기본 3종) | 항목당 1개 (필수) | 하위가 상위를 상속 | 없음 | 삶의 영역 구분 |
| **우선순위** | 0~3 (0이 가장 높음) | 항목당 1개 (기본 `1`) | 상속 없음 | **있음** | 순서 결정 |
| **태그** | 자유 입력 | 항목당 0~5개 | 상속 없음 | 없음 | 임의 묶기 |

## 4. 기능 요구사항

### F-01. 상위 할 일 추가

상단 입력창에 제목을 쓰고 카테고리를 골라 목록에 추가한다.

**수용 기준**
- [ ] 입력창에서 `Enter` 또는 `추가` 버튼으로 등록된다
- [ ] 등록 직후 입력창이 비워지고 **포커스가 유지**된다 (S1을 위해 필수)
- [ ] 카테고리는 직전에 선택한 값이 기본값으로 유지된다
- [ ] 제목 문자열에서 우선순위와 태그를 파싱한다 (F-05, F-07)
- [ ] 공백만 입력하면 등록되지 않고, 입력창 포커스도 그대로다 (에러 문구 없음)
- [ ] 파싱 후 제목이 100자를 넘으면 차단한다
- [ ] 새 항목은 형제 그룹 안에서 우선순위 규칙에 따라 배치된다 (F-06)

### F-02. 하위 할 일 추가

상위 할 일을 실행 단위로 쪼갠다. **깊이는 2단계까지만 허용한다.**

**수용 기준**
- [ ] 상위 항목에 마우스를 올리거나 포커스하면 `+` 버튼이 노출된다
- [ ] `+` 클릭 시 해당 상위 항목 바로 아래에 인라인 입력창이 열린다
- [ ] 입력 후 `Enter` → 하위 항목이 추가되고 **입력창이 그 자리에 유지된다** (연속 입력)
- [ ] `Esc` 또는 빈 상태로 `Enter` → 입력창이 닫힌다
- [ ] 하위 입력에서도 `!`·`#` 파싱이 동일하게 동작한다
- [ ] 하위 항목에는 `+` 버튼이 없다 (3단계 차단)
- [ ] 하위 항목은 카테고리 선택 UI가 없다 (상위에서 상속)

> **왜 2단계인가**: 저장 스키마(`parentId`)는 임의 깊이를 표현할 수 있다. 깊이를 제한하는 것은 **UI뿐**이다. 나중에 3단계가 필요해지면 렌더링과 `+` 버튼 노출 조건만 고치면 되고, 데이터 마이그레이션은 없다. 반대로 처음부터 무한 깊이를 지원하면 재귀 렌더링, 캐스케이드 삭제 범위, 진행률 집계가 전부 재귀가 되면서 "복잡하지 않게"라는 조건이 깨진다.

### F-03. 할 일 수정

**수용 기준**
- [ ] 제목을 클릭하면 인라인 편집 모드로 전환되고 텍스트가 전체 선택된다
- [ ] 편집 시 원본 제목만 보여준다 — **태그는 제목 문자열에 다시 합치지 않는다** (F-07 참조)
- [ ] `Enter`로 저장, `Esc`로 취소, 포커스가 벗어나면 저장
- [ ] 편집 중 입력한 `!`·`#`도 새로 파싱된다
- [ ] 빈 제목으로 저장하면 취소로 처리한다 (삭제하지 않는다)
- [ ] 상위/하위 항목 모두 동일하게 동작한다
- [ ] 상위 카테고리를 바꾸면 **하위 항목의 카테고리도 함께 갱신된다**
- [ ] 완료된 항목도 수정할 수 있다

### F-04. 할 일 삭제

**수용 기준**
- [ ] 각 항목의 삭제 버튼으로 즉시 삭제된다 (확인 다이얼로그 없음)
- [ ] **상위 항목 삭제 시 하위 항목도 함께 삭제된다** (캐스케이드)
- [ ] 삭제 직후 하단에 `실행 취소` 토스트가 5초간 뜬다
- [ ] 하위가 함께 삭제된 경우 토스트에 총 개수를 표시한다 — "4개 항목이 삭제됨"
- [ ] 실행 취소 시 **상위·하위의 구조, 순서, 우선순위, 태그가 전부** 복원된다
- [ ] 마지막 하위 항목을 지우면 상위 항목은 다시 리프가 된다 (진행률 분모에 다시 포함)

### F-05. 우선순위

**0 / 1 / 2 / 3** 네 단계. **0이 가장 높다.** 기본값은 `1`.

**수용 기준**
- [ ] 모든 항목이 우선순위를 가지며, 지정하지 않으면 `1`이다
- [ ] 상위와 하위는 **각자 독립적으로** 우선순위를 가진다 (상속 없음)
- [ ] 입력창 **카테고리 옆 선택 상자**로 0~3을 고른다. 직전 선택값이 유지된다
- [ ] 선택지는 **숫자만** 적는다. `가장 높음` 같은 설명은 붙이지 않는다 —
      몇 번 써 보면 알게 되는 규칙이고, 매번 읽히면 목록보다 선택 상자가 넓어진다.
      대신 `aria-label`과 도움말(F-21)이 그 사실을 알린다
- [ ] 제목 **맨 앞**의 `!` 하나는 `0`으로 해석되고 제목에서 제거된다.
      선택 상자보다 `!`가 **이긴다** — 방금 친 글자가 미리 골라둔 값보다 최근이다
- [ ] 항목의 우선순위 마커를 클릭하면 `0 → 1 → 2 → 3 → 0` 순으로 순환한다
- [ ] 우선순위 변경 즉시 형제 그룹 안에서 재정렬된다 (F-06)
- [ ] 저장값은 **숫자**다. 숫자 자체가 순위라 정렬 가중치 표를 따로 두지 않는다

**입력 규칙**

`priority`는 **지정했을 때만** 값을 가진다. `null`은 "안 적었다"는 뜻이고, 그때 무엇을 쓸지는 호출부(입력창 선택값 또는 기본값)가 정한다.

```
"!세금 신고"   → priority: 0,    title: "세금 신고"
"세금 신고"    → priority: null, title: "세금 신고"    (선택 상자 값을 쓴다)
"중요! 확인"   → priority: null, title: "중요! 확인"   (맨 앞이 아니면 무시)
"!!긴급"      → priority: 0,    title: "!긴급"        (하나만 소비)
```

낮추는 접두어는 두지 않는다. 급한 걸 빠르게 올리는 게 접두어의 목적이고, 나머지는 선택 상자와 마커 클릭으로 충분하다. 접두어가 늘수록 제목에 기호를 쓸 때 부딪힐 여지만 커진다.

> **왜 0이 가장 높은가**: 사용자가 정한 규칙이다. "1순위"라는 일상 어법과는 어긋나지만, 배열 첨자와 정렬 가중치가 그대로 일치해 코드에 변환 계층이 생기지 않는다.

> **왜 하위에 상속하지 않나**: 쪼개는 이유가 "이 중에 뭐가 급한지 가리려고"인데, 상위 우선순위를 하위가 물려받으면 그 구분이 사라진다. 카테고리는 삶의 영역이라 트리 전체가 공유하는 게 자연스럽지만, 우선순위는 실행 단위마다 다르다.

### F-06. 우선순위 기반 정렬

**형제 그룹 안에서만** 정렬한다. 트리 구조는 절대 깨지지 않는다.

```js
const compare = (a, b) => a.priority - b.priority || a.order - b.order;
```

**수용 기준**
- [ ] 상위 항목끼리는 상위 항목끼리, 하위 항목은 같은 부모의 형제끼리만 정렬된다
- [ ] 1차 기준은 우선순위, 2차 기준은 추가 순서(`order`)다
- [ ] **완료 여부는 정렬에 영향을 주지 않는다** (완료해도 제자리 유지)
- [ ] 우선순위를 바꾸면 그 자리에서 즉시 이동한다

> 완료 토글은 하루에 20번 일어나므로 항목이 움직이면 위치 기억이 깨진다. 반면 우선순위 변경은 드물게, 그리고 의도적으로 하는 동작이라 이동이 오히려 피드백이 된다. 그래서 정렬은 우선순위에만 반응한다.

### F-07. 태그

자유 입력. 카테고리는 만들고 지우는 데 한 번 손이 가지만, 태그는 제목을 치면서 그 자리에서 붙는다.

**수용 기준**
- [ ] 제목 **끝쪽에 연속으로 나열된** `#태그`만 태그로 파싱되고 제목에서 제거된다
- [ ] 태그 앞에는 반드시 공백이 있어야 한다
- [ ] 항목당 최대 5개까지 저장하고, 초과분은 버린다
- [ ] 앞뒤 공백 제거, 영문은 소문자로 정규화, 중복 제거
- [ ] 상위와 하위는 각자 독립적으로 태그를 가진다 (상속 없음)
- [ ] 태그 배지는 항목 제목 오른쪽에 표시하고, 클릭하면 해당 태그로 필터링된다

**파싱 규칙**

제목 **끝에서부터 역방향으로** `#단어`가 연속되는 구간만 태그로 본다. 이렇게 하면 제목 중간의 `#`를 태그로 오인하지 않는다.

```js
// "C# 공부 #cs #복습" → title: "C# 공부",  tags: ["cs", "복습"]
// "홈택스 입력 #세금"  → title: "홈택스 입력", tags: ["세금"]
// "C# 공부"           → title: "C# 공부",    tags: []
// "#세금"             → title: "#세금",      tags: []   (앞에 공백이 없음)

function parseTags(raw) {
  let title = raw.trim();
  const tags = [];
  const TAIL_TAG = /\s#([^\s#]+)$/;
  let m;
  while ((m = title.match(TAIL_TAG))) {
    tags.unshift(m[1]);
    title = title.slice(0, m.index).trimEnd();
  }
  return { title, tags: normalizeTags(tags) };
}
```

`#세금` 하나만 입력하면 제목이 "#세금"인 항목이 만들어진다. 제목이 비는 상황을 만들지 않기 위한 의도된 동작이다.

**편집 시 태그 처리**

인라인 편집을 열 때 태그를 제목 문자열에 다시 합치지 **않는다**. 제목만 보여주고, 편집 중 새로 `#`를 입력하면 기존 태그에 **추가**된다. 태그를 지우려면 배지의 `×`를 누른다.

> 합쳐서 보여주면 "제목만 고치려다 태그가 통째로 날아가는" 사고가 난다. 파싱은 입력 시점의 편의 기능이지, 태그의 저장 형태가 아니다.

### F-08. 카테고리 분류

처음 열면 **업무 / 개인 / 공부** 셋이 주어지고, 이후로는 사용자가 만들고 지운다.

**수용 기준**
- [ ] 모든 상위 할 일은 반드시 하나의 카테고리를 가진다 (미분류 없음)
- [ ] 하위 할 일은 상위의 카테고리를 그대로 따르며, 독립적으로 바꿀 수 없다
- [ ] 카테고리 배지는 **상위 항목에만** 표시한다
- [ ] 색상 외에 **텍스트 라벨도 함께** 표시한다
- [ ] 내부 저장값은 id, 화면 표시는 이름. 기본 3종의 id는 `work` / `personal` / `study`
- [ ] 카테고리를 만들고 지우는 방법은 F-13에 있다

### F-09. 필터

**필터는 한 번에 하나만 활성화된다.** 상태는 다음 셋 중 하나다.

```js
filter = { type: "all" }
       | { type: "category", value: "work" }
       | { type: "tag",      value: "세금" }
```

**수용 기준**
- [ ] 상단 탭: `전체` / `업무` / `개인` / `공부`
- [ ] 그 아래 태그 바에 **현재 사용 중인 태그 목록**을 미완료 개수와 함께 노출한다
- [ ] 카테고리 필터 중 태그를 클릭하면 카테고리 필터가 해제되고 태그 필터로 **전환**된다 (그 반대도 동일)
- [ ] 활성 필터를 다시 클릭하거나 `전체` 탭을 누르면 해제된다
- [ ] 카테고리 필터는 **상위 기준**으로 적용되고, 매칭된 상위는 하위와 함께 통째로 표시된다
- [ ] 태그 필터는 **항목 단위**로 매칭하되, 매칭된 하위의 상위를 **문맥 행**으로 함께 표시한다
- [ ] 문맥 행은 체크박스가 비활성이고 흐리게 표시되며, 삭제·편집 버튼이 노출되지 않는다
- [ ] 필터 상태는 새로고침 시 초기화된다 (`전체`로 복귀)
- [ ] 필터 중인 태그를 가진 항목이 0개가 되면 자동으로 `전체`로 복귀한다
- [ ] 필터 결과가 0건이면 빈 상태 문구를 보여준다

> **왜 필터를 하나만 허용하나**: 카테고리 축과 태그 축을 동시에 켜면 조합 상태가 곱으로 늘고, 빈 상태 문구·진행률 분모·자동 복귀 조건을 조합마다 정의해야 한다. 단일 필터로 두면 상태가 3종으로 끝나고, 이 규모의 앱에서 잃는 게 거의 없다. 다중 필터는 v2 후보다.

### F-10. 진행률 보기

**리프만 센다.** 상위 할 일은 하위가 있으면 분모에서 제외한다.

```
분모 = 현재 필터에 보이는 항목 중 하위가 없는 항목의 수
분자 = 그중 완료된 항목의 수
```

**수용 기준**
- [ ] 상단에 `완료 수 / 전체 수` 와 백분율을 표시한다
- [ ] 가로 프로그레스 바로 시각화한다
- [ ] **현재 필터 기준으로 계산한다** (`전체` / 카테고리 / 태그 모두 동일 규칙)
- [ ] 하위를 가진 상위 항목은 분모·분자 어디에도 포함되지 않는다 — 문맥 행도 정의상 리프가 아니므로 자동으로 제외된다
- [ ] 하위가 없는 상위 항목은 리프로 취급해 포함한다
- [ ] 우선순위와 태그는 진행률 계산에 **가중치를 주지 않는다** (모든 리프가 1개)
- [ ] 분모가 0이면 0%로 표시하고 바는 빈 상태로 둔다 (NaN 금지)
- [ ] 백분율은 소수점 없이 반올림한다
- [ ] 헤더 우측에 **남은 할 일 개수 배지**를 둔다. `전체 − 완료`이며 0이면 감춘다.
      진행률과 같은 기준(리프·현재 필터)으로 세야 나란히 놓았을 때 어긋나지 않는다

### F-11. 완료 체크와 전파

**수용 기준**
- [ ] **하향 전파**: 상위를 완료로 체크하면 하위가 전부 완료된다. 되돌리면 하위도 전부 미완료가 된다.
- [ ] **상향 전파**: 하위가 전부 완료되면 상위가 자동으로 완료된다.
- [ ] **상향 해제**: 완료 상태에서 하위 하나를 해제하면 상위도 자동으로 미완료가 된다.
- [ ] **부분 완료**: 하위 일부만 완료된 상위는 체크박스를 `indeterminate` 상태로 표시한다
- [ ] 하위가 없는 상위 항목은 일반 항목처럼 독립적으로 동작한다
- [ ] 완료 시 제목에 취소선이 그어지고 명도가 낮아진다
- [ ] 완료해도 목록에서 사라지지 않고 **제자리에 남는다**
- [ ] 전파로 상태가 바뀐 항목도 `completedAt`이 갱신된다

```js
checkbox.indeterminate = !item.completed && children.some(c => c.completed);
```

### F-12. 데이터 영속성

**수용 기준**
- [ ] 모든 변경 직후 `localStorage`에 저장한다
- [ ] 앱 로드 시 저장된 데이터를 복원한다
- [ ] 새로고침, 탭 종료 후 재접속, 브라우저 재시작 후에도 데이터가 유지된다
- [ ] 저장 실패 시 사용자에게 알린다 (§8)

### F-13. 카테고리 관리

카테고리 탭 오른쪽 톱니바퀴로 관리 패널을 연다.

**수용 기준**
- [ ] 톱니바퀴에 `aria-label="카테고리 관리"`, `aria-expanded`, `aria-controls`를 둔다
- [ ] 패널은 탭 바로 아래에 열리고, `Esc`로 닫히면 포커스가 톱니바퀴로 돌아온다
- [ ] 패널은 카테고리마다 색 점 · 이름 · 항목 수 · 삭제 버튼을 보여준다
- [ ] 이름을 입력해 추가한다. 추가 후 입력창은 비워지고 **포커스가 유지된다**
- [ ] 이름은 1~12자. 같은 이름은 거부하고 이유를 알린다 (색만으로는 구분되지 않기 때문)
- [ ] 새 카테고리의 색조는 **이미 쓰는 색들과 가장 멀리 떨어진 자리**를 자동으로 고른다
- [ ] 항목이 없는 카테고리는 확인만 받고 지운다
- [ ] 항목이 남아 있으면 **옮겨갈 카테고리를 반드시 고르게 한다**. 미분류가 없기 때문이다
- [ ] 상위를 옮기면 그 하위도 함께 따라간다
- [ ] **마지막 하나는 지울 수 없다.** 버튼을 비활성화하고 store에서도 거부한다
- [ ] 필터 중인 카테고리를 지우면 자동으로 `전체`로 복귀한다

> **왜 이름 중복을 막나**: 카테고리는 색과 이름 두 가지로 읽힌다. 색은 자동 배정이라 사용자가 고를 수 없으므로, 이름까지 같으면 배지만 보고는 어느 쪽인지 알 방법이 없다.

> **왜 삭제할 때 옮길 곳을 강제하나**: F-08의 "미분류 없음"을 지키려면 항목은 언제나 어딘가에 속해야 한다. 삭제를 막아버리면 쓸 수 없는 카테고리가 목록에 남고, 항목까지 함께 지우면 되돌릴 수 없는 손실이 된다. 옮기는 쪽이 둘 다 피한다.

### F-14. 테마 전환

우측 상단 토글 스위치로 라이트/다크를 고른다.

**수용 기준**
- [ ] 고르기 전에는 **OS 설정을 따른다**. 고른 뒤에는 OS와 무관하게 그 선택을 지킨다
- [ ] 선택은 저장되고 새로고침·재접속 후에도 유지된다
- [ ] 아직 고르지 않았다면 OS 설정이 바뀔 때 화면도 따라 바뀐다
- [ ] 토글은 `role="switch"` + `aria-checked`를 쓴다
- [ ] 팔레트는 값마다 `light-dark()`로 한 번만 적는다. 두 벌을 따로 적지 않는다

> **왜 두 벌을 적지 않나**: 라이트·다크 팔레트를 각각 나열하면 한쪽만 고치는 실수가 반복된다. `color-scheme` 하나를 바꿔 모든 `light-dark()`가 함께 뒤집히게 하면 어긋날 자리가 없다. 카테고리 배지처럼 색조가 동적인 값도 같은 방식으로 처리한다.

### F-15. 검색

입력창 아래 검색란에서 실시간으로 걸러낸다.

**수용 기준**
- [ ] 입력하는 즉시 목록이 좁혀진다 (별도 확인 동작 없음)
- [ ] **제목과 태그를 함께 본다.** 대소문자는 구분하지 않는다
- [ ] 검색어는 분류 축(전체/카테고리/태그)과 **함께** 걸린다. 서로를 해제하지 않는다
- [ ] 카테고리·태그 탭을 바꿔도 검색어는 유지된다
- [ ] 매칭된 하위의 상위는 **문맥 행**으로 함께 표시한다 (태그 필터와 같은 규칙)
- [ ] `Esc` 또는 `×` 버튼으로 검색어를 비운다
- [ ] 0건이면 `"{검색어}"에 해당하는 할 일이 없습니다.`

> **왜 검색만 다른 축과 겹치나**: F-09가 하나만 허용한 것은 카테고리와 태그, 즉 **같은 성격의 분류 축 둘**이다. 검색은 분류가 아니라 좁히기라서 어느 분류 위에도 얹힌다. "업무 중에서 세금 관련만"은 자연스러운 요구고, 이걸 막으면 검색이 반쪽이 된다.

> **주의**: 태그 필터의 자동 복귀(F-09)를 판정할 때는 **검색어를 뺀 채로** 물어야 한다. 검색 결과가 0건인 것과 그 태그를 가진 항목이 사라진 것은 다르다.

### F-16. 완료한 항목 일괄 삭제

**수용 기준**
- [ ] 완료한 항목이 하나라도 있을 때만 `완료한 항목 N개 삭제` 버튼이 보인다
- [ ] 누르면 **확인 다이얼로그**를 띄운다. 개수를 밝히고, 되돌릴 수 있다고 알린다
- [ ] 다이얼로그는 `<dialog>` + `showModal()`을 쓴다. `confirm()`을 쓰지 않는다
- [ ] `Esc`와 `취소`로 닫히고, 닫으면 아무것도 지우지 않는다
- [ ] 삭제 후 `실행 취소` 토스트가 뜨고, 되돌리면 완료 상태까지 그대로 복원된다
- [ ] 삭제 대상은 **현재 필터와 무관하다**. "모두"이므로 전체를 센다

> **왜 `confirm()`이 아닌가**: 네이티브 대화상자는 스타일을 맞출 수 없고, 자동화 도구에서 페이지 전체를 멈춰 세운다. `<dialog>`는 포커스 가둠과 `Esc`를 기본으로 주면서 앱과 같은 모양을 유지한다.

> **왜 F-04와 달리 확인을 받나**: 한 건 삭제는 실행 취소로 충분하다. 일괄 삭제는 한 번에 수십 건이 사라지고 무엇이 지워졌는지 눈으로 세기 어려워, 실행 취소만으로는 되돌릴 판단조차 하기 힘들다.

### F-17. 키보드 단축키

**수용 기준**
- [ ] `Alt+N` — 새 할 일 입력창으로 포커스를 옮기고 내용을 전체 선택한다
- [ ] `Alt+1`~`Alt+9` — 카테고리 탭을 **자리 순서대로** 전환한다 (1번은 `전체`)
- [ ] 입력 중에도 동작하되, 글자가 끼어들지 않도록 기본 동작을 막는다
- [ ] 한글 조합 중(`isComposing`)에는 반응하지 않는다
- [ ] 각 대상에 `aria-keyshortcuts`와 `title`을 달고, 입력창 도움말에도 적는다

> **왜 `key`가 아니라 `code`인가**: macOS에서 `Alt+1`은 `key`가 `¡` 같은 특수문자로 바뀐다. `code`(`Digit1`)는 자판 배열과 무관하게 그대로다.

### F-21. 도움말

화면 오른쪽 위 `?` 버튼으로 연다.

**수용 기준**
- [ ] `<dialog>` + `showModal()`을 쓴다. `Esc`와 `닫기`로 닫힌다
- [ ] 닫으면 포커스가 `?` 버튼으로 돌아온다
- [ ] 열면 `닫기` 버튼에 포커스가 간다. 스크롤 영역이 먼저 잡히면 테두리가 본문 전체를 두른다
- [ ] 내용은 정적 마크업이다. 스크립트로 만들지 않는다
- [ ] 일곱 묶음: 빠른 입력 · 우선순위 · 필터와 검색 · 정렬 · 뽀모도로 · 단축키 · 데이터
- [ ] 본문이 길면 대화상자 안에서만 스크롤한다 (`max-height` + `overflow-y`)
- [ ] 좁은 화면에서는 용어와 설명을 한 줄씩 쌓는다

### F-22. 뽀모도로 타이머

오른쪽 위 토마토 아이콘으로 열고 닫는다. 패널은 제목 줄과 진행률 게이지 사이에 나타난다.

**버튼 표기**
- [ ] 토마토는 **빨간색**이다. 팔레트 밖의 색을 하나 쓰는 유일한 자리다
- [ ] 아이콘 옆에 `뽀모도로`라고 적는다. 모양만으로는 무엇인지 단정할 수 없다
- [ ] **돌아가는 중임은 글자 쪽이 알린다.** 아이콘은 늘 빨갛게 둔다 —
      토마토가 파래지거나 초록이 되면 그건 더 이상 토마토가 아니다
- [ ] 휴식 중에는 패널과 같은 초록으로 맞춘다
- [ ] 좁은 화면에서도 글자를 지우지 않는다. 대신 헤더 간격을 좁혀 자리를 만든다

> **왜 색 규칙의 예외인가**: §7은 색을 카테고리·우선순위·중립 배경까지로 묶었다. 토마토는 그 규칙보다 "무엇인지 바로 알아보는 것"이 앞선다고 판단해 예외로 뒀다. 예외는 여기 하나뿐이고, 그래서 `--tomato` 변수 하나로만 쓴다.

**단일 타이머 수용 기준**
- [ ] 시계 아이콘 옆에 남은 시간을 `MM:SS`로 보여준다
- [ ] 미리 정해둔 길이 세 가지(25 · 5 · 15분)를 한 번에 고른다. 고른 것은 표시가 남는다
- [ ] 직접 입력으로 1~180분을 정한다. `min`/`max`/`step`을 두어 브라우저가 먼저 걸러낸다
- [ ] 시작 · 일시정지 · 계속 · 초기화. 끝난 뒤에는 `다시 시작`으로 바로 한 판 더 돌린다
- [ ] 끝나면 `00:00`을 남긴다. 끝났다는 사실이 화면에 보여야 한다
- [ ] 돌아가는 동안 문서 제목에 남은 시간을 얹는다. 배경 탭에서도 보인다
- [ ] 패널을 닫아도 돌아간다. 그때는 토마토 아이콘 색으로 알린다
- [ ] `Esc`로 패널을 닫고 포커스는 아이콘으로 돌아온다
- [ ] 끝날 때 소리를 낸다. **소리 파일을 두지 않고** 그 자리에서 만든다 (외부 요청 0건)
- [ ] 남은 시간 표시는 `role="timer"` + `aria-live="off"`.
      1초마다 읽어주면 방해만 된다. 끝났다는 안내는 토스트가 맡는다

> **왜 저장하지 않나**: 1초마다 저장하면 판 번호(`rev`)가 계속 올라가고, 그때마다 다른 탭이 전부 다시 읽는다 (F-20). 타이머는 메모리에만 두고 새로고침하면 처음으로 돌아간다. 할 일 데이터와 달리 잃어도 다시 시작하면 그만이다.

> **왜 1초씩 빼지 않나**: 끝나는 시각을 정해두고 남은 시간을 매번 다시 잰다. 배경 탭에서는 타이머가 1분에 한 번까지 느려지므로, 1초씩 빼면 돌아왔을 때 그만큼 어긋나 있다. 화면이 다시 보이는 순간에도 한 번 더 맞춘다.

**사이클 수용 기준 (F-22a)**
- [ ] `사이클` 버튼 한 번으로 1회차 집중부터 끝까지 이어서 돈다
- [ ] 네 회차를 돌고 **1회차로 되돌아온다**
- [ ] 1~3회차 뒤에는 짧은 휴식, **4회차 뒤에는 긴 휴식**이 온다
- [ ] 한 구간이 끝나면 다음 구간이 **자동으로 이어진다**. 매번 누르게 하지 않는다
- [ ] 지금 어느 구간인지 이름으로 보여준다 — `집중 2/4` · `휴식 2/4` · `긴 휴식`
- [ ] 휴식 구간은 색을 달리해 한눈에 갈라 보이게 한다
- [ ] 프리셋이나 직접 입력을 고르면 사이클에서 빠져 단일 타이머가 된다
- [ ] `초기화`는 사이클 중이면 1회차 집중으로 되돌린다
- [ ] 구간이 끝날 때 나는 소리는 **다음이 집중이면 올라가고 휴식이면 내려간다**.
      화면을 보지 않아도 무엇이 시작됐는지 알 수 있어야 한다

**회차 설정 수용 기준 (F-22b)**
- [ ] 톱니바퀴로 설정을 열고 닫는다. 회차마다 집중·휴식 시간을 분 단위로 정한다
- [ ] 회차 수는 넷으로 고정한다. 값은 1~180분
- [ ] 설정은 **저장된다**. 돌아가는 상태와 달리 자주 바뀌지 않기 때문이다
- [ ] 값 하나를 고칠 때 **다른 칸을 다시 그리지 않는다.**
      전부 새로 그리면 방금 옮겨간 칸이 교체되며 포커스와 입력하던 내용이 사라진다
- [ ] 범위 밖 값은 **직전 값으로 되돌린다.** 공장 기본값이 아니다 —
      한 칸이 잘못됐다고 손대지도 않은 값이 바뀌면 안 된다
- [ ] `기본값` 버튼으로 공장 설정(25/5 · 25/5 · 25/5 · 25/25)으로 되돌린다

**펼친 시계 수용 기준 (F-22c)**
- [ ] 화살표로 원형 시계를 열고 닫는다. 간단한 줄만 보는 상태가 기본이다
- [ ] **시간이 흐른 만큼 원이 채워진다.** 남은 시간이 아니라 지나간 시간을 그린다
- [ ] 가운데에 남은 시간과 구간 이름을 함께 둔다
- [ ] 사이클 회차 넷을 점으로 보여주고, 지난 회차와 지금 회차를 갈라 표시한다
- [ ] `Esc`는 안쪽 화면(설정 → 시계 → 패널) 순서로 하나씩 닫는다

> **왜 4단계가 아니라 세 가지인가**: 25 · 5 · 15는 뽀모도로의 집중·짧은 휴식·긴 휴식이다. 나머지는 직접 입력이 받는다.

> **왜 자동으로 이어지나**: 사이클은 "한 번 걸어두고 일에 집중한다"가 목적이다. 구간마다 눌러야 하면 25분에 한 번씩 앱으로 돌아와야 하고, 그게 바로 집중을 끊는다.

> **왜 채우는 방향인가**: 뽀모도로는 "얼마나 남았나"보다 "얼마나 했나"를 보는 기법이다. 비어가는 원은 조급함을 주고, 채워지는 원은 쌓인 것을 보여준다.

> **왜 설정만 저장하나**: 회차 길이는 한 번 정하면 오래 쓰는 값이라 저장할 값어치가 있다. 반대로 돌아가는 상태는 1초마다 바뀌어서, 저장하면 판 번호가 계속 올라가고 다른 탭이 그때마다 다시 읽는다 (F-20).

> **무엇을 넣나**: "써 보면 아는 것"은 넣지 않는다. 넣는 건 **써 봐도 모르는 것**이다 — 타이핑 접두어, 단축키, `0이 가장 높다`, 진행률이 하위만 세는 이유, 끌기가 직접 순서에서만 되는 이유, 데이터가 이 브라우저에만 있다는 사실. 화면에 단서가 없는 규칙만 모은다.

**문체 — 사용자에게 말하듯 쓴다**

도움말은 §7 마이크로카피 규칙("버튼은 실행 결과를 그대로 말한다")의 연장이지만, 짧게 자르는 것보다 **한 문장을 끝까지 맺는 것**이 먼저다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| 넣습니다 · 답니다 · 붙입니다 | **추가합니다** |
| 이깁니다 · 잡힙니다 · 걸립니다 | **관계 없이 적용됩니다** · **선택할 수 있습니다** |
| 한 항목에 5개까지. | **항목당 5개까지 추가할 수 있습니다.** |
| 옆에서 고른 값 | **우측에 선택된 우선순위** |
| 추려 보기 · 빠르게 적기 | **필터와 검색** · **빠른 입력** |

- **명사로 끊지 않는다.** "5개까지."처럼 서술어 없이 멈추면 메모처럼 읽힌다
- **은유와 압축을 쓰지 않는다.** "이깁니다", "손잡이가 잡힙니다"는 짧지만 한 번 더 해석해야 한다
- **위치는 화면에 보이는 대로 부른다.** "옆에서"가 아니라 "우측에"
- **설명이 길어지면 지운다.** `+` 버튼 설명은 "하위 할 일을 추가합니다." 한 줄이면 된다.
  깊이 제한 같은 건 부딪혀 봐야 알게 되는 것이지, 미리 읽을 내용이 아니다

### F-18. 내보내기 / 가져오기

**수용 기준**
- [ ] `내보내기` — 저장 형식 그대로를 JSON 파일로 내려받는다. 파일명은 `my-task-YYYY-MM-DD.json`
- [ ] 날짜는 **로컬 기준**이다. `toISOString()`은 UTC라 한국 오전에는 하루 전으로 찍힌다
- [ ] `가져오기` — 파일을 고르면 **덮어쓰기 전에** 확인 다이얼로그를 띄운다
- [ ] 다이얼로그는 `취소` / `그냥 가져오기` / **`백업 후 가져오기`** 셋을 준다
- [ ] `백업 후 가져오기`는 현재 데이터를 먼저 내려받은 뒤 교체한다
- [ ] 가져온 데이터는 **로드와 같은 검증 파이프라인**을 탄다 (§8)
- [ ] JSON이 아니거나 `todos` 배열이 없으면 거부하고 이유를 알린다. 기존 데이터는 그대로 둔다
- [ ] 가져온 뒤 필터·검색어를 초기화한다. 예전 필터가 가리키던 것이 없을 수 있다
- [ ] 외부로 아무것도 보내지 않는다. `Blob` + `URL.createObjectURL`로 브라우저가 저장한다

> **왜 백업을 권하나**: 가져오기는 이 앱에서 유일하게 **실행 취소가 없는** 동작이다. 전부를 한 번에 갈아치우므로 토스트 한 줄로 되돌릴 수 있는 규모가 아니다. 되돌릴 수 없으면 되돌릴 재료를 먼저 쥐여주는 게 맞다.

### F-19. 정렬 옵션

필터 줄 오른쪽 선택 상자로 고른다. **어느 모드에서도 형제 그룹 안에서만 정렬한다.**

| 모드 | 기준 |
|---|---|
| **우선순위순** (기본) | F-06 그대로. 우선순위 1차, `order` 2차 |
| 직접 순서 | `order`만. 끌어서 옮길 수 있는 유일한 모드 |
| 생성일순 | `createdAt` |
| 카테고리순 | 카테고리 목록의 순서 |
| 완료상태순 | 미완료 먼저 |

**수용 기준**
- [ ] 고른 모드는 저장되고 새로고침 후에도 유지된다
- [ ] 트리 구조는 어느 모드에서도 깨지지 않는다
- [ ] **직접 순서 모드에서만** 끌기 손잡이가 잡힌다
- [ ] 손잡이 자리는 모든 모드에서 유지한다. 모드를 바꿀 때 목록 왼쪽이 흔들리면 안 된다
- [ ] 끌어 놓기는 **같은 부모의 형제 사이에서만** 된다. 부모가 바뀌는 이동은 거부한다
- [ ] 놓일 자리를 선으로 미리 알린다
- [ ] 마우스 없이 `Alt+↑` / `Alt+↓`로도 옮긴다. 옮긴 뒤 포커스는 그 항목에 남는다

> **왜 드래그를 직접 순서 모드로 제한하나**: 다른 모드에서는 정렬 기준이 자리를 다시 정한다. 우선순위순에서 낮음 항목을 맨 위로 끌어 놓으면 놓는 순간 제자리로 튕긴다. 사용자가 한 일이 취소되는 것처럼 보이므로, 손으로 정한 순서가 그대로 남는 모드에서만 잡히게 했다.

> **왜 부모를 바꾸지 못하게 하나**: 부모가 바뀌면 캐스케이드 삭제 범위, 진행률 분모(리프 판정), 완료 전파 대상이 한꺼번에 달라진다. 순서 바꾸기는 `order` 하나만 건드리므로 이 셋 중 어느 것도 흔들리지 않는다.

### F-20. 여러 탭에서 열었을 때

같은 앱을 두 탭에서 열어두면, 한쪽이 통째로 저장하면서 다른 쪽의 작업을 덮어쓸 수 있다. **두 겹으로 막는다.**

**1겹 — 따라가기.** 다른 탭이 저장하면 `storage` 이벤트가 온다. 받는 즉시 다시 읽어 화면을 맞춘다.

**2겹 — 쓰기 직전 확인.** 저장본에 판 번호(`rev`)를 둔다. 쓰기 직전에 저장소를 다시 읽어, 우리가 마지막으로 본 `rev`와 다르면 **쓰지 않고 물러난다.**

**수용 기준**
- [ ] 다른 탭의 저장을 받으면 곧바로 다시 읽어 화면을 맞춘다
- [ ] 그때 편집·하위 입력·되돌리기 토스트는 접는다. 없어진 항목을 가리킬 수 있다
- [ ] 낡은 상태에서 쓰기를 시도하면 **거부하고 되돌린 뒤** 최신을 읽어온다
- [ ] 거부됐을 때 사용자가 입력한 내용은 그대로 둔다. 다시 누르면 되게 한다
- [ ] `rev`는 내보내기에 넣지 않는다. 가져온 파일에는 없는 값이다
- [ ] 메모리 폴백(저장 불가 환경)에서는 다른 탭이 없으므로 늘 통과한다

> **왜 이벤트만으로는 부족한가**: `storage` 이벤트는 비동기다. A가 쓰고 B에게 이벤트가 닿기 전에 B가 먼저 쓰면 A의 저장이 사라진다. 이벤트는 "평소에 맞춰두는" 장치고, 실제로 손실을 막는 건 쓰기 직전의 `rev` 확인이다.

> **왜 병합하지 않나**: 두 탭의 변경을 합치려면 항목 단위 타임스탬프와 충돌 해소 규칙이 필요하다. 1인용 단일 기기 앱에서 그 복잡도를 지불할 이유가 없다. 거부하고 최신을 보여준 뒤 다시 하게 하는 편이 예측 가능하다.

## 5. 데이터 모델

### 항목 스키마

트리를 중첩 객체로 저장하지 않고 **평평한 배열 + `parentId`**로 저장한다.

```js
{
  id:          "018f2a...",   // string, 고유 ID
  parentId:    null,          // null이면 상위 할 일, 아니면 상위 항목의 id
  title:       "홈택스 입력",   // string, 1~100자 (태그·우선순위 접두어 제거 후)
  category:    "work",         // string, 카테고리 id (하위는 상위 값 복사)
  priority:    1,              // 0~3. 0이 가장 높다. 기본 1
  tags:        ["세금"],        // string[], 0~5개
  completed:   false,          // boolean
  createdAt:   1754179200000,  // number, Date.now()
  completedAt: null,           // number | null
  order:       0               // number, 같은 parentId 안에서의 추가 순서
}
```

`priority`는 숫자이고 그 값이 곧 순위다. 정렬 가중치 표가 따로 없어 단계를 늘려도 비교자를 고칠 필요가 없다. v2까지 쓰던 `"high"`/`"normal"`/`"low"`는 로드 시 `0`/`1`/`2`로 옮긴다.

`order`는 정렬의 **2차 기준**으로만 쓰인다. 화면 순서는 `priority` → `order` 조합으로 매번 계산한다.

### 카테고리 스키마

```js
{
  id:   "work",   // string, 고유 ID. 기본 3종만 읽기 쉬운 고정값을 쓴다
  name: "업무",    // string, 1~12자. 목록 안에서 유일해야 한다
  hue:  221       // number, 0~359. 채도·명도는 CSS가 정하고 색조만 여기서 온다
}
```

색을 `#2563eb` 같은 완성된 값이 아니라 색조 하나로 저장하는 이유: 라이트·다크 두 벌을 각각 저장하면 어긋나기 시작한다. 색조만 데이터로 두고 채도·명도는 테마마다 한 곳에서 정하면 카테고리가 몇 개로 늘어나도 톤이 흐트러지지 않는다.

### store가 제공해야 하는 조회 헬퍼

```js
Store.getRoots(filter)               // 필터 적용 + 정렬된 상위 항목
Store.getChildren(parentId, filter)  // 해당 부모의 자식, 정렬 적용.
                                     //   filter를 생략하면 전부 — indeterminate 판정처럼
                                     //   "보이는 것"이 아니라 "실제 자식 전부"가 필요한 곳이 있다
Store.isLeaf(id)                     // 자식이 0개인가
Store.getStats(filter)               // { done, total, percent } — 리프 기준
Store.getAllTags(filter)             // [{ tag, openCount }] — 태그 바용
Store.getDescendants(id)             // 캐스케이드 삭제·복원용
Store.isContextRow(id, filter)       // 태그 필터에서 문맥 행인가
Store.getCategories()                // 카테고리 목록 (복사본)
Store.countInCategory(id)            // 그 카테고리의 항목 수 (상위·하위 모두)
Store.countCompleted()               // 완료한 항목 수 — 지우기 전에 물어보려면 필요하다
Store.getItem(id)                    // id로 항목 하나. 색인을 쓰므로 상수 시간
Store.getTheme()                     // "light" | "dark" | null
Store.getSort()                      // 현재 정렬 모드
Store.exportData()                   // 저장 형식 그대로의 객체 (rev는 뺀다 — 내부 토큰이다)
Store.lastError                      // "conflict" | "save" | null — 변경이 null을 줬을 때의 이유
Store.STORAGE_KEY                    // UI가 storage 이벤트를 걸러낼 때만 쓴다
```

**색인**: `find` / `childrenOf` / `hasChildren`는 매번 배열을 훑지 않고 `Map` 두 개(`byId`, `parentId → 자식들`)를 쓴다. 없으면 질의가 O(n²)이 되어 1000개에서 눈에 띈다. 구조가 바뀌는 자리마다 색인을 버리고 다음 질의에서 다시 만든다.

### 필터 모양

```js
filter = {
  type:  "all" | "category" | "tag",   // 분류 축 — 한 번에 하나
  value: "work",                        // category / tag일 때만
  query: "세금"                          // 검색어 — 어느 축에도 함께 얹힌다
}
```

### store가 제공해야 하는 변경 API

```js
Store.load() / save()
Store.add(parsed, categoryId) / addChild(parentId, parsed)
Store.update(id, patch) / remove(id) / toggle(id)
Store.restore(items)                 // remove()가 돌려준 항목을 그대로 되살린다 (F-04 실행 취소)
Store.addCategory(name)              // 색조는 store가 자동으로 고른다
Store.removeCategory(id, moveToId)   // 항목이 남아 있으면 moveToId가 필수
Store.removeCompleted()              // 완료한 항목 일괄 삭제. 되돌리기용 배열을 돌려준다
Store.setTheme("light" | "dark" | null)
Store.setSort(mode)                  // F-19의 다섯 가지 중 하나
Store.reorder(id, beforeId)          // 형제 그룹 안에서만. beforeId가 null이면 맨 뒤
Store.importData(parsed)             // load와 같은 검증을 태워 통째로 교체
```

변경 API는 저장에 실패하면 **변경 전체를 되돌리고 `null`을 준다.** 호출부는 `null`을 "저장하지 못했다"로 읽는다 (§8 참조).

### 저장 형식

- **키**: `daily-todo:v1` (스키마가 바뀌어도 키는 하나만 쓴다)
- **값**: 아래 객체를 `JSON.stringify()` 한 문자열

```js
{
  version: 4,
  rev:        7,                   // 판 번호. 쓸 때마다 1씩 오른다 (F-20)
  theme:      "dark",              // "light" | "dark" | null (null이면 OS를 따름)
  sort:       "priority",          // 정렬 모드 (F-19)
  pomodoro:   [ /* 회차별 { focus, rest } 넷 (F-22) */ ],
  categories: [ /* 카테고리 배열 */ ],
  todos:      [ /* 항목 배열 (평평한 구조) */ ]
}
```

테마도 이 안에 넣는다. 키를 하나만 쓴다는 규칙을 지키면서 저장 실패 롤백과 메모리 폴백을 그대로 물려받는다.

**v1 → v2 이관**: `categories`가 없는 저장본은 기본 3종을 채워 넣고 시작한다. 기본 3종의 id가 v1의 카테고리 값과 같으므로 항목은 그대로 이어진다.

**v3 → v4 이관**: `pomodoro`가 없으면 기본 사이클(25/5 · 25/5 · 25/5 · 25/25)을 채운다. 덧붙이는 값이라 옮길 것이 없다.

**v2 → v3 이관**: `priority` 문자열을 숫자로 옮긴다 — `high`→`0`, `normal`→`1`, `low`→`2`. 알 수 없는 값은 `1`이다. 세 단계가 네 단계의 앞자리로 그대로 들어가므로 순서가 뒤집히지 않는다.

이관 결과를 로드 시점에 되쓰지는 않는다 — 다음 변경이 일어날 때 함께 저장된다.

## 6. 기술 요구사항

### 스택
- HTML + CSS + 순수 JavaScript (ES2020+)
- 프레임워크, 빌드 도구, npm 패키지 **없음**
- 저장소: `localStorage`

### 파일 구조

```
daily-todo/
├── index.html
├── styles.css
├── parse.js    # 제목 문자열 → { title, priority, tags }. 순수 함수만.
├── store.js    # 데이터 계층: 로드/저장/CRUD/전파/정렬/집계. DOM을 모른다.
└── app.js      # UI 계층: 렌더링 + 이벤트. store와 parse만 호출한다.
```

`index.html`에서 `parse.js` → `store.js` → `app.js` 순서로 일반 `<script>` 태그로 로드한다.

> **`type="module"`을 쓰지 않는 이유**: ES 모듈은 `file://` 프로토콜에서 CORS 정책에 막힌다. 일반 스크립트 태그를 쓰면 `index.html`을 더블클릭하는 것만으로 앱이 실행된다. 로컬 서버가 필요하면 `python -m http.server` 로 충분하다.

**`parse.js`를 따로 두는 이유**: 입력 파싱은 순수 함수라 콘솔에서 바로 검증할 수 있다. 우선순위·태그 규칙은 엣지 케이스가 가장 많은 부분인데, store나 UI에 섞여 있으면 확인하기 번거롭다. 분리해두면 M6·M7을 파싱 → 저장 → 표시 순으로 하나씩 확인하며 붙일 수 있다.

**완료 전파와 정렬은 store 안에서 끝낸다.** UI는 `Store.getRoots(filter)`가 돌려준 순서대로 그리기만 한다.

### 렌더링 전략

상태가 바뀌면 목록 전체를 다시 그린다. 항목 20개 규모에서는 diff 알고리즘이 불필요하다.

- 깊이가 2단계로 고정이므로 **재귀 없이 2중 루프**로 렌더링한다
- 이벤트는 목록 컨테이너 하나에 **이벤트 위임**으로 붙인다
- 각 DOM 노드에 `data-id`를 심고, `closest('[data-id]')`로 대상을 찾는다
- 액션은 `data-action` 속성으로 구분한다 (`toggle` / `edit` / `delete` / `add-child` / `cycle-priority` / `remove-tag` / `filter-tag` / `filter-category` / `remove-category` / `confirm-remove-category` / `cancel-remove-category`)
- 인라인 편집 중이거나 하위 입력창이 열려 있을 때는 재렌더를 건너뛴다 (포커스 유실 방지)

### 브라우저 지원
최신 버전의 Chrome, Edge, Safari, Firefox.


### 우선순위 표현 — 숫자를 그대로 보여준다

네 단계를 색이나 굵기만으로 구분시키면 읽을 수 없다. 사용자가 0~3으로 고르는 값이므로 **그 숫자가 곧 표시다.**

| 단계 | 표현 |
|---|---|
| 0 | 3px 세로 바(accent) + 숫자를 accent 색으로 + 제목 굵게 |
| 1 | 숫자만 (흐린 색) |
| 2 | 숫자 + 제목 명도를 낮춤 |
| 3 | 숫자를 더 흐리게 + 제목 명도를 낮춤 |

취소선은 어느 단계에도 쓰지 않는다 — 완료와 헷갈린다.

한눈에 걸려야 하는 건 `0` 하나뿐이라 세로 accent 바는 0에만 세운다. 나머지는 숫자가 조용히 알려주면 된다.

마커 영역은 모든 단계에서 **같은 자리를 차지한다**. 클릭으로 순환시켜야 하므로 히트 영역이 필요하고, 자리가 들쭉날쭉하면 목록 왼쪽 정렬이 흔들린다.

### 태그 표현
- 제목 오른쪽에 작은 배지, 카테고리 배지보다 **약한 대비**로 (카테고리가 1차 축)
- 태그에는 색을 쓰지 않는다 — 색은 카테고리 전용이다
- 배지에 마우스를 올리면 `×`가 나타나 개별 삭제
- 3개를 넘으면 `+2` 로 접고, 항목에 포커스하면 전부 펼친다

### 계층 표현
- 하위 항목은 왼쪽으로 **24px 들여쓰기**, 상위-하위를 잇는 1px 세로 연결선
- 하위 항목의 폰트 크기는 상위와 동일, **굵기만 낮춘다**

### 상태별 화면

| 상태 | 표시 |
|---|---|
| 할 일이 하나도 없음 | "아직 할 일이 없습니다. 위에 입력해서 시작하세요." |

### 입력창 도움말
접두어 규칙은 발견되지 않으면 없는 기능이다. 입력창 `placeholder` 아래에 한 줄로 상시 노출한다.

> `!`로 시작하면 우선순위 0, 끝에 `#태그`

**여기에는 타이핑 규칙 둘만 남긴다.** 화면을 보고는 알 수 없는 건 이 둘뿐이다. 단축키를 비롯한 나머지는 도움말(F-21)로 옮긴다 — 힌트 줄이 길어지면 아무도 읽지 않는다.

### 마이크로카피 규칙
- 버튼은 실행 결과를 그대로 말한다 — `추가`, `삭제`, `실행 취소`
- 에러는 사과하지 않고, 무엇이 잘못됐고 어떻게 고치는지 말한다
- 빈 화면은 안내가 아니라 행동 유도다

### 스타일 방향
- 카테고리 색 + 우선순위 accent 1종 + 중립 배경. 그 외에 색을 늘리지 않는다
- 카테고리 색은 개수가 정해져 있지 않다. **색조만 카테고리마다 받고 채도·명도는 테마별로 한 번만 정한다.** 그래야 개수가 늘어도 톤이 흐트러지지 않는다
- `prefers-color-scheme` 으로 다크 모드 자동 대응
- 모바일 폭(360px)까지 대응. 좁은 화면에서는 들여쓰기 16px, 태그는 1개만 표시하고 나머지는 접는다

## 8. 엣지 케이스와 예외 처리

### 파싱

| 상황 | 처리 |
|---|---|
| `#` 뒤가 비어 있음 (`"할 일 #"`) | 태그로 보지 않는다. 제목에 그대로 남긴다 |
| 태그 6개 이상 | 앞에서부터 5개만 저장, 나머지는 버린다 (경고 없음) |
| 제목 중간의 `#` (`"C# 공부"`) | 태그 아님. 끝에서 역방향 연속 구간만 파싱 |
| 파싱 후 제목이 빔 | 등록 거부, 입력창 내용과 포커스 유지 |
| 제목 맨 앞 `!` 여러 개 | 하나만 소비, 나머지는 제목에 남는다 |
| 태그 대소문자·공백 차이 | 정규화 후 중복 제거 (`#Tax`, `#tax ` → `tax` 하나) |

### 계층·상태

| 상황 | 처리 |
|---|---|
| **고아 항목** (`parentId`가 가리키는 부모가 없음) | 로드 시 `parentId`를 `null`로 바꿔 상위로 승격 |
| **3단계 이상 데이터** | 로드 시 손자 이상은 상위로 승격해 2단계로 평탄화 |
| **순환 참조** (A→B→A) | 로드 검증 시 감지해 해당 항목들을 상위로 승격 |
| **문맥 행에 대한 조작 시도** | 체크박스·버튼이 비활성이므로 발생하지 않는다. 이벤트 위임 핸들러에서도 한 번 더 막는다 |
| **필터 중인 태그의 마지막 항목 삭제** | 자동으로 `전체` 필터로 복귀 |
| **필터 중인 카테고리 삭제** | 자동으로 `전체` 필터로 복귀 |
| **전파 도중 저장 실패** | 전파 전 상태 전체를 롤백 (부분 적용 금지) |
| **`priority`가 0~3 밖이거나 알 수 없는 값** | 로드 시 `1`로 교정. 옛 문자열은 숫자로 옮긴다 |
| **`tags`가 배열이 아님** | 로드 시 빈 배열로 교정 |

### 카테고리

| 상황 | 처리 |
|---|---|
| **항목의 `category`가 없는 카테고리를 가리킴** | 항목을 버리지 않고 첫 번째 카테고리로 옮긴다. 카테고리는 지워질 수 있으므로 이 값의 불일치는 손상이 아니다 |
| **`categories`가 없는 저장본 (v1)** | 기본 3종을 채우고 시작한다. id가 같아 항목은 그대로 이어진다 |
| **`categories`를 하나도 못 살림** | 기본 3종으로 되돌린다. 미분류 상태를 만들지 않는다 |
| **`hue`가 없거나 숫자가 아님** | 0으로 교정 |
| **이름이 12자 초과** | 로드 시 잘라내고, 입력 시에는 거부하고 이유를 알린다 |
| **같은 이름으로 추가 시도** | 거부한다. 색은 자동 배정이라 이름까지 같으면 구분할 방법이 없다 |
| **마지막 카테고리 삭제 시도** | 거부한다. 버튼도 비활성이고 store도 `null`을 준다 |
| **항목이 남은 카테고리 삭제** | 옮겨갈 카테고리 없이는 거부한다. UI가 먼저 물어본다 |
| **카테고리 변경 중 저장 실패** | 항목과 카테고리를 함께 롤백 (부분 적용 금지) |
| **테마 변경 중 저장 실패** | 테마도 함께 롤백. 화면은 되돌아간 값으로 다시 칠한다 |

### 검색·테마·단축키

| 상황 | 처리 |
|---|---|
| **검색 중에 태그 필터의 항목이 0건** | 자동 복귀를 판정할 때 검색어를 뺀다. 검색 결과 0건으로 태그 필터가 풀리면 안 된다 |
| **검색어가 공백뿐** | 앞뒤를 다듬은 뒤 비었으면 검색하지 않는 것으로 본다 |
| **검색 중 카테고리·태그 전환** | 검색어는 그대로 유지된다 |
| **저장된 `theme`이 알 수 없는 값** | `null`로 보고 OS 설정을 따른다 |
| **이미 열린 다이얼로그에 다시 `showModal()`** | 예외가 난다. 열려 있으면 아무것도 하지 않고 빠진다 |
| **한글 조합 중 단축키** | `isComposing`이면 반응하지 않는다 |
| **`Alt+숫자`가 가리키는 탭이 없음** | 아무것도 하지 않는다 (기본 동작도 막지 않는다) |
| **타이머가 도는 중 새로고침** | 타이머는 사라진다. 저장하지 않기로 한 결과다 (F-22). 회차 설정은 남는다 |
| **회차 설정에 범위 밖 값** | 직전 값으로 되돌린다. 공장 기본값으로 가지 않는다 |
| **`pomodoro`가 없거나 망가진 저장본** | 모자란 자리만 기본값으로 채운다 |
| **배경 탭에서 인터벌이 느려짐** | 끝나는 시각으로 다시 재고, 화면이 보일 때 한 번 더 맞춘다 |
| **소리를 낼 수 없는 환경** | 조용히 넘어간다. 토스트와 `00:00`으로 끝났다는 건 남는다 |
| **hover가 없는 기기(터치)** | 스치듯 드러나는 버튼(`+`, 삭제, 끌기 손잡이, 태그 `×`)을 숨기지 않는다. 숨기는 규칙은 `@media (hover: hover) and (pointer: fine)` 안에만 둔다 |

### 내보내기·가져오기·정렬

| 상황 | 처리 |
|---|---|
| **JSON이 아닌 파일** | 거부하고 "JSON 파일이 아닙니다"라고 알린다. 기존 데이터는 그대로 |
| **구조가 다른 JSON** | `todos` 배열이 없으면 거부한다 |
| **가져온 데이터가 깨져 있음** | 로드와 같은 검증을 탄다 — 고아 승격, 깊이 평탄화, `priority`·`tags`·`category` 교정 |
| **가져오기 도중 저장 실패** | 가져오기 전 상태로 통째로 되돌린다 |
| **같은 파일을 다시 고름** | `input.value`를 비워 `change`가 다시 오게 한다 |
| **저장된 `sort`가 알 수 없는 값** | `priority`로 교정한다 |
| **형제가 아닌 곳에 끌어 놓음** | 거부한다. `dragover`에서 미리 막고 `reorder`도 다시 확인한다 |
| **자기 자신 위에 놓음** | 아무것도 하지 않는다 |

### 저장·환경

| 상황 | 처리 |
|---|---|
| `localStorage` 접근 불가 (시크릿 모드, 브라우저 차단) | 메모리 배열로 폴백해 앱은 정상 동작. 상단 경고 배너 |
| JSON 파싱 실패 (데이터 손상) | `daily-todo:v1:corrupted` 로 옮기고 빈 목록으로 시작. 배너 안내 |
| `QuotaExceededError` | 마지막 변경을 롤백하고 "저장하지 못했습니다" 알림 |
| 스키마 필드 누락/타입 불일치 | 항목 단위로 검증. 불량 항목만 버리고 나머지는 살린다 |
| 같은 앱을 여러 탭에서 열어둠 | **덮어쓰지 않는다.** F-20 참조 |
| `crypto.randomUUID` 미지원 | §5의 폴백 사용 |
| 제목·태그·카테고리 이름에 HTML/스크립트 삽입 | `textContent`로만 렌더링. `innerHTML` 금지 |
| 항목 100개 이상 | 전체 재렌더로도 문제없음. 500개 넘으면 그때 대응 |

**로드 시 검증 순서**: **카테고리 목록 확정** → 스키마 검증 → `priority`·`tags` 교정 → 순환 참조 제거 → 고아 승격 → 깊이 평탄화 → 카테고리 상속 재확인 + `order` 재정렬. 이 순서를 지켜야 뒤 단계가 앞 단계의 결과를 신뢰할 수 있다. 카테고리가 맨 앞인 이유는 항목의 `category` 검증이 그 목록을 기준으로 돌아가기 때문이다.

**소스 파일에 제어 문자를 남기지 않는다.** `Map` 키 구분자 같은 데 `'\u0000...'`를 쓰면 원시 NUL 바이트가 파일에 박히고, `grep`·`file`이 그 파일을 바이너리로 취급해 정적 검사가 조용히 아무것도 못 찾고 지나간다. `Map`은 `null`을 그대로 키로 받으므로 구분자가 필요 없다.

## 9. 비기능 요구사항

**성능**
- 초기 로드 200ms 이내, 토글/추가 반응 16ms 이내 (항목 100개 기준)
- 조회는 **색인(`Map`)으로 선형**을 유지한다. 배열을 항목마다 훑으면 O(n²)이 되어 1000개에서 무너진다
- 화면 갱신은 전체 재렌더로 둔다. 색인을 넣은 뒤로는 DOM 재구성이 지배적이고, 그마저 선형이다
- 외부 폰트·이미지·CDN 요청 0건 → 오프라인에서도 동작

**접근성**
- 완료 체크는 실제 `<input type="checkbox">` 사용 (`indeterminate` 때문에 더욱 그렇다)
- 계층은 `<ul>` 안에 `<ul>`을 중첩해 마크업으로 표현한다
- 모든 인터랙션이 키보드만으로 가능하고, 포커스 링이 보인다
- 우선순위는 마커에 **숫자를 직접 그린다**. 색·굵기만으로 네 단계를 구분시키지 않는다
- 우선순위 순환 버튼에 `aria-label="우선순위 변경: {제목}, 현재 0 (가장 높음)"`
- 태그 배지는 `<button>`으로 만들고 `aria-label="태그 필터: 세금"`
- 하위 추가 버튼에 `aria-label="하위 할 일 추가: {상위 제목}"`
- 삭제 버튼에 `aria-label="삭제: {제목}"`
- 진행률 바에 `role="progressbar"` + `aria-valuenow`
- 문맥 행에 `aria-disabled="true"`
- 토스트는 `aria-live="polite"`
- 카테고리 관리 버튼에 `aria-label="카테고리 관리"` + `aria-expanded` + `aria-controls`
- 카테고리 삭제 버튼에 `aria-label="카테고리 삭제: {이름}"`, 옮길 곳 선택에 `aria-label="{이름}의 항목을 옮길 카테고리"`
- 카테고리 색 점은 장식이다. 이름을 반드시 함께 쓴다 (색만으로 구분되지 않게)
- 테마 토글은 `role="switch"` + `aria-checked`. 남은 할 일 배지는 `aria-live="polite"`
- 도움말 버튼에 `aria-label="도움말"` + `aria-haspopup="dialog"`
- 뽀모도로 버튼에 `aria-label="뽀모도로"` + `aria-expanded` + `aria-controls`.
  보이는 글자와 접근 이름을 같게 둔다 — 음성으로 조작할 때 부르는 이름이 달라지면 안 된다
- 시계 펼치기·설정 버튼도 `aria-expanded` + `aria-controls`를 가진다.
  펼치기 버튼의 `aria-label`은 상태에 따라 `시계 펼치기` ↔ `시계 접기`로 바뀐다
- 회차 설정의 입력 칸마다 `aria-label`을 둔다 — `2회차 집중 시간(분)`
- 숫자만 적힌 선택지는 `aria-label`이 뜻을 채운다 — `우선순위 (0이 가장 높음)`
- 확인 다이얼로그는 `<dialog>` + `showModal()` — 포커스 가둠과 `Esc`를 브라우저가 맡는다
- 단축키 대상에 `aria-keyshortcuts`를 단다 (`Alt+N`, `Alt+1`~`Alt+9`)
- **끌어 놓기에는 반드시 키보드 대안을 둔다.** 손잡이에 `Alt+↑`/`Alt+↓`를 걸고
  `aria-label`로 그 사실을 알린다. 드래그만 있으면 마우스 없이는 순서를 못 바꾼다
- **삭제 직후 `실행 취소`에 키보드로 닿을 수 있어야 한다.** 지운 행이 사라지면서 포커스도 없어지는데 토스트는 DOM 맨 끝이라 Tab으로는 5초 안에 도착하기 어렵다. 키보드로 지운 경우(`e.detail === 0`)에는 실행 취소 버튼으로 포커스를 옮기고, 토스트가 닫힐 때 포커스가 그 안에 있었으면 입력창으로 되돌린다

## 10. 개발 마일스톤

각 단계는 **그 자체로 동작하는 앱**으로 끝난다. 중간에 멈춰도 쓸 수 있는 상태여야 한다.

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| **M1** | `store.js` — 로드/저장/CRUD + `parentId`·`priority`·`tags` 필드 + 조회 헬퍼 | 콘솔에서 트리를 만들고 새로고침해도 살아있다 |
| **M2** | 평평한 목록 렌더 + 상위 추가 + 완료 토글 (계층·우선순위·태그 표시 없음) | 화면에서 추가하고 체크할 수 있다 |
| **M3** | 계층 렌더링 + 하위 추가 + 완료 전파 | 쪼개기가 화면에서 된다. 상위/하위 체크가 맞물린다 |
| **M4** | 인라인 수정 + 캐스케이드 삭제 + 실행 취소 | CRUD가 전부 화면에서 된다 |
| **M5** | 카테고리 필터 + 리프 기준 진행률 | 필터 인프라와 집계가 완성된다 |
| **M6** | `parse.js` 우선순위 파싱 + 정렬 + 시각 표현 + 순환 클릭 | `!`로 입력한 항목이 위로 올라온다 |
| **M7** | `parse.js` 태그 파싱 + 태그 배지 + 태그 바 + 태그 필터 + 문맥 행 | `#`로 붙인 태그로 추려 볼 수 있다 |
| **M8** | 엣지 케이스, 빈 상태, 접근성, 반응형 | §8 표의 항목이 전부 처리됐다 |

> **순서에 관한 두 가지 원칙.**
> **M2를 계층 없이 끝낸다** — store에는 이미 모든 필드가 있지만 화면은 평평하게 그린다. M2 끝에서 이미 쓸 수 있는 앱이 나오고, M3은 렌더링 교체 하나로 좁혀진다.
> **M6·M7을 M5 뒤에 둔다** — 태그 필터는 M5에서 만든 필터 상태 기계를 재사용한다. 필터가 없는 상태에서 태그를 먼저 붙이면 "태그는 달았는데 쓸 데가 없는" 구간이 생기고, 나중에 필터를 넣으면서 태그 표시를 다시 고치게 된다.

## 12. 확인이 필요한 결정

착수 전에 답이 필요한 항목들이다. 기본 가정은 명시해뒀다.

1. **누적인가, 매일 리셋인가?**
   기본 가정 = **누적**. 완료 항목도 목록에 남고 직접 지운다.
   매일 초기화되는 개념이라면 `dueDate` 필드와 자정 롤오버 처리가 필요하고, 계층이 붙은 지금은 "부모는 어제 건데 자식은 오늘 것" 같은 경우까지 정의해야 해서 스코프가 크게 늘어난다.

2. ~~**우선순위 3단계로 충분한가?**~~ → **결정됨 (v1.6)**: 부족하다고 판단해 **0~3 네 단계**로 늘리고 입력창에 선택 상자를 두었다. 0이 가장 높다.

3. **태그를 상위에 붙였을 때 하위도 그 태그로 필터에 걸려야 하나?**
   기본 가정 = **아니오**. 상위만 걸리고, 하위는 하위대로 자기 태그로 걸린다.
   상속시키면 태그가 카테고리와 역할이 겹치기 시작한다.

4. **깊이 2단계로 충분한가?**
   기본 가정 = **2단계**. 스키마는 임의 깊이를 표현할 수 있어 나중에 UI만 고쳐 확장 가능하다.

5. ~~**카테고리 3개로 충분한가?**~~ → **결정됨 (v1.3)**: 부족하다고 판단해 사용자가 직접 만들고 지우게 했다 (F-13).
   다만 **이름 바꾸기는 넣지 않았다.** 지우고 다시 만들면 항목을 전부 옮겨야 하므로 언젠가 필요해지겠지만, 요청 범위 밖이라 v2 후보로 미뤘다.

## 13. 구현하면서 명세와 달라진 것

만들어보고 나서 조정한 지점들이다. 명세를 그대로 두면 어긋나 보이므로 여기에 남긴다.

**편집 중 `!`는 올리기만 하고 내리지 않는다** (F-03·F-05).
F-03의 "편집 중 입력한 `!`·`#`도 새로 파싱된다"를 글자 그대로 적용하면, 오타 하나 고치려고 편집할 때마다 `!`를 안 썼다는 이유로 `높음`이 `보통`으로 떨어진다. `!`를 "올려라"라는 지시로 읽고, 없으면 기존 값을 유지한다. 태그는 F-07 명시대로 기존에 더한다.

**태그 필터 0건 문구는 도달할 수 없다** (F-09·§7).
"필터 중인 태그를 가진 항목이 0개가 되면 자동으로 `전체`로 복귀한다"가 먼저 걸려서 0건 화면이 나올 자리가 없다. 두 규칙이 겹치고 자동 복귀가 이긴다. 문구는 구현해뒀으니 자동 복귀를 빼면 바로 보인다.

**카테고리 탭에 개수를 넣지 않았다** (§7 화면 설계).
§7 그림에는 `전체 6 │ 업무 3`처럼 개수가 있지만, 그 숫자는 리프 기준 진행률과 계산 기준이 다르다. 두 숫자가 한 화면에서 다르게 세어지면 어느 쪽이 맞는지 알 수 없어 뺐다.

**태그 배지는 `<span>` 안에 버튼 두 개다** (§7 태그 표현).
"배지는 `<button>`으로"를 그대로 따르면서 `×`까지 버튼으로 만들면 버튼 중첩이라 유효하지 않은 HTML이 된다. 필터 동작이 버튼인 것은 지켰다.

**하위 입력창은 포커스가 벗어나도 닫히지 않는다** (F-02).
닫히는 조건으로 `Esc`와 빈 상태 `Enter` 둘만 정해져 있어 그대로 뒀다. 다른 상위의 `+`를 누르면 입력창이 그쪽으로 옮겨간다.

**`load()`는 교정한 데이터를 되쓰지 않는다** (F-12).
여는 것만으로 저장소를 건드리지 않는 편이 안전하다. 다음 변경이 일어날 때 정리된 상태로 함께 저장된다.

**검색은 분류 축과 함께 걸린다** (F-09 vs F-15).
F-09의 "필터는 하나만"은 카테고리와 태그, 같은 성격의 분류 축 둘에 대한 규칙이다. 검색은 분류가 아니라 좁히기라 그 위에 얹힌다. 자세한 이유는 F-15.

**우선순위 4단계는 비목표였다.**
§1이 "우선순위 4단계 이상"을 제외했고 F-05는 3단계 고정이었다. 요청에 따라 0~3으로 늘렸다. 세 단계가 네 단계의 앞자리(0·1·2)로 그대로 들어가므로 기존 데이터의 상대 순서는 바뀌지 않는다.

함께 바뀐 것 둘: 저장값이 문자열에서 **숫자**가 됐고(§5), `보통`에 표시하지 않던 규칙이 **모든 단계에 숫자를 그리는** 것으로 바뀌었다(§7). 네 단계를 색과 굵기만으로 구분시킬 수 없기 때문이다.

**완료상태순 정렬은 F-06을 뒤집는다 — 다만 옵션으로만.**
F-06은 "완료 여부는 정렬에 영향을 주지 않는다"고 못 박았고 그 이유(하루 20번 일어나는 토글에 목록이 흔들리면 위치 기억이 깨진다)는 지금도 유효하다. 그래서 **기본값은 우선순위순 그대로** 두고, 완료상태순은 고를 때만 켜지게 했다. 기본을 쓰는 한 F-06의 수용 기준은 그대로 성립한다.

**수동 정렬은 비목표였다.**
§1이 "항목 순서 수동 정렬"을 제외했지만 요청에 따라 넣었다. 대신 **형제 그룹 안으로만** 한정해, 원래 함께 제외됐던 "드래그로 부모 바꾸기"는 그대로 막아뒀다. 이유는 F-19에 적었다.

**테마 전환은 첫 화면에서 한 번 깜빡일 수 있다.**
`app.js`가 `Store.load()` 뒤에 테마를 칠하므로, OS가 라이트인데 다크를 골라둔 경우 아주 짧게 라이트가 보인다. `<head>`에 인라인 스크립트를 넣으면 없앨 수 있지만, 파일 구성을 흐트러뜨리는 값이 깜빡임보다 크다고 보아 두었다.
